# Escouade — Spécification v1

Anciennement « Claude Code Manager » (jusqu'à la 0.1.3 pour les noms internes). Au premier lancement de la 0.1.4, ce qui existait sous les anciens noms est déplacé : dossier `~/.claude-code-manager/` → `~/.escouade/`, dossiers de l'identifiant `dev.gagnaire.claude-code-manager` → `dev.gagnaire.escouade` (WebView, taille de fenêtre), préférences `ccm.*` → `escouade.*`. La variable `CCM_DATA_DIR` reste acceptée à côté d'`ESCOUADE_DATA_DIR`. Les nouveaux agents travaillent sur des branches `escouade/` ; ceux d'avant gardent leurs branches `ccm/`. La mise à jour réapplique le nouvel identifiant aux raccourcis, dont Windows se sert pour les notifications.

Application desktop pour piloter plusieurs instances de Claude Code en local, organisées par projet.
Référence visuelle : `design/Claude Code Manager.dc.html` (source de vérité pour le look & feel).

## Stack

| Couche | Choix |
|---|---|
| Shell applicatif | Tauri 2 (Windows 10 / 11 et macOS 11+) |
| Backend | Rust (tokio) : process `claude`, PTY (portable-pty), git (gix/CLI), watchers (notify), SQLite (rusqlite), trousseau du système (keyring), corbeille (trash), serveur MCP (`rmcp` 3.5 derrière `hyper`), langue du système (`sys-locale`) |
| Frontend | Svelte 5 + TypeScript + Vite ; textes par catalogues maison (`src/lib/i18n/`) |
| Éditeur | CodeMirror 6 (`@codemirror/merge` pour les changements dans le texte) |
| Terminaux | xterm.js (addon WebGL) |
| Markdown | marked (GFM) + DOMPurify ; pendant le streaming, le message est rendu à nouveau en entier au plus une fois par image ; coloration syntaxique (shiki) une fois le texte final |
| Stockage | `~/.escouade/` (config JSON + SQLite ; `claude/<compte>/` pour le dossier de chaque compte Claude ajouté) |

## Pilotage de Claude Code

- Chat natif (pas de TUI embarqué dans la conversation) ; la *vue Claude Code*, plus bas, montre l'interface de Claude Code elle-même dans un terminal.
- Chaque agent = un process `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages` dans le dossier du projet (ou du worktree de l'agent).
- Les demandes de permission et `AskUserQuestion` remontent via le protocole de contrôle (permission prompts « host ») et s'affichent comme cartes « Claude attend ta réponse ».
- Modèle, effort et mode de permission changeables en cours de conversation.
- **1 agent = 1 conversation.** Reprise après redémarrage via `--resume <session_id>`.
- **Vue Claude Code** (bouton « Vue Claude Code » de l'en-tête de l'agent, ou « Ouvrir les nouveaux agents dans l'interface de Claude Code » dans Réglages › Claude Code ; jamais pour un agent de ticket) : l'agent tourne dans l'interface de Claude Code elle-même, dans un terminal, sur la même session ; un seul process à la fois, changer de vue arrête l'un et reprend la session dans l'autre (faits et formats : `PROTOCOL.md`). **Session à reprendre** (ESC-106) : avant chaque lancement de l'interface, « Relancer » compris, Escouade cherche le transcript de la session (`<dossier du compte>/projects/*/<session>.jsonl`, celui de l'original pour une copie qui n'a pas encore la sienne) dans le dossier du compte de l'agent, parce que Claude Code quitte aussitôt sur une session qu'il ne trouve pas (« No conversation found with session ID… », code 1) et qu'un agent qui n'a rien envoyé n'en a pas encore (Claude Code l'écrit au premier message). Trois issues : trouvé, l'interface reprend la session (`--resume`) ; absent, mais dans le dossier d'un autre compte du même côté (Windows ou WSL), il est copié dans celui du compte de l'agent, la session est reprise et la conversation le dit (information : « La session était dans le dossier du compte « A » : elle a été copiée dans celui de « B » pour être reprise. ») ; absent partout, la session est abandonnée et l'interface démarre une nouvelle session (`--session-id`), avec l'avertissement « Session Claude introuvable : l'interface repart en nouvelle session. » dans la conversation si l'agent avait quelque chose à perdre (des messages envoyés ou des entrées lues ; un agent qui n'a jamais rien envoyé repart sans rien dire), toujours « La session de l'original est introuvable : la copie repart en nouvelle session. » pour une copie dont l'original manque. Une copie qui échoue avertit aussi (« La session est dans le dossier du compte « A », mais elle n'a pas pu être copiée dans celui de « B » (<erreur>) : l'interface repart en nouvelle session. »). **Sortie de l'interface** : « aussitôt » veut dire moins de 20 s après son lancement et un code autre que 0 (un `/exit`, code 0, n'est jamais « aussitôt » : « Claude Code s'est arrêté. » et « Relancer »). Aussitôt, avec « No conversation found » dans ses premiers Ko de sortie (une session que le contrôle n'a pas pu juger, un transcript que Claude Code ne voit pas) : la session est abandonnée de la même façon, avec le même avertissement, et la vue relance l'interface d'elle-même, une seule fois, sur la nouvelle session, sous la note « Session Claude introuvable : l'interface repart en nouvelle session. » (6 s une fois l'interface lancée). Aussitôt pour toute autre raison, ou une deuxième fois de suite : aucune relance, « Claude Code s'est arrêté dès son lancement (code N). Regarde sa sortie ci-dessus, puis relance-le. » (sans « (code N) » si le process a été tué) et « Relancer », la sortie restant lisible dans le terminal. « Relancer » est un lancement manuel : il passe toujours et remet à zéro le compte des sorties aussitôt de suite, que le backend tient aussi pour refuser un lancement automatique à la deuxième (« Claude Code s'arrête dès son lancement (2 fois de suite) : regarde sa sortie, puis clique sur « Relancer ». ») ; changer de vue le remet à zéro aussi. La vue ne dépend que de l'identité de l'agent : la fin de l'interface, qui met l'agent à jour, ne la relance pas.
- Chaque agent tourne sur un compte Claude (voir *Comptes Claude*) : son process reçoit le `claude` et le `CLAUDE_CONFIG_DIR` de ce compte, et reprend sa session dans ce dossier. Le compte Principal ne reçoit jamais `CLAUDE_CONFIG_DIR`.
- Serveur MCP d'Escouade : tant que « Claude et les agents peuvent piloter Escouade » est activé (et que le serveur tourne), chaque agent le reçoit par `--mcp-config` (avec un jeton à lui) ; sinon il en est tenu à l'écart par `--settings` (`deniedMcpServers`) et `--disallowedTools mcp__escouade` (voir *Serveur MCP*).
- Chaque agent reçoit `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` tant que « Les agents tiennent une liste de tâches » est actif (par défaut) : les outils de liste de tâches de Claude Code, dont l'avancée de l'agent se lit (voir *Avancée d'un agent qui exécute un plan*).
- Ce qu'Escouade dit aux agents et fait écrire à Claude suit « Langue des textes rédigés par Claude » (voir *Langues*).

## Fenêtre

- Fenêtre sans cadre : la barre d'onglets du design sert de barre de titre (zone de drag), boutons Windows ─ ☐ ✕ à droite (à la place des pastilles macOS) ; sous macOS, la barre de titre native garde ses boutons de fenêtre.
- Thème sombre du design, teinté par la couleur du projet actif (`color-mix` sur les tokens).
- Polices Hanken Grotesk + JetBrains Mono embarquées (hors-ligne).
- Infobulles : une seule, celle de l'app (`use:tip`, `lib/tip.ts` ; aucun `title` natif, un test échoue sur un nouveau), au style de la barre d'état (fond `--elev`, bordure `--line2`, ombre, 11,5 px, plusieurs lignes possibles). Elle s'affiche après 400 ms de survol, tout de suite quand Tab ou une flèche y amène le focus (pas au focus d'un clic, ni à celui qu'une fenêtre qui se ferme rend à son bouton), et la suivante tout de suite pendant 300 ms après qu'une a disparu ; une seule à la fois (l'élément le plus intérieur sous le pointeur ou le focus l'emporte, s'il a quelque chose à dire ; revenu sur l'élément qui l'entoure, le pointeur retrouve l'infobulle de celui-ci). Au-dessus de l'élément, centrée, en dessous faute de place, toujours dans la fenêtre. Elle reste tant que le pointeur ou le focus est sur l'élément, et part au clic (sans revenir avant que le pointeur ressorte), au défilement de ce qui contient l'élément (pas d'une conversation qui suit la réponse en cours), quand la fenêtre perd le focus, ou avec Échap (WCAG 1.4.13 : le focus ne bouge pas, et quand il est dans l'élément, Échap ne fait rien d'autre que ce que l'élément en fait lui-même, ni fermer une fenêtre ni interrompre un tour). Un texte coupé (points de suspension) n'a son infobulle que s'il est coupé. Lecteur d'écran : un contrôle qui n'affiche qu'un symbole ou une icône (⚙, ×, ⌕) est nommé par son infobulle ; un autre contrôle est décrit par elle tant qu'elle est affichée (`aria-describedby`, comme Radix) ; un élément hors de l'ordre de tabulation reçoit `aria-description`. Le graphique des stats garde son infobulle riche (titre, séries), au même style.
- Fermer la fenêtre → réduction dans le tray, les agents continuent. « Quitter » (menu tray) → arrêt propre ; au relancement, chaque agent reprend sa session. Le menu du tray : « Afficher », « Recharger l'interface » (voir ci-dessous), « Quitter ».
- La fenêtre ne quitte jamais l'interface de l'app (ESC-101, issue #9 : un clic sur un lien de la conversation chargeait la page dans la fenêtre, sans bouton retour). La fenêtre principale est construite par `build_window` (`src-tauri/src/lib.rs`) avec des gestionnaires de navigation et de nouvelle fenêtre que juge `src-tauri/src/navigation.rs` : seules les pages de l'app passent (`http(s)://tauri.localhost` sous Windows, `tauri://localhost` ailleurs, et le `devUrl` en développement) ; une page web (`http`, `https`) ou une adresse `mailto` est ouverte hors de l'app, dans le navigateur ou le client de messagerie du système, et tout le reste (fichier, `about:blank`…) est refusé et n'ouvre nulle part. Chaque refus est écrit dans le journal, schéma et hôte seulement. Côté fenêtre, `lib/links.ts` (installé par `main.ts`) attrape tout clic de lien en phase de capture sur le document, avant tout autre gestionnaire : clic gauche, clic du milieu, `Ctrl` / `Maj` + clic et `Entrée` sur un lien qui a le focus ouvrent `http`, `https` et `mailto` dans le navigateur sans que la fenêtre suive le lien (un double clic ne l'ouvre qu'une fois) ; un autre lien (chemin relatif, `#…`, `[texte]()` vide, qui rechargeait toute l'interface) ne fait rien. Le gestionnaire de clic du markdown (`handleMarkdownClick`, `lib/markdown.ts`) ne traite plus que les boutons de copie des blocs de code. Terminaux et vue Claude Code (`lib/terminals.ts`) : le `linkHandler` de xterm.js ouvre les liens OSC 8 (ceux que Claude Code écrit lui-même, dont le texte diffère de l'adresse) dans le navigateur au clic, sans le `confirm()` par défaut (« Do you want to navigate to … ? »), seuls `http` et `https` étant cliquables ; une URL écrite en clair s'ouvre dans le navigateur comme avant. Filet de sécurité : l'entrée « Recharger l'interface » (« Reload the interface »), entre « Afficher » et « Quitter » dans le menu de l'icône de la zone de notification, recharge la fenêtre sur l'interface de l'app si elle restait bloquée ou blanche, en demandant d'abord (dialogue natif « Recharger » / « Annuler ») quand la fenêtre est sur l'app et que des fichiers de l'éditeur ne sont pas enregistrés.

## Langues

- Interface en français et en anglais. Réglages › Application › « Langue de l'interface » : « Système (…) » (défaut ; la langue du système y est nommée dans celle de l'interface), « English » et « Français » (chacune nommée dans elle-même). La langue du système est lue par le backend (`sys-locale`, une fois par lancement) et dite à la fenêtre pour que les deux côtés s'accordent : français si la langue de la première étiquette de locale est `fr` (`fr`, `fr-CA`, `fr_FR.UTF-8` ; pas `frr`), anglais sinon. Jusqu'à la lecture des réglages, la fenêtre part de `navigator.language` (même règle) et le backend est en français (l'app l'était jusqu'à la 1.6). Le changement s'applique à l'enregistrement, sans redémarrer ni recharger : `<html lang>`, la fenêtre, le menu de l'icône de la zone de notification et son infobulle, et sous macOS le menu de l'app (même entrées que celui de Tauri, avec les mots de macOS) sont réécrits ; les menus ne le sont que lorsque la langue de l'interface change. Ce que macOS ajoute de lui-même à ses menus (dictée, emoji et symboles, liste des fenêtres) suit la langue du système parmi `CFBundleLocalizations` (`en`, `fr`), non le réglage. Installeur Windows (NSIS) en anglais ou en français selon la langue du système. Seule une installation neuve suit la langue du système : un fichier de réglages d'avant la 1.7 (sans `language`) garde l'interface en français après la mise à jour, et avec elle les textes pour Claude, qui suivent l'interface par défaut ; l'utilisateur choisit « Système » ou « English » dans Réglages › Application.
- Fenêtre : un catalogue par langue et par zone (`src/lib/i18n/fr/`, `en/`), clés `zone.composant.sens` ; une clé absente ou en trop, ou des paramètres qui diffèrent d'une langue à l'autre, ne passent ni `svelte-check` ni les tests. Paramètres `{nom}`, pluriels `{ one, other }` choisis par `Intl.PluralRules` (paramètre `count`), une phrase entière par clé (jamais de fragments recollés : l'ordre des mots change), `Rich` pour une phrase à morceaux balisés. `t()` lit la langue au moment d'afficher : aucun texte n'est figé au chargement d'un module (une table de libellés est une fonction, un getter ou un `$derived`). Un garde-fou fait échouer les tests quand un texte visible est écrit en dur hors des catalogues (exceptions justifiées une à une). Les tests existants restent en français ; une série en anglais couvre formats, pluriels et écrans, et un e2e tourne en anglais. Glossaire `src/lib/i18n/GLOSSARY.md` : « À tester » se dit « To review » (colonne `review`), « Principal » « Main », « fenêtre de 5 h » « 5-hour window ».
- Backend : un texte est écrit dans les deux langues à l'endroit où il sert, `tr!("texte fr {x}", "english {x}", x = …)` (le compilateur refuse un argument nommé que l'une des deux n'utilise pas), `tr_in!` pour une langue donnée, `tr_n!` / `tr_n_in!` pour un nombre (français : 0 et 1 au singulier ; anglais : 1 seul). Une fonction qui prend la langue permet de tester l'anglais sans toucher à la langue globale. Le journal (`log::`) reste en anglais. Une erreur que la fenêtre doit reconnaître passe par un code (`NOT_FOUND:<chemin>`, `DIRTY`, `IN_WORKTREE:…`), non par un mot. Sont concernés : erreurs, toasts, notices de la conversation, activité d'un agent, raisons d'un ticket bloqué, issue d'une validation, ce que dit le Kanban quand rien ne démarre, notifications du système, menus, étapes des statistiques (« 27/09 », « S39 », « sept. » / « Sep 27 », « W39 », « Sep »).
- Formats, en un seul endroit (`format.ts` et son pendant Rust) : montants « 0,10 $ » (espace insécable) / « $0.10 », pourcentage « 42 % » / « 42% », tokens « 1,2 k · 2,35 M · 3,20 Md » / « 1.2k · 2.35M · 3.20B », durées « 1h 48m », comptes à rebours « 4j 12h » / « 4d 12h », tailles « 312 Mo » / « 312 MB », dates « 2 octobre 2026 à 09:30 » / « October 2, 2026 at 9:30 AM » (`Intl`, `fr-FR` / `en-US`), temps relatifs « il y a 5 min », « hier », « il y a 4 j » / « 5 min ago », « yesterday », « 4 days ago ». Les touches des raccourcis s'écrivent comme sur le clavier de la langue (`Ctrl+Maj+Entrée` / `Ctrl+Shift+Enter`, `Échap` / `Esc`). L'heure d'une reprise s'écrit en 24 h (« reprise à 15:00 ») dans les textes du backend, dans les deux langues ; la fenêtre, elle, écrit les heures avec la locale de l'interface (« 15:00 » / « 3:00 PM », par exemple « Quota atteint — reprise à 15:00 » / « Quota reached — resumes at 3:00 PM »).
- Texte enregistré dans la langue de son moment : ce qui est écrit une fois puis relu plus tard garde la langue où il a été écrit, un changement de langue ne le réécrit pas. C'est le cas des notices de la conversation, de la raison d'un ticket bloqué (`blocked`), de l'issue d'une validation (`outcome`, avec `outcome_claude`, la même dans la langue des textes pour Claude, que cite le commentaire publié), de l'étape de validation en cours, des critères par défaut d'un ticket, du nom d'une copie (« (copie) » / « (copy) »), de la ligne d'origine d'un ticket importé (« Ticket Jira X : <adresse> »), du nom d'un état GitHub gardé dans la correspondance des statuts, du protocole et de la consigne de copie gardés avec l'agent à sa création (`append_prompt`). Le nom du compte Principal est enregistré dans la langue du premier enregistrement, mais s'affiche « Principal » / « Main » selon la langue tant qu'il n'a pas été renommé. À l'inverse, suivent la langue du moment : le texte d'un quota illisible (l'état est gardé, le texte réécrit), un `BoardIssue` (réécrit au passage suivant du Kanban), et les étapes des statistiques (relues par la fenêtre au changement de langue).
- Textes pour Claude. Réglages › Application › « Langue des textes rédigés par Claude » : « Comme l'interface » (défaut), « English » ou « Français ». Elle porte sur tout ce qu'Escouade dit aux agents ou fait écrire : protocole d'un ticket et ses messages (boucles, relance du bilan, reprise, retour de test, tests en échec, merge et rebase de la branche cible), « Préparer le lancement », message de commit d'un ticket et description de sa pull request, message proposé pour un commit direct, nom donné à un agent par Haiku, questions de « ✦ Remplir automatiquement » (et noms des commandes proposées), consigne d'une copie d'agent, « continue » de la reprise, demande de commit envoyée à l'agent, refus d'une autorisation sans message, refus d'un plan, et commentaires publiés dans Jira, Trello et GitHub. Chaque texte est écrit par une fonction qui prend la langue du réglage (celle du cœur). Les marqueurs que le code relit ne se traduisent pas : la clôture ```` ```escouade ```` et les clés JSON (`criteres`, `n`, `ok`, `note`, `avancement`, `lancement`, `preparation`, `processus`, `nom`, `commande`, `dossier`, `env`, `url`, `ouvrir`, `demontage`, `commandes`) sont les mêmes dans les deux langues, et certains analyseurs acceptent aussi des équivalents anglais (`criteria`, `progress`, `setup`, `teardown`, `name`, `command`…). Le message de commit d'un ticket nomme sa langue (un ticket importé dans une autre ne la décide pas). Le message proposé pour un commit direct est écrit dans la langue choisie quand le réglage en nomme une (même sans commit dans le dépôt) ; avec « Comme l'interface », il imite la langue des derniers commits du dépôt (comportement de la 1.6, dit par l'aide du réglage). Les descriptions des outils du serveur MCP sont en anglais seulement, leurs refus et erreurs dans la langue de l'interface.
- Site et vidéo : le site (`website/`) est généré en deux pages, le français à la racine (les liens existants restent bons) et l'anglais sous `/en/`, chacune avec sa langue (`<html lang>`), son titre, sa description, ses balises de partage, son lien canonique et ses `hreflang` ; les textes sont dans deux catalogues de mêmes clés (un test le vérifie), les liens, la version et les noms propres communs. Sélecteur « FR / EN » dans l'en-tête, choix gardé (stockage local) ; à la première visite de la racine, un petit script envoie vers `/en/` un navigateur sans français, sauf choix gardé ou `?lang=fr` (sans JavaScript, rien ne bouge). Une adresse inconnue affiche une page « introuvable » dans la langue de l'adresse. La vidéo garde sa voix française ; la page anglaise propose ses sous-titres anglais par défaut (mêmes repères que les français) et ses captures et son affiche faites avec l'interface reconstituée de la vidéo en anglais (`npm run site-images`, une langue ou les deux). README et CHANGELOG restent en français ; pas de README anglais ni de voix anglaise en 1.7.

## Barre d'onglets

- Un onglet par projet : pastille couleur, nom, point vert si un agent tourne, compteur `Δ n` (fichiers non commités, worktrees des agents inclus), pastille pulsante = nombre d'agents en attente.
- `+` ouvre la modale « Nouveau projet ». Onglet « Stats » à droite. À gauche des onglets de projets, séparé par un filet : « Vue d'ensemble » (voir *Vue d'ensemble*).
- Défauts : onglets réordonnables par glisser ; clic droit → renommer, couleur, worktree par agent, « Réglages du projet… » (onglet « Projets » des réglages), ouvrir le dossier, fermer le projet (retire de l'app et garde son historique, ne touche pas au disque : voir *Fermer un projet, retrouver son historique*).

## Modale « Nouveau projet »

Dossier (+ Parcourir…), détection git (sinon `git init`), nom, aperçu d'onglet, 14 couleurs, bascule « Créer un premier agent » (+ modèle), bascule « Un worktree git par agent ». Quand le dossier est celui d'un projet fermé qui a gardé son historique, la fenêtre le dit (« Historique retrouvé : 12 agents, 34 tickets, dernière activité le 14 octobre 2026 »), préremplit le nom, la couleur et « Un worktree git par agent » avec ceux du projet fermé, et le bouton devient « Rouvrir le projet » ; la bascule « Partir d'un projet vierge » (« L'historique reste dans Réglages › Projets, où l'effacer. ») crée un projet neuf à la place (voir la section suivante). Ouverte par « Rouvrir » sur un projet fermé (Réglages › Projets › Projets fermés), la fenêtre part du dossier de ce projet, lu tout de suite (sans l'attente d'une frappe), et de cet historique-là (`app.modal = { kind: 'newProject', path, historyId }`, puis `inspect_folder { path, historyId }` et `create_project { …, historyId }`, la clé n'étant envoyée que si elle existe) : changer le chemin saisi abandonne `historyId`, le remettre tel qu'au départ le rend. « Annuler » ferme la fenêtre sans revenir aux réglages.

## Fermer un projet, retrouver son historique

Demandé le 2026-10-14, pour la 1.8 (ESC-89).

- **Fermer** (`Core::remove_project`, commande `remove_project { id, erase }`) retire le projet de l'app et arrête ses process, ses terminaux, ses préparations de worktree, ses lancements de test et ses services isola, comme avant. Il ne touche ni aux fichiers du dossier, ni aux worktrees, ni aux sessions de Claude Code, ni aux stats (`stats.db`, rangées par id de projet). La fenêtre de confirmation dit que l'historique est gardé et propose la case « Effacer aussi son historique (conversations, tickets, réglages) », décochée par défaut (la zone sensible de Réglages › Projets montre la même confirmation).
- **Ce qui est gardé** : un fichier `<dossier de données>/closed-projects/<id du projet>.json` (« projet fermé ») avec le `Project` entier (réglages, Kanban, intégrations, commandes de lancement et de préparation…), les `AgentMeta` de tous ses agents (archivés compris), ses tickets, l'agent sélectionné et la date de fermeture (pas les comptes qui lui étaient réservés : voir *Comptes* et la puce « Réservations et projet fermé »). Les journaux de conversation (`conversations/<agent>.jsonl`), ceux de préparation de worktree et les images des tickets (`tickets/<id>/`) restent où ils sont ; ce qu'un tour coupé laissait ouvert y est fermé (question ou permission annulée, outil interrompu, texte qui ne s'écrit plus). Le fichier est écrit deux fois : avant que rien ne s'arrête (s'il ne peut pas l'être, le projet reste ouvert : « L'historique du projet n'a pas pu être écrit (…) : le projet reste ouvert. »), puis une fois tout arrêté (un échec, rare, est dit par un toast, la première écriture restant). Un arrêt brutal de l'app pendant la fermeture ne perd donc rien : au démarrage suivant, un projet resté ouvert qui a un fichier de projet fermé y reprend les agents et les tickets que l'état enregistré n'avait plus, et le fichier s'efface une fois l'état enregistré. Deux fermetures du même projet en même temps n'en font qu'une ; l'historique final part du projet tel qu'il sort de la liste (un ticket créé ou un réglage changé pendant la fermeture y est). Les comptes gardent le projet dans leur « Réservé aux projets » : fermer en gardant l'historique n'y touche pas. Les blocs de ports des agents d'un projet fermé restent retenus : aucun autre agent ne les reçoit en attendant sa réouverture. Un ticket « En cours » à ce moment est gardé bloqué avec « Projet fermé pendant le ticket » (« Project closed during the ticket » en anglais, dans la langue de l'interface) ; un ticket dont la validation tournait repasse sans étape, bloqué comme après un redémarrage (« Validation interrompue »), sans conflit.
- **Pas pendant une validation.** Fermer est refusé tant que la validation d'un ticket du projet tourne (`step` présent) : « La validation du ticket {key} est en cours : attends sa fin pour fermer le projet. » (dans la langue de l'interface) ; et une validation ne démarre pas sur un projet en cours de fermeture.
- **Synchros d'intégration.** `run_ticket_syncs` (statut externe, commentaires de boucle…) oublie les opérations en file d'un ticket absent de la liste des tickets de l'app. Celles d'un ticket d'un historique fermé sont gardées, mises de côté (ni tentées ni oubliées) ; la réouverture relance les synchros du projet ; effacer l'historique (la case à la fermeture, ou « Effacer l'historique… ») oublie celles de ses tickets.
- **Index en mémoire.** L'app tient un index des projets fermés, chargé au démarrage et mis à jour à chaque écriture et à chaque effacement : id, clé de dossier (`folder_key`), infos de la liste (`ClosedProjectInfo`), blocs de ports de ses agents non archivés, ids de ses tickets. `closed_projects`, `inspect_folder` (qui ne touche plus au disque), la retenue des ports et les synchros le lisent. Ce qui lit encore le disque (le repli sur le chemin canonique de la recherche par dossier, la lecture complète d'un historique pour le rouvrir ou l'effacer) passe par `tokio::task::spawn_blocking` et se fait hors des verrous.
- **Rouvrir** : ajouter un projet dans le dossier d'un projet fermé (`inspect_folder` rend alors `history`, un `ClosedProjectInfo` : id, nom, couleur, dossier, worktree par agent, nombre d'agents non archivés et de tickets, dernière activité, date de fermeture, taille) lui rend son historique **avec le même id**, donc ses stats : réglages, agents (sans process, comme après un redémarrage de l'app ; un worktree disparu suit la règle d'aujourd'hui), conversations, tickets (un ticket « En cours » revient bloqué, « Reprendre » le relance), et ses synchros d'intégration en file. Les réservations de comptes n'ont pas quitté les comptes : rien à remettre. `inspect_folder` prend `historyId` (facultatif) et rend cet historique-là s'il est lisible et dans ce dossier, sinon le plus récent du dossier. `create_project` prend `restore` (vrai par défaut) et `historyId` (facultatif : avec `restore`, il rouvre celui-là s'il est lisible et dans ce dossier, sinon comme avant) ; son `firstAgent`, s'il est donné, est honoré en plus (la fenêtre n'en demande pas quand un historique est trouvé). Le nom, la couleur et « Un worktree git par agent » sont ceux que la fenêtre envoie (nom vide : celui de l'historique) ; le chemin du projet reste celui de l'historique, d'où ses agents et ses worktrees ont été faits (le même dossier, peut-être écrit autrement) ; son « Compte préféré » retombe sur Automatique si ce compte n'existe plus. Le fichier est supprimé une fois l'état enregistré (`save_now` avant), pour qu'un arrêt brutal ne perde rien. Si ce fichier ne peut pas être supprimé (antivirus, fichier ouvert), l'état retient avant la suppression les ids des agents et des tickets de cet historique : ce que l'utilisateur supprime ensuite ne ressuscite pas au démarrage suivant, qui retente de supprimer le fichier sans jamais le refusionner. Plusieurs projets fermés au même dossier : le plus récemment fermé. Les agents et les tickets rendus sont émis à l'interface avant la réponse ; ses agents Remote Control redémarrent comme au lancement de l'app. Un second ajout pendant que le premier rouvre le projet rend ce projet, pas un projet vierge de plus. Le fichier n'est supprimé que si l'état a pu être enregistré. Une réouverture n'est pas comptée comme une création de projet dans les statistiques anonymes (pas d'événement `project_created`). La recherche du dossier compare d'abord les chemins sans toucher au disque, puis, seulement si rien ne correspond, le chemin canonique du dossier saisi à ceux des projets fermés sur un disque local (jamais un partage réseau ou WSL, qui pourrait bloquer ou démarrer une distribution).
- **Le même dossier** se reconnaît par `folder_key` (`paths.rs`) : espaces de bord retirés, préfixes `\\?\` et `\\?\UNC\` retirés (le second devient `\\`), sous Windows `\` lu comme `/`, `/` répétés réduits à un (sauf le `//` d'un chemin UNC) et `/` final retiré ; un partage WSL (`//wsl$/<distribution>/…` ou `//wsl.localhost/<distribution>/…`, hôte sans égard à la casse) devient `//wsl.localhost/<distribution en minuscules>/…` (Linux distingue la casse du reste) ; sinon tout en minuscules sous Windows, la casse gardée ailleurs. `same_folder` ajoute les chemins qui se canonicalisent vers le même dossier (noms courts 8.3, liens).
- **Partir d'un projet vierge** (`restore: false`) : un projet neuf, avec un nouvel id comme avant ; l'historique reste un projet fermé, listé dans Réglages › Projets › « Projets fermés ». Rien n'est effacé sans demande.
- **Effacer** : « Effacer aussi son historique » à la fermeture fait ce que faisait « Fermer » avant (journaux de conversation et de préparation et images des tickets supprimés, rien dans `closed-projects`) ; dans les deux cas, le projet sort aussi de « Réservé aux projets » de chaque compte et les synchros d'intégration en file de ses tickets sont oubliées. Pour un projet fermé, « Effacer l'historique… » (`erase_closed_project { id }`, après confirmation : « Ses conversations, ses tickets et ses réglages sont effacés pour de bon. Les fichiers et les worktrees sur le disque ne sont pas touchés. ») supprime son fichier, les journaux de ses agents et les images de ses tickets (tout passe par `erase_history_files`, le seul endroit où s'effacent les fichiers d'un historique). Erreur lisible, dans la langue de l'interface, si aucun projet fermé n'a cet id.
- **Liste** (`closed_projects`, du plus récemment fermé au plus ancien) : Réglages › Projets › « Projets fermés » (seulement s'il y en a, sous la note « Leur historique est gardé : ajouter un projet dans leur dossier le retrouve. »), par projet : pastille, nom, dossier, taille (son fichier, les conversations et les journaux de préparation de ses agents, les images de ses tickets), « dernière activité le … » (la plus récente date d'un agent ou d'un ticket, à défaut la fermeture), « Rouvrir » (la fenêtre d'ajout sur son dossier et sur cet historique-là, même quand le dossier en a plusieurs : voir *Modale « Nouveau projet »*) et « Effacer l'historique… ». Un fichier dont l'id est celui d'un projet ouvert (arrêt brutal entre l'écriture du fichier et l'enregistrement de l'état) est ignoré partout : listes et recherche par dossier.
- **Fichier illisible.** Un fichier de `closed-projects/` dont le JSON est invalide, ou dont le nom n'est pas `<id de son contenu>.json` (pourvu que son nom soit un nom de fichier simple), est listé quand même (`ClosedProjectInfo.unreadable`) : `id` est son nom sans `.json`, `name`, `color` et `path` sont vides, `agents` et `tickets` valent 0, `size` est celle du fichier, `closedAt` et `lastActivity` sont sa date de modification. La liste le montre comme « Historique illisible » avec le nom `<id>.json` et sa taille, sans « Rouvrir », avec « Effacer » (confirmation, danger : « Ce fichier, que l'application ne peut pas lire, est effacé pour de bon. Les autres historiques, les fichiers et les worktrees sur le disque ne sont pas touchés. ») ; `erase_closed_project { id }` supprime alors ce seul fichier.
- **Avant la 1.8** : un projet fermé avant cette version a perdu son historique à la fermeture, il n'y a rien à retrouver et rien à migrer.

## Barre latérale projet

- **Agents** : compteur, « + Nouvel agent » (et, à côté, un menu « Nouvel agent sur une branche… » : voir *Git & fichiers*). Carte : statut (Prêt / En cours / Question / Terminé), nom, modèle · durée active, tokens · coût · nb fichiers ; pour l'agent d'un ticket, « ▸ ATL-42 · boucle 2/5 » (« · à tester » une fois le ticket à tester : voir *Kanban*) ; sous le nom, la ligne d'état que l'agent a donnée par `report_progress`, s'il en a donné une (voir *Serveur MCP*) ; quand il a une liste de tâches, une mini-barre et « Plan 2/7 » ou « Plan 2/7 · 3 sous-agents » (voir *Avancée d'un agent qui exécute un plan*) ; sous la carte, tant que son plan a des sous-agents (en cours ou finis), le groupe « Sous-agents de <agent> » (voir *Avancée d'un agent qui exécute un plan*, « Sous-agents »).
- Nom créé en `agent-N`, puis renommé automatiquement en slug par Haiku après le premier message. Renommable (double-clic).
- Clic droit : Renommer, « Dupliquer la conversation » (ci-dessous), Archiver (historique du projet, réouvrable), Préparer le lancement (agent à worktree, pas tant que son ticket est « En cours » : voir *Kanban*), « Intégrer <base> » (agent à worktree, non archivé : voir *Git & fichiers*), Ouvrir dans l'éditeur, « Ouvrir un terminal » (dans son worktree, sinon le dossier du projet ; nommé « <shell> · <agent> », avec le premier shell détecté ; pas pour un agent archivé), Supprimer (arrête le process, supprime le worktree après confirmation si non mergé).
- « Dupliquer la conversation » (pas pour un agent archivé ; désactivé pendant un tour, « Attends la fin de son tour. », et refusé par le backend : « Attends la fin du tour de <nom> pour le dupliquer. ») : crée « <nom> (copie) », puis « (copie 2) »…, dans le même projet, avec le même modèle, effort et mode, et la sélectionne. La copie montre la conversation de l'original (écrite d'un bloc, un ajout par élément) ; son process démarre avec `--resume=<session de l'original> --fork-session --resume-session-at=<dernière entrée>` (la dernière réponse de l'assistant ou le dernier résultat d'outil du fil principal, noté et enregistré avec l'agent dès qu'il change, donc aussi après un arrêt brutal en plein tour) jusqu'à son premier tour, qui lui donne sa propre session : l'original n'est jamais touché, et ses tours suivants ne sont pas dans la copie. Une copie de copie qui n'a encore rien fait reprend le même point. Limites : un agent qui n'a fait aucun tour depuis la 1.6, ou qui vient de compacter sa conversation, n'a pas de point noté et sa copie reprend toute sa session telle qu'elle est au lancement de la copie ; un point introuvable (l'original a compacté depuis) donne « Point de copie introuvable dans la session de l'original : Claude reprend toute sa conversation, jusqu'à maintenant. » ; une session de l'original disparue est traitée comme une reprise perdue (nouvelle session). Avec un worktree, la copie a le sien, sur une branche `escouade/<nom de l'original>-copie` (`-copie-2`…, 40 caractères au plus) partie du commit où en est l'original, avec la même branche de base, les fichiers copiés et la préparation d'un nouvel agent ; `--append-system-prompt` lui dit « Cette conversation a été copiée depuis un agent qui travaillait dans <dossier>. Tu travailles maintenant dans <dossier de la copie> : ne lis et n'écris que dedans. » ; des modifications non commitées de l'original donnent la notice « Les modifications non commitées de <original> ne sont pas dans cette copie. ». Si ce worktree ne peut pas être créé, aucune copie n'est faite. Sans worktree, la copie travaille dans le même dossier. Un agent de ticket se copie en agent ordinaire (ni ticket, ni protocole, ni ports) ; ni les coûts, ni le remote control allumé à la main (un réglage allumé couvre la copie comme tout nouvel agent, sauf si l'original est mis à part : la copie l'est aussi), ni les recettes et leurs approbations ne passent à la copie.
- **Remote control** (éteint par défaut ; allumé au clic droit, pour un agent, ou par un réglage, pour tous les agents d'un projet ou de l'app) : la session de l'agent devient accessible depuis claude.ai et l'app Claude mobile, sous le nom « projet · agent » (requête de contrôle `remote_control` avec `name` ; pour un agent de ticket, son nom vient du ticket). Escouade lance tout de suite le process de chaque agent, au plus 3 à la fois ; il reste lancé (démarré avec l'app, jamais arrêté pour inactivité) et retrouve la même session distante après un redémarrage (`reattach_session_id`, `keep_session_on_exit`), donc le lien reste valable, que le remote control vienne du clic droit ou d'un réglage. Renommer un agent renomme sa session distante (`rename_session`, vérifié : le titre change sur claude.ai) ; renommer un projet renomme les sessions distantes des agents reliés en vue Escouade, et une interface de la vue Claude Code garde l'ancien nom jusqu'à son prochain lancement. Les messages envoyés depuis claude.ai s'affichent dans l'app (« depuis claude.ai ») grâce à `--replay-user-messages` ; l'écho des messages envoyés depuis l'app est écarté par son uuid. Icône sur la carte (connecté / en attente) ; clic droit : Ouvrir sur claude.ai, Copier le lien. Couper le remote control (clic droit, réglage éteint, archivage, suppression) ferme la session distante, archivée sur claude.ai (réserve : voir *Fin du remote control*) ; restaurer un agent archivé la lui rend si un réglage le couvre (pas s'il était allumé à la main, comme avant). « Remote control indisponible : … » (le lien n'a pas pu s'établir) n'est dit qu'une fois par agent et par lancement d'Escouade (rien n'est gardé d'un lancement à l'autre), jusqu'à un lien réussi ou un rallumage à la main.
  - **Fin du remote control** : `enabled:false` n'archive pas une session ouverte avec `keep_session_on_exit` (« skipArchive » : elle restait orpheline sur claude.ai, vérifié sur Claude Code 2.1.300). Pour la fermer, Escouade envoie `enabled:false`, puis `enabled:true` avec `reattach_session_id` et `keep_session_on_exit:false`, puis `enabled:false`. Passer un agent en vue Claude Code ferme ainsi la session distante de sa vue Escouade (son interface ouvre la sienne) ; revenir en vue Escouade en ouvre une nouvelle, avec un nouveau lien. L'identifiant d'une session distante (`remote_session` de l'agent) est gardé tant que sa fermeture n'a pas réussi : si aucun process de l'agent ne tourne quand le remote control s'arrête (juste après le démarrage, après un lien raté, process mort), aucune requête ne peut la fermer sur le moment, et elle est fermée au prochain démarrage d'un process de l'agent, ou reprise (même lien) si le remote control est revenu entre-temps. Une fermeture qui échoue (requête refusée, process mort) est journalisée et laisse l'identifiant. Ce qui lie le process à claude.ai et ce qui ferme la session passent l'un après l'autre, par agent : une coupure suivie d'un rallumage rapide n'entremêle pas leurs requêtes.
  - **Réglage global** : Réglages › Claude Code, groupe « Remote control » (juste avant « Escouade dans Claude » et son interrupteur « Claude et les agents peuvent piloter Escouade »), interrupteur « Remote control pour tous les agents » (éteint par défaut), décrit par « Chaque agent de chaque projet, existant ou nouveau (agents des tickets compris), est accessible depuis claude.ai et l'app Claude. Escouade lance tout de suite le process claude de chacun, qui reste lancé. La session apparaît sur claude.ai sous le nom « projet · agent » (pour un agent de ticket, son nom vient du ticket). En vue Claude Code, une interface déjà ouverte ne le prend qu'à son prochain lancement. Pour mettre un agent à part : clic droit, « Désactiver le remote control ». »
  - **Réglage d'un projet** : Réglages › Projets, groupe « Remote control » (après « Identité »), interrupteur « Remote control pour les agents de ce projet » (éteint par défaut), avec la même description, pour les agents du projet (« Chaque agent de ce projet, existant ou nouveau… »). Les deux sont des réglages du brouillon comme les autres : ils marquent leur onglet comme modifié et s'enregistrent avec « Enregistrer ».
  - **Jamais deux interrupteurs qui se contredisent** : le global allumé, l'interrupteur du projet se montre allumé et grisé, avec « Activé pour tous les projets dans Réglages › Claude Code » (aussi sa description pour les lecteurs d'écran). La valeur propre du projet est gardée, un clic sur l'interrupteur grisé ne change rien : le global éteint (même dans le brouillon), le projet retrouve son état.
  - **Allumé**, un réglage vaut pour les agents existants non archivés de son périmètre et pour chaque nouvel agent, agents de tickets et copies « Dupliquer la conversation » compris : Escouade lance tout de suite leur process, au plus 3 à la fois, et il reste lancé (en vue Claude Code, un démarrage garde sa place jusqu'à ce que l'interface soit prête, 15 s au plus). **Éteint**, il retire le remote control aux agents qui le tenaient de lui (leur session distante est fermée), sans toucher à ceux allumés à la main ni à ceux qu'un autre réglage couvre encore (global éteint, projet allumé : l'agent le garde, par le projet).
  - **D'où il vient** : trois sources, le clic droit (« à la main »), le réglage du projet et le réglage global. L'infobulle de l'icône d'ondes de la carte ajoute à sa fin, après « · », laquelle l'a allumé : « activé à la main », « activé par le réglage du projet » ou « activé par le réglage de tous les agents ». Le clic droit reste possible quelle que soit la source.
  - **Mettre un agent à part** : « Désactiver le remote control » au clic droit le retire toujours à l'agent et le met à part, qu'un réglage (celui de son projet ou le global) le couvre ou non à ce moment : aucun réglage ne le lui rend, ni quand il s'allume ensuite ni au redémarrage d'Escouade, jusqu'à ce que « Activer le remote control » le rallume à la main. Une copie (« Dupliquer la conversation ») d'un agent mis à part l'est aussi. Le ticket d'un agent mis à part le garde : un ticket renvoyé en « À faire » puis relancé crée un agent lui aussi mis à part, sauf si le remote control a été rallumé à la main.
  - **Vue Claude Code** : mêmes règles. Vérifié sur Claude Code 2.1.300 et 2.1.301 (2026-10-15) : l'interface d'un agent en remote control est lancée avec `--remote-control=<projet · agent>` (un seul argument : un nom qui commence par « - » n'est pas pris pour une option) ; Claude Code affiche alors le lien de la session ; quand l'interface reprend sa session (redémarrage d'Escouade, relance), il rattache la même session distante, avec le même lien ; une interface fermée archive sa session distante. Au démarrage d'Escouade, l'interface d'un tel agent est lancée en fond, sans être ouverte, pour qu'il soit joignable ; ouvrir l'agent affiche cette interface déjà lancée. Ces lancements, comme ceux d'un réglage, se font au plus 3 à la fois : un démarrage garde sa place jusqu'à ce que l'interface soit prête (voir *Interface prête*), 15 s au plus. Escouade ne peut pas allumer ni couper le remote control d'une interface déjà ouverte : un changement (réglage ou clic droit) vaut au prochain lancement de son interface. Après un changement à la main (clic droit) sur un agent dont l'interface ouverte ne peut pas suivre, un toast le dit (« Pris en compte au prochain lancement de son interface Claude Code ; d'ici là, c'est sa commande /remote-control qui le fait. ») ; pour un réglage, c'est sa description qui le dit. Une interface lancée en fond et jamais ouverte s'arrête quand son remote control s'éteint, sauf en plein tour (son travail serait perdu). Une interface qu'Escouade arrête pour de bon (retour en vue Escouade, archivage, suppression, interface jamais affichée dont le remote control s'éteint) est fermée en douceur, pour que Claude Code archive sa session : deux Ctrl+C (le second 700 ms après que le premier est écrit pour de bon), puis arrêt forcé au bout de 5 s. Un démarrage de process ou d'interface de l'agent demandé pendant ce temps attend que l'ancienne soit partie : jamais deux process sur une session (le verrou de lancement de l'agent n'est pas tenu pendant ces secondes). À la fermeture d'Escouade, elle ne l'est pas, pour que le lien revienne au prochain démarrage. Le passage en vue Claude Code n'est pas refusé quand le remote control est allumé. Le menu d'un agent en vue Claude Code propose « Activer / Désactiver le remote control » ; « Ouvrir sur claude.ai » et « Copier le lien claude.ai » s'y ajoutent une fois l'interface connectée : le lien vient de l'interface (entrée `system`/`bridge_status` de son transcript, avec `url`).
    - **Infobulle de l'icône d'ondes** (textes de `nav.sidebar.remote.*`) : « Remote control : aucune interface lancée, pas joignable pour l'instant (ouvre l'agent pour la lancer) » ; « Remote control : connexion… (accessible depuis claude.ai et l'app Claude) » ; « Remote control : connecté (accessible depuis claude.ai et l'app Claude) » ; « Remote control : au prochain lancement de son interface Claude Code » quand l'interface qui tourne a été lancée sans le remote control (`interfaceRemote` de l'agent : l'interface a-t-elle été lancée avec `--remote-control`) ; « Remote control : pas ouvert par Claude Code (compte sans abonnement claude.ai, réseau, proxy ou règle de l'organisation) » (`remoteState` `unavailable`, texte `nav.sidebar.remote.unavailable`) quand l'interface tourne sans que Claude Code ait ouvert la session distante : voir *Pas ouvert par Claude Code*. Remote control éteint pour Escouade mais encore actif dans l'interface ouverte : l'icône reste, barrée et dans la couleur d'avertissement, avec « Remote control encore actif dans l'interface ouverte, jusqu'à son prochain lancement (sa commande /remote-control le coupe) », jusqu'au prochain lancement ; seulement si l'interface ouverte a vraiment eu son lien (`remoteState` `connected`), pas pour une interface lancée avec l'option mais jamais liée.
    - **Pas ouvert par Claude Code** : Claude Code n'écrit jamais « Remote Control requires a claude.ai subscription… » ni « --rc flag ignored. » dans le terminal (il intercepte ce texte et ne le met que dans son journal de debug ; vérifié le 2026-10-16) : Escouade ne le repère pas, il le déduit. Deux causes, qui donnent l'état `unavailable` et un avis dans la conversation, dit une fois par agent et par lancement d'Escouade (le compteur de tous les « Remote control indisponible : … ») : (1) le transcript de l'interface a une entrée `system`/`bridge_status` sans `url`, alors qu'elle est lancée avec l'option et qu'aucun lien n'a été vu : « Remote control indisponible : Claude Code n'a pas pu ouvrir la session distante (« <ce que dit l'entrée, 200 caractères au plus> »). », sans la parenthèse si l'entrée ne dit rien ; (2) rien ne prouve un lien (`bridge_status` avec `url`, `bridge-session` avec un `bridgeSessionId` non vide, `bridgeSessionId` non vide dans le fichier du registre) 20 s après que Claude Code a inscrit l'interface dans son registre, l'agent tenant encore le remote control : « Remote control indisponible : l'interface de Claude Code ne l'a pas ouvert (compte sans abonnement claude.ai, réseau, proxy ou règle de l'organisation). » Le remote control reste en vigueur pour l'agent : son prochain lancement réessaie. Un lien qui arrive plus tard remet « connecté » (et le compteur de l'avis à zéro). Une interface lancée sans l'option ne dit rien d'un lien qui manque.
    - **Repli** : une interface lancée avec le remote control, qu'aucune fenêtre n'a jamais montrée, qui se ferme dans les 10 s (sans que l'utilisateur ait fermé son terminal) donne la notice « Remote control indisponible : l'interface de Claude Code s'est fermée juste après son lancement avec le remote control ; elle est relancée sans lui. » ; elle est relancée tout de suite en fond, sans l'option, et les lancements suivants de cet agent se font sans l'option, jusqu'au prochain démarrage d'Escouade ou un rallumage à la main. Une interface qu'une fenêtre a montrée n'est jamais un échec de l'option, quel que soit son délai : l'utilisateur a vu son écran et a pu la finir (« No, exit » sur la boîte de confiance, Échap, `/exit`, deux Ctrl+C). Ni repli ni notice ; « Relancer » reste à lui. Une session introuvable (voir la vue Claude Code : interface qui s'arrête dès son lancement) n'est pas non plus un échec de l'option. Le repli et les lancements en fond suivent la même garde que le lancement automatique de la fenêtre : après deux arrêts dès le lancement de suite, plus aucun lancement automatique, seulement « Relancer » ; une interface qui quitte aussitôt n'est donc jamais relancée deux fois d'elle-même.
    - **Interface prête** : une interface est prête quand elle prend ce qu'on tape, c'est-à-dire qu'elle n'est ni sur l'écran du premier lancement d'un compte ni sur la boîte de confiance du dossier (« Quick safety check », dont le choix par défaut est « No, exit » : un texte tapé y choisirait une option). Elle l'est dès qu'un de ces signes est là : une fenêtre l'a montrée ; son transcript a une entrée `system`/`bridge_status` ou `bridge-session`, écrite depuis son lancement ; ou Claude Code l'a inscrite dans son registre des sessions, `<dossier de config du compte>/sessions/<pid>.json` avec `entrypoint` `cli` (le process du flux de la même session y est `sdk-cli`), écrit en moins de 2 s une fois prête et absent sur l'écran du premier lancement et la boîte de confiance (vérifié le 2026-10-16). `SessionStart` n'est plus écouté du tout : Claude Code ne l'envoie jamais en HTTP.
    - **Message refusé** : un message de la fenêtre ou du serveur MCP est refusé tant que l'interface n'est pas prête : « L'interface de Claude Code de cet agent n'est pas encore prête (premier lancement ou dossier à approuver) : ouvre l'agent pour la voir. » Cela vaut pour toute interface, celle relancée sans l'option (repli des 10 s) comprise : elle est prête aux mêmes signes.
    - **Fenêtre rechargée** : une fenêtre rechargée, ou qui ouvre l'agent après un lancement en fond, se rattache à l'interface qui tourne (sa sortie est rejouée, sans les requêtes du terminal, et ses modes reposés) au lieu de la relancer ; « Relancer » attend l'arrêt de l'ancienne avant d'ouvrir la nouvelle.
  - **Projet fermé** (voir *Fermer un projet, retrouver son historique*) : son historique garde son réglage de remote control et, pour chaque agent, d'où lui venait le sien et sa mise à part ; un projet fermé ne lance aucun agent, même si le réglage global s'allume entre-temps. Rouvert, ses agents reçoivent les réglages comme au démarrage d'Escouade : un agent mis à part le reste, les autres reprennent leur session distante (même lien).
  - **Statistiques d'usage** : l'événement `remote_control_enabled` porte la propriété `from` : `agent` (clic droit), `project` (réglage d'un projet allumé) ou `global` (réglage global allumé) ; rien d'identifiant.
- **Lancement** (entre Agents et Terminaux) : les commandes qui lancent le projet, configurées dans l'onglet « Projets » des réglages, qu'ouvrent le ⚙ de la section et « Réglages du projet… » au clic droit sur l'onglet (nom, ligne de commande, shell parmi ceux détectés, sous-dossier optionnel ; enregistrées avec le projet). « ✦ Remplir automatiquement » (première rangée du groupe « Lancement » de ces réglages) : même lecture que pour les worktrees (`claude -p`, Sonnet, outils Read, Glob et Grep seulement, dans le dossier du projet) ; Claude lit manifestes, scripts, docker-compose et README et propose les processus qu'on lance pour développer (serveurs de dev, watchers, workers, base locale via docker compose…), chacun avec un nom court, son sous-dossier et sa commande pour le shell par défaut, jamais d'installation ni de tests. La proposition (8 commandes au plus ; une commande dont le sous-dossier sort du projet ou n'existe pas est écartée, de même qu'une commande ou un dossier qui ne tient pas sur une ligne simple : retour à la ligne, caractère de contrôle ou invisible, 24 blancs de suite ou plus, plus de 300 caractères, règle que le prompt donne à Claude ; un nom est nettoyé de ses caractères invisibles, et un nom absent ou vide est tiré de la commande) s'affiche d'abord en entier sous la rangée (région « Commandes de lancement proposées » : « Proposition de Claude : relis chaque commande en entier. Elles remplacent celles de la liste. », chaque commande en police à chasse fixe, jamais coupée, ses caractères invisibles écrits en clair et dans l'ordre où le shell la lit, avec son shell et son dossier) ; « Remplacer les commandes » la met à la place des commandes du brouillon, à relire avant « Enregistrer » (« Annuler » la jette), « Ignorer » les laisse telles quelles ; la proposition reste en attente d'un onglet à l'autre, et une nouvelle ouverture des réglages l'oublie. Pendant la lecture le bouton affiche « Claude lit le projet… » ; à la fin, le focus passe à la proposition si on l'avait laissé sur le bouton. Le toast compte les commandes écartées pour leur texte (« 2 commandes proposées, 1 écartée (caractères invisibles ou trop longue) : relis-les avant d'enregistrer. ») ; toutes écartées : « Claude a proposé des commandes illisibles : aucune n'a été gardée. » ; réponse illisible : « Claude n'a pas proposé de commandes lisibles. » ; rien à lancer : « Claude n'a trouvé aucune commande à lancer pour ce projet. ». Sans commande, la section propose « Configurer » et « ✦ Proposer des commandes », qui ouvre ces réglages sur le groupe « Lancement » et lance la lecture. Chacune tourne dans son propre terminal ConPTY (`pwsh -Command …`, `bash --login -c …`, `wsl -- bash -lc …`), sans saisie : un clic sur la commande affiche son log dans la zone principale (xterm.js en lecture seule, gardé d'un lancement à l'autre avec un séparateur « relancé à HH:MM »). Statut en direct : prêt, en cours, arrêté (stoppé depuis l'app), terminé (code 0), planté (code N, avec une notification). Lancer ▶, relancer ⟳, stopper ■ (arrête aussi les programmes lancés par la commande), « Tout lancer » / « Tout arrêter ». Fermer le projet arrête ses commandes ; elles ne survivent pas à un redémarrage.
- **Terminaux** : menu `+` → PowerShell 7 (cherché dans le PATH, Program Files et l'alias du Microsoft Store ; à défaut, Windows PowerShell 5.1), Git Bash, WSL (Ubuntu). Vrai terminal (ConPTY via portable-pty + xterm.js WebGL) : autocomplétion native du shell (Tab / PSReadLine / bash-completion), historique, Ctrl+R, couleurs ANSI, programmes plein écran (vim, less, htop), redimensionnement, copier/coller, liens cliquables (URL en clair et liens OSC 8 ouverts dans le navigateur, voir *Fenêtre*), recherche. Un terminal s'ouvre dans le dossier du projet ; « Dans le worktree de… », au bas du menu `+`, liste les agents du projet qui ont un worktree (pas les archivés, dans l'ordre de la barre latérale ; ni l'entrée ni son séparateur sans un tel agent) et ouvre le terminal dans celui qu'on choisit, comme le bouton « Terminal » de l'en-tête de sa conversation (voir *Conversation*) ; « Ouvrir un terminal » (clic droit sur un agent) l'ouvre dans le worktree de l'agent, « Ouvrir un terminal ici » (arborescence de l'éditeur) dans un dossier de la source affichée, confiné à cette source (un worktree disparu est refusé). Les terminaux ne survivent pas à un redémarrage.
  - Saisie : chaque terminal a sa file d'écriture et son propre fil qui l'écrit dans le pseudo-terminal, dans l'ordre des frappes. Un programme qui ne lit pas son entrée ne retient que ce fil : ni la fenêtre, ni les autres terminaux (leur saisie, leur redimensionnement, leur fermeture) ; au-delà de 32 Mo en attente, la saisie de ce terminal est refusée (« le terminal ne lit plus son entrée »), et le fil écrit 256 Ko au plus à la fois. Si l'écriture échoue (le programme est parti), le journal le dit (« its input can no longer be written »). Fermer un terminal (arrêter ses programmes) se fait hors du fil de la fenêtre.
  - Latence, dans le journal de l'app (`app.log` du dossier de données) : à l'ouverture d'un terminal interactif, son moteur de rendu (« renderer webgl (<nom du GPU>) », un GPU logiciel comme SwiftShader se reconnaît à son nom ; « renderer dom (<raison>) » sans WebGL), et de nouveau s'il perd son contexte WebGL (Chromium en garde 16 au plus et retire le plus ancien). Une frappe ou un collage dont l'écho met plus de 300 ms à s'afficher (et moins de 10 s : au-delà, ce n'était pas un écho) est noté, au plus une fois toutes les 10 s par terminal, avec le temps de chaque étape : « echo of a 1-byte write shown after 837 ms: written 0 ms after the backend got it, first output 835 ms after, the echo 835 ms after, to and from the window 1 ms (answer to the write 2 ms), painted 1 ms later ». « written » est l'attente dans la file du terminal ; « first output » et « the echo », quand le programme a répondu quelque chose puis quand l'écho lui-même est sorti (le bloc de sortie qui le montre, repéré par sa place dans le flux) : le temps du programme et du pseudo-terminal ; « to and from the window », celui des échanges avec la fenêtre, aller et retour (« answer to the write » : l'aller-retour de la frappe seule, jusqu'à la réponse du backend) ; « painted », celui du rendu. Seules les frappes de l'utilisateur (un caractère, dont l'écho est reconnu à son contenu) et ses collages sont mesurés, fenêtre visible : ni les réponses automatiques du terminal (focus, position du curseur, souris), ni les touches qui n'affichent rien. Mesures et chemin d'une frappe : `docs/PROTOCOL.md`, *Terminaux intégrés*.
- **Pied** : chemin, branche (et « Parcourir » : l'éditeur sur la branche du projet), `~ modifiés / + ajoutés / − supprimés`, sélecteur de couleur.

## Vue d'ensemble

- « Vue d'ensemble » (bouton à gauche des onglets de projets, infobulle « Tous les agents de tous les projets (Ctrl+Maj+A) », ou `Ctrl+Maj+A`, aussi depuis un terminal où il n'envoie rien au shell) remplace toute la zone sous la barre d'onglets, barre latérale comprise, comme « Stats » ; le bouton ou le raccourci de nouveau, ou Échap, reviennent à la vue d'avant (Échap ne fait rien derrière une boîte de dialogue ou un menu ouvert). La vue est mémorisée dans `state.json`.
- En-tête « Vue d'ensemble », « 3 projets · 8 agents · 2 en cours » et « ↑ ↓ choisir · Entrée ouvrir · Échap revenir ». Groupes : d'abord « Attend ta réponse » (les agents qui ont une question ou une autorisation en attente, de tous les projets, celui qui attend depuis le plus longtemps d'abord, chaque ligne avec son projet), puis un groupe par projet, dans l'ordre des onglets, ses agents dans l'ordre de la barre latérale ; un agent n'apparaît qu'une fois. Ni agents archivés, ni projets sans agent. Vide : « Aucun agent pour l'instant. ».
- Ligne : statut, nom, ticket (« ▸ DEM-1 · boucle 2/5 »), activité comme sur les cartes du Kanban (« Lit src/db.ts », « Prépare le worktree · … », « Reprise à … », sinon le statut), modèle, coût de la session (« ≈ » pendant un tour), contexte utilisé (en couleur d'attente au-delà de 80 %, « — » tant qu'il n'est pas connu), « Depuis » (dernier changement de statut ou dernier message).
- Une ligne en attente montre sa plus ancienne demande, résumée par le backend sans charger la conversation (textes de 2 000 caractères au plus, listes de 10). Autorisation : le badge de l'outil et son argument (lignes gardées, 4 au plus ; caractères invisibles ou de direction écrits en clair, `⟨U+202E⟩`, et texte affiché de gauche à droite), la description et la raison, puis « Autoriser » et « Refuser » sur place, seulement pour un outil dont le résumé dit tout (Bash, PowerShell, commande slash, Read, Edit, Write, MultiEdit, NotebookEdit, Grep, Glob, WebFetch, WebSearch) avec un argument non vide affiché en entier, et que Claude Code n'invite pas à refuser par défaut. Sinon « Répondre » (ouvre l'agent), avec « À lire dans la conversation avant de répondre. » (autre outil, MCP compris, argument vide, ou demande que Claude Code refuserait par défaut) ou « Trop long pour être lu ici : lis-la et réponds dans la conversation. » (coupé, plus de 4 lignes, ou qui déborde une fois dessiné). Question : son texte et « Répondre » ; plan à approuver : « Claude propose un plan » et « Répondre ». Une ligne dont la demande, le contenu ou la place change pendant que la vue est ouverte (celle du dessus vient d'être réglée, la demande suivante arrive) garde ses boutons fermés 500 ms.
- Clavier : une seule ligne dans l'ordre de tabulation, ↑ ↓ Début Fin entre les lignes, Entrée ou Espace (ou un clic) ouvre l'agent dans son projet, l'éditeur fermé ; `Ctrl+Entrée` n'y répond à rien. Après une réponse au clavier, le focus revient sur la ligne de l'agent.

## Conversation

- En-tête : nom, statut, projet / branche ; « Terminal », juste après « Éditeur » (agent à worktree, non archivé : un terminal dans son worktree, nommé comme celui du clic droit, avec le glyphe du premier shell détecté ou `$_` sans shell) ; « ▶ Tester » (agent à worktree qui a une recette de lancement) ou « Préparer le lancement » (agent à worktree sans recette, pas tant que son ticket est « En cours ») : voir *Kanban* ; modèle, tokens, coût, « Fichiers ▸ » (ouvre le panneau), durée ; sélecteur de disposition. Quand la colonne est étroite, tokens et durée (puis coût et fichiers) s'effacent : la carte de l'agent les affiche aussi. Sous l'en-tête, quand l'agent a des tâches, le bandeau « Plan » (voir *Avancée d'un agent qui exécute un plan*).
- **Disposition** (globale, mémorisée dans `state.json`, `Ctrl+Maj+L`) : classique (panneau des fichiers à ouvrir) ou **moitié / moitié** : conversation à gauche, à droite le panneau « Non commités » toujours visible avec, sous la liste, le diff du fichier sélectionné (premier fichier par défaut, rafraîchi pendant que l'agent édite).
- Messages : utilisateur (bulle à droite), assistant (markdown), lignes d'outils compactes **dépliables** (diff pour Edit/Write, unifié ou côte à côte selon le style choisi dans les vues de diff ; sortie pour Bash…), réflexion repliée dépliable. Un message venu du serveur MCP (`send_message`, premier message de `create_agent`) est montré précédé de « Message de <auteur> : » (voir *Serveur MCP*).
- Longues conversations : seuls les 80 derniers éléments sont dessinés, et la fenêtre suit les nouveaux tant que la vue est en bas. « Afficher les N précédents » (« Afficher le précédent » pour un seul), en haut, ajoute les 80 d'avant sans déplacer le message lu, autant de fois qu'il le faut ; un lecteur d'écran entend « 80 messages précédents affichés », et le focus reste sur le bouton (sur la conversation après la dernière tranche). Dès que la vue quitte le bas, ce qui est dessiné ne bouge plus ; revenir en bas (ou « ↓ Nouveaux messages ») redessine les 80 derniers. Seul un geste vers le haut quitte le bas : molette vers le haut, ↑, Page↑, Début, Maj+Espace, Maj+Tab, ou le focus qui passe sur un élément plus haut ; ni la molette vers le bas, ni les touches qui descendent, ni Ctrl, Alt ou Maj seuls.
- Mémoire de la fenêtre : la conversation d'un agent qui n'est pas affichée depuis 10 minutes (vérifié chaque minute) quitte la mémoire, sauf si l'agent travaille ou attend une réponse, ou si un message attend la préparation de son worktree ; elle est relue à sa prochaine ouverture.
- Position de lecture, par agent et en mémoire : revenir sur un agent remet la conversation sur le message qu'on lisait (même décalage, gardé une seconde pendant que les messages voisins prennent leur vraie hauteur), avec les messages plus anciens qu'on avait affichés ; laissée en bas, elle reste en bas et suit les nouveaux messages.
- Carte question (AskUserQuestion / permission) : options en boutons, réponse libre possible dans le composer ; carte répondue grisée « → réponse ». Les demandes d'un agent restent dans l'ordre d'arrivée ; la plus ancienne est celle à laquelle le clavier et le composer répondent.
- Réponses au clavier, depuis la conversation ou son champ de saisie (pas un terminal, pas l'éditeur, pas derrière une boîte de dialogue ; jamais avec AltGr ni une touche maintenue) : `Ctrl+Entrée` autorise (« Approuver le plan » pour un plan), `Ctrl+Maj+Entrée` autorise toujours quand Claude propose une règle ; `Alt+1..9` choisit l'option n de la question (coche ou décoche pour un choix multiple ; avec plusieurs questions, celle qui attend sa réponse, puis la suivante), `Ctrl+Entrée` valide quand la réponse est complète (sinon passe à la question sans réponse, ou envoie le texte du composer comme réponse libre). Les boutons de la demande en cours montrent leur raccourci (`aria-keyshortcuts`). Un texte tapé puis Entrée refuse toujours avec ce message. Pendant 500 ms après qu'une demande devient celle à laquelle le clavier répond (elle arrive, la carte s'affiche, ou elle prend la place de celle qu'on vient de régler), ces touches, et Entrée dans le champ de saisie (pas Maj+Entrée), ne font rien : le texte tapé reste dans le champ. Une demande que Claude Code refuserait par défaut (`defaultNo`) n'a ni raccourci ni réponse au clavier : seul son bouton « Autoriser » l'autorise, et « Refuser » (« Continuer à planifier » pour un plan) est le bouton principal de sa carte ; Ctrl+Entrée dans le champ y agit comme sans carte (un texte la refuse). Après une réponse donnée depuis la carte, le focus revient au champ de saisie.
- Carte « Tâche terminée » (dernier tour, agent « Terminé ») : durée, tokens, coût, nombre de fichiers modifiés, puis leur liste (chemin, +ajouts −suppressions), chaque chemin ouvrant le fichier dans l'éditeur. Les autres tours finissent par une ligne « durée · tokens · coût » (« Interrompu » à la place de la durée). Un tour en erreur : « Le tour s'est terminé en erreur », sa raison, et « Reprise automatique … » avec « Annuler la reprise » quand une reprise est prévue. Un tour arrêté par la limite d'usage propose en plus « Reprendre sur <compte> » (voir *Comptes Claude*) ; si la reprise sur un autre compte a échoué : « La reprise sur <compte> a échoué : <erreur>. » et « Revenir sur <compte> ».
- Indicateur « Claude travaille… » + bouton Stop (interrompre).
- Préparation du worktree : « Préparation du worktree · 2/3 · npm ci — tes messages partiront une fois terminée. » ; « Voir la sortie » déplie la sortie de l'étape en cours, en direct (ses 500 dernières lignes, telles qu'un terminal les laisse : codes ANSI retirés, barres de progression ramenées à leur dernier état), qui défile toute seule tant qu'on reste en bas (« Pas encore de sortie. » avant la première ligne). Les lignes arrivent par lots de 50 ms au plus.
- Composer : menus déroulants ouverts vers le haut — Modèle (Fable · Opus · Sonnet · Haiku, alias CLI), Compte (seulement avec plusieurs comptes Claude : voir *Comptes Claude*), Effort (Bas · Moyen · Élevé · Très élevé · Max), Mode (Auto · Demander · Plan · Édits auto · Bypass ; **Auto par défaut**) — puis Envoyer (↵), toujours sur une seule ligne : dans une colonne étroite, les libellés des menus s'effacent et Stop se réduit à ■. Bordure jaune si une question attend.
- Composer v1 : fichiers joints — images (PNG, JPEG, GIF, WebP ; 5 Mo), PDF (20 Mo), fichiers texte UTF-8 (1 Mo) — par le trombone, le collage ou le glisser-déposer (tout autre fichier est refusé avec un message), dictée (voir *Dictée*), autocomplétion `@fichier`, slash commands (intégrées + `.claude/commands` + skills), messages envoyés pendant que Claude travaille : transmis tout de suite, le CLI les intègre à l'étape suivante du tour (mention « transmis pendant le tour » jusqu'à la fin du tour). Un message envoyé pendant la préparation du worktree s'affiche tout de suite avec « En attente de la préparation… » et part une fois la préparation finie ; un deuxième, envoyé avant, est refusé par un toast « Un message attend déjà la fin de la préparation. » et reste dans le champ. Un message refusé à l'envoi (Claude Code introuvable…) revient dans le champ de son agent, même si un autre agent est affiché entre-temps, au-dessus de ce qui a été tapé depuis (séparé par une ligne vide), ses fichiers joints avant ceux ajoutés depuis.
- Brouillons : le texte tapé dans le composer de chaque agent est gardé dans les préférences locales (`escouade.draft.<agent>`, 300 ms après la dernière frappe, et tout de suite avant un redémarrage pour mise à jour ou un rechargement de la fenêtre) : il revient après un redémarrage, une mise à jour ou un rechargement. Vidé à l'envoi (remis si l'envoi est refusé, voir ci-dessus), supprimé avec l'agent ; les fichiers joints ne sont gardés que pendant la session.

## Rechercher dans les conversations

- `Ctrl+K` (Cmd+K sous macOS ; dans un terminal sous Windows, Ctrl+K reste au shell) ouvre « Rechercher dans les conversations », en haut de la fenêtre : un champ, « Ce projet » (par défaut ; indisponible sans projet) ou « Tous les projets », « Agents archivés » (coché par défaut). La recherche part à partir de 2 caractères, 150 ms après la frappe ; seule la réponse de la dernière compte.
- Le backend lit les journaux des conversations (`conversations/<agent>.jsonl`, en lecture seule, sur un fil à part), sans tenir compte de la casse ni des accents (lettres latines accentuées, accents écrits à part, `œ` `æ` `ß`, apostrophes typographiques, `\` comme `/`, blancs successifs) : textes de l'utilisateur (et noms des fichiers joints) et de Claude, notices, questions et leurs options, autorisations, plans, erreurs de tour, et pour les outils leur résumé (commande, fichier depuis le dossier de l'agent, motif, adresse…) et leur sortie. Ni la réflexion, ni le contenu écrit par un Edit / Write. Un résultat par message, les agents par dernière activité, les messages récents d'abord ; 200 au plus (« Les 200 premiers résultats : précise ta recherche. »), 5 s au plus (« N résultats, recherche arrêtée au bout de 5 s : précise ta recherche. ») ; une nouvelle recherche arrête la précédente.
- Résultats groupés par agent (nom, projet, « archivé »), chaque ligne avec un extrait sur une ligne (le nom de l'outil devant, la correspondance surlignée vers le début) et sa date relative ; « Aucun message ne correspond. » sinon. ↑ ↓ choisir, Entrée ouvrir, Échap fermer.
- Ouvrir un résultat ferme l'éditeur, affiche l'agent (un agent archivé s'ouvre en lecture, la liste « Archivés » dépliée) et fait défiler sa conversation jusqu'au message (celui d'un sous-agent : son appel), au milieu de la vue, surligné 2 s ; un message plus ancien que ceux dessinés est dessiné avec les 10 qui le précèdent. Ce point devient la position de lecture. Agent disparu : « Cet agent n'existe plus. ».
- Limites : le texte encore en cours de streaming n'est trouvé qu'une fois écrit dans le journal ; les accents des autres alphabets (grec, cyrillique) ne sont pas ignorés.

## Avancée d'un agent qui exécute un plan

- But : dire où en est un agent qui déroule un plan (liste de tâches, sous-agents, plan superpowers) sans lire sa conversation. Trois endroits seulement : le bandeau « Plan » de la conversation, la ligne de la carte de l'agent dans la barre latérale et, pour les sous-agents, le groupe sous cette carte avec la conversation de chacun (voir « Sous-agents ») ; la carte du ticket, la vue d'ensemble et le panneau latéral ne changent pas (la carte du ticket garde sa barre de critères et son activité).
- **Modèle.** `AgentMeta.plan: Option<PlanState>` (`plan.rs`), absent tant que l'agent n'a ni tâche, ni sous-agent, ni workflow, écrit dans `state.json` et dans `AgentView` : la fenêtre le reçoit avec l'événement `agent` existant, aucun événement nouveau (un changement qui n'est qu'un détail vivant, comme ce que fait un sous-agent, émet la vue sans demander de sauvegarde). Il contient `source` (`tools` : la liste de l'agent ; `plan` : les fichiers ; `null`), `planFile` et `title` (le plan des fichiers), `tasks` (100 au plus : id, titre, `pending` / `inProgress` / `done`, `active` (« Running tests »), `steps` (cochées, toutes), `blockedBy`), `agents` (30 au plus, toutes celles qui tournent puis les dernières terminées : id de l'appel, titre, `kind`, `model` tel que l'appel l'écrit, `running` / `done` / `failed` / `stopped` / `interrupted`, arrière-plan, outils, jetons, `doing`, `planTask`, `parent` (l'appel du sous-agent qui l'a lancé, s'il y en a un) et `taskId` (la tâche de Claude Code, que « Arrêter » et « Lui écrire » nomment)), `launched` (tous les sous-agents lancés depuis la remise à zéro, non borné) et `workflows` (10 au plus). Un titre, `active`, `doing` ou un modèle est une ligne visible (marques de direction, caractères de largeur nulle et sauts de ligne retirés) de 160 caractères au plus ; le plan ne garde pas le `prompt` d'un sous-agent (la conversation, elle, le garde sur l'élément de son appel, 16 000 octets au plus : voir « Sous-agents »). Un ancien `state.json` se charge ; une copie d'agent démarre sans plan. L'état « Bloqué » n'est pas dans le modèle : la fenêtre le déduit.
- **Première source : le flux** (`plan.rs`, un seul réducteur, que la fenêtre ne recalcule pas). Liste de tâches, du fil principal seulement (`parent_tool_use_id` nul ; ce qu'un sous-agent appelle est ignoré) : `TodoWrite` remplace la liste (id = rang) ; `TaskCreate` ajoute une tâche en attente tout de suite, dont l'id est celui du `tool_result` (« Task #<id> created successfully ») ; un résultat en erreur la retire ; `TaskUpdate` agit par `taskId` (statut, titre, `activeForm`, `addBlockedBy` ; `deleted` retire ; un id inconnu crée l'entrée) ; `TaskList` et `TaskGet` ne changent rien ; un `TaskCreate` quand toutes les tâches sont faites ouvre une nouvelle liste ; un appel reçu deux fois ne compte qu'une fois. Plusieurs tâches peuvent être en cours à la fois. Ce sont les règles que Claude Code applique lui-même (voir `docs/PROTOCOL.md`).
  - Sous-agents : un appel `Task` ou `Agent` (n'importe quel parent) ouvre une rangée `running` et compte dans `launched`. Sa tâche (`planTask`) est celle que son `prompt` ou sa `description` nomme (`task-<id>-brief.md` ou `-report.md`, puis `Task <id>`) si la liste l'a, sinon la seule tâche en cours, sinon aucune. Ce qu'il fait (`doing`) est son dernier outil, dans les mêmes mots que l'activité de l'agent (« Édite src/a.ts » ; une commande qui commence par `cd "<dossier>" &&` dit ce qu'elle lance ensuite) ; ses outils se comptent sans émettre la vue. Il se clôt au `tool_result` (premier plan), à `task_updated` ou à `task_notification` (arrière-plan), dans n'importe quel ordre ; une rangée close ne rouvre pas. Son `parent` est la rangée de l'appel qui porte son `parent_tool_use_id`, sinon celle dont la tâche est le `parent_task_id` de son `task_started` ; son `taskId` est le `task_id` de son `task_started`, sinon l'`agentId` du résultat de lancement. En vue Claude Code, aucune frame `system` n'arrive : un sous-agent en arrière-plan s'y clôt par la `task-notification` que Claude Code rejoue dans le transcript de l'agent (`origin.kind` `task-notification`, lue par `on_replay`) ou par son hand-back rejoué (`origin.kind` `peer`, `<agent-message from="<tâche>">[Subagent hand-back] … The report follows: …`), qui donne aussi son rapport ; dans la session interactive observée (Claude Code 2.1.283), aucune `task-notification` de sous-agent n'était rejouée, seulement celles de commandes. Les tâches de fond d'autres types (`Bash`…) ne comptent pas.
  - Workflows : `task_started` d'un `local_workflow` ouvre une exécution (nom, phase courante, outils, jetons) que `task_progress` met à jour et que `task_notification` clôt. Ils sont gardés, **jamais montrés** (voir *Limites*).
  - Remise à zéro : une nouvelle session Claude, ou le premier message d'un tour (pas un message mis en file) quand le plan est fini (toutes les tâches faites, ou aucune, et rien qui tourne). Quand le process meurt ou que l'application redémarre, les rangées et workflows qui tournaient passent à `interrupted` ; à la fin d'un tour, une rangée au premier plan encore ouverte l'est aussi (un arrêt de l'utilisateur) ; les tâches gardent leur statut, l'agent reprendra.
- **Seconde source : le plan et le registre superpowers** (`planfiles.rs`, formes de superpowers 6.4.1). Lus **en lecture seule, dans le dépôt de l'agent seulement** (racine = `git rev-parse --show-toplevel` de son dossier, sinon son dossier), jamais ailleurs, jamais `~/.claude` :
  - le registre `.superpowers/sdd/<plan>/progress.md`, le plus récent dont la ligne 1 est `# SDD ledger — plan: <chemin>` et dont le plan existe (à défaut de chemin utilisable, le fichier `plan-path` du dossier) ; les noms des `task-<id>-brief.md` du dossier (jamais leur contenu) ; le plan, un `.md` du dépôt ; sans registre, un plan de `docs/superpowers/plans/` que l'agent a écrit dans cette conversation (outils `Write`, `Edit`, `MultiEdit`, ou commande qui écrit : redirection, `tee`, destination d'un `cp` ou d'un `mv`, jamais un plan qu'elle lit ou cherche ; 5 au plus). Seuls les fichiers ordinaires sont ouverts : jamais un lien, un dossier ou un tube.
  - Confinement : un chemin écrit dans ces fichiers n'est jamais interrogé au disque tant qu'il n'est pas, d'après son écriture seule, sous la racine (un chemin absolu ailleurs, un chemin réseau ou de périphérique sous toutes ses écritures, un nom avec `:` ou de périphérique Windows : refusés), puis passe par `paths::contained`. Fichiers lus au plus 256 Kio (un registre plus gros donne ses deux bouts), hors du verrou de l'agent.
  - Plan : titre = le premier `# ` hors bloc de code, sans « Implementation Plan » ; tâche = `## Task <id>: <titre>` (à `####`) hors bloc de code, 100 au plus ; `steps` = les cases `- [ ]` / `- [x]` de sa section. Registre : lignes `Task <id>: <texte>` (une ligne peut en porter plusieurs) ; `complete` = faite ; `dispatched`, `implementer`, `review`, `fix round` = au travail ; le reste (`Ruling`, `minor`, `parked`, lignes libres) sans effet ; la dernière ligne qui dit quelque chose l'emporte. Une tâche qui a son brief et aucune ligne `complete` est en cours (la première, si tous les briefs sont faits d'avance et qu'aucune ligne ne dit laquelle). Une tâche donnée faite ne repasse jamais à « à faire » (sauf `fix round` : « en cours »). Un plan sans tâche n'est aucun plan.
  - Un plan ou un registre qu'aucune activité n'a touché depuis le début de la conversation de l'agent (le plus récent du registre et des briefs) n'est pas le sien : un nouvel agent d'un dépôt qui garde un vieux `.superpowers/sdd` ne montre pas son plan.
  - Quand : au `tool_result` d'un `Bash`, d'un sous-agent, de l'écriture d'un plan ou d'un fichier de `.superpowers/sdd/` par le fil principal, et à la fin de chaque tour ; au plus un regard toutes les 2 s par agent (une rafale en donne un de plus à la fin) ; les fichiers ne sont relus que si la date ou la taille du registre ou du plan, ou la liste des briefs, a changé. Une erreur de lecture est avalée (ni toast, ni notice), le dernier état reste.
  - Fin du plan : une commande du fil principal qui supprime le dossier de travail du plan suivi (`rm -rf .superpowers/sdd/<plan>`, `Remove-Item`…, directement ou par une variable qu'elle définit comme exactement ce dossier ; pas un fichier de ce dossier) met toutes les tâches d'un plan de fichiers à faites à son `tool_result` réussi : les skills la terminent ainsi, parfois dans la même commande que la dernière ligne du registre, que plus aucun regard ne verrait.
- **Précédence.** La liste que l'agent tient (non vide) l'emporte ; les fichiers ne lui donnent que le titre et le nom du plan, et seulement si l'une de ses tâches est une tâche du plan (même titre, ou « Task 2: Titre », ou un titre qui contient l'autre entier) : deux agents du même dépôt lisent le même dossier. Sans liste, c'est celle des fichiers (`source: "plan"`). La fenêtre ne reçoit qu'une liste et décide qu'elle existe d'après `tasks.length`, jamais d'après `source` ni `planFile` (un `TodoWrite` vide laisse `source: "tools"` et `tasks: []`). Quand l'agent se met à tenir sa liste, celle des fichiers lui laisse la place ; le titre du plan revient dès que sa liste est celle du plan. **Pas d'outil MCP pour l'avancée** : un `report_plan` ne servirait qu'aux agents d'Escouade et ferait doublon avec les outils de tâches ; `report_progress` reste la seule ligne dite par l'agent (voir *Serveur MCP*).
- **Bandeau « Plan »** (`PlanBanner.svelte`, calculé par `planView`, `lib/plan.ts`) : entre l'en-tête de la conversation et les messages, seulement si l'agent a des tâches (ou, sans tâche, des sous-agents en cours : voir plus bas). Titre : celui du plan, sinon celui du ticket de l'agent, sinon son nom (l'infobulle donne le fichier du plan quand la liste vient de lui).
  - Ligne d'en-tête : un bouton (`aria-expanded`) qui plie et déplie la liste : pastille « Plan », titre, « 2/7 tâches », pourcentage, chevron ; à côté de lui, hors du bouton (un bouton n'en contient pas un autre), la pile de pastilles des sous-agents en cours (6 au plus ; les autres ne sont que comptés) et « 3 sous-agents actifs ». La pile est un seul bouton, dont la zone de clic fait 24 px au moins (WCAG 2.5.8) et dont les pastilles ne sont que du dessin (`aria-hidden`) ; le compteur est à côté, hors du bouton. Un seul sous-agent en cours : le bouton (« Ouvrir la conversation du sous-agent <titre> », son titre en infobulle) ouvre sa conversation, liée à une tâche ou non (voir « Sous-agents »). Plusieurs : le bouton (« Ouvrir la conversation d'un sous-agent », `aria-haspopup="menu"`, la même phrase en infobulle) ouvre un menu de tous ceux qui tournent, dans l'ordre du plan, y compris au-delà des 6 pastilles (le titre, et le modèle en indication quand l'appel en a nommé un), dont l'entrée choisie ouvre la conversation de ce sous-agent. Ouvert par défaut quand la fenêtre fait au moins 800 px de haut (suivi tant que l'utilisateur n'a pas choisi), puis au choix de chaque agent, en mémoire de la session (`app.planOpen`). Dessous, une barre segmentée (`role="progressbar"`) : un segment par tâche, plein et vert si faite, à la couleur d'accent sur son avancement si en cours, d'attente si bloquée, fond atténué si à faire.
  - Liste : une ligne par tâche (rang « 01 », icône d'état précédée de son mot en texte pour les lecteurs d'écran, titre, barre, avancement). Avancement : faite 100, à faire 0, en cours = cases cochées sur cases du plan si elle en a et qu'au moins une est cochée, sinon *non mesuré* : « En cours » (« Bloqué » pour une tâche bloquée), barre pleine à 35 % d'opacité, jamais un pourcentage inventé. Global = moyenne arrondie, une tâche non mesurée comptant 0. Sous le titre : « ↳ nom » et le modèle du sous-agent en cours lié à la tâche (« ↳ nom » est un bouton qui ouvre sa conversation) ; le pas courant (le `doing` de ce sous-agent, sinon le `active` de la tâche) ; « En attente de ta réponse » pour une tâche bloquée ; « après 03, 05 » (rangs) pour une tâche à faire dont un bloqueur n'est pas fini. **Bloquée** : seulement la première tâche en cours d'un agent qui attend (`status == waiting`, question ou autorisation). Les titres, `doing`, `active` et noms de sous-agents sont les mots de l'agent : du texte, jamais traduit ni interprété.
  - Tâche mise en avant : la première bloquée, sinon la première en cours, sinon la première à faire ; fond d'accent et filet à gauche ; la liste la centre quand elle change (ou que le nombre de lignes change, ou à l'ouverture), sauf dans les 6 s qui suivent un défilement de l'utilisateur, et toujours au changement d'agent.
  - Poignée sous la liste (`Splitter` d'axe vertical, `role="separator"`) : glisser ou ↑ ↓ (16 px) / Début / Fin règle la hauteur de la liste (60 px au moins ; les messages gardent 160 px au moins) ; double-clic, Entrée ou Échap la remettent à « auto » ; retenue (`escouade.planHeight`).
  - Sans tâche mais avec des sous-agents en cours : cadre réduit, pastille « Sous-agents », pile de pastilles (un bouton, comme ci-dessus) et compteur, ni bouton de pli, ni barre, ni liste ; il disparaît quand ils ont fini. Un `interrupted` n'est pas actif.
  - Accessibilité : tout au clavier avec un focus visible ; une seule région `role="status"` polie, la synthèse « d/n tâches », mise à jour au plus toutes les 2 s ; `prefers-reduced-motion` (rond fixe, pas de transition de largeur, défilement instantané) ; couleurs de texte lisibles sur le fond (le gris le plus faible n'est employé que pour des éléments décoratifs). Français et anglais, changement de langue à chaud. Étroit (disposition moitié / moitié, requête de conteneur à 560 px) : la barre des lignes et, sans liste, le compteur de sous-agents s'effacent.
- **Carte de l'agent** (barre latérale) : entre la ligne « tokens · coût · fichiers » et l'étiquette du ticket, une mini-barre (largeur = pourcentage global) et « Plan 2/7 » ou « Plan 2/7 · 3 sous-agents » (pluriel exact). Cette ligne n'existe qu'avec des tâches : pour des sous-agents seuls, c'est le groupe « Sous-agents de <agent> » sous la carte qui les montre (voir « Sous-agents »).
- **Lignes d'outil** : `TaskCreate` « Tâche : <sujet> », `TaskUpdate` « Tâche #3 : terminée » (à faire, en cours, terminée, supprimée, modifiée) ; leur résultat n'est pas répété (une erreur est dite) ; `TaskList` et `TaskGet` en retrait. `TodoWrite` (« N tâches ») ne change pas ; la ligne d'un appel de sous-agent (`Agent`, `Task`) garde son contenu et gagne un bouton ↗ qui ouvre sa conversation (voir « Sous-agents »).
- **Sous-agents** (ESC-13 ; `lib/subagents.ts`, `Sidebar.svelte`, `SubagentView.svelte`, `agent/sidechain.rs`). Ce que la fenêtre en sait vient des rangées du plan (30 au plus, remises à zéro avec le plan) et de la conversation, qui garde le reste (voir « Après coup »).
  - **Barre latérale.** Sous la carte de chaque agent dont le plan a des sous-agents (la carte est un bouton : le groupe est dessous, pas dedans), un groupe nommé « Sous-agents de <agent> » (`role="group"`) dont l'en-tête est un bouton (`aria-expanded`) : chevron, « Sous-agents », « 2 en cours », « 5 finis ». Déplié tant qu'un sous-agent tourne, replié sinon ; le choix de l'utilisateur est gardé par agent, en mémoire de la session (`app.subsOpen`). Déplié, d'abord ceux qui tournent, dans l'ordre du plan : une rangée-bouton par sous-agent (point d'état, titre, modèle, ce qu'il fait, `doing`), 5 au plus, puis « N autres en cours » qui déroule le reste (« Réduire » le replie) ; ensuite « N sous-agents finis », qui se déplie à son tour : les finis du dernier fini au premier, chacun avec son état (Terminé, Échoué, Arrêté, Interrompu), 10 au plus, puis « N de plus » (« Réduire »). Un sous-agent lancé par un autre est décalé d'un cran par ancêtre (`parent`, 4 crans au plus). Aucune liste ne défile : la barre défile déjà, et une liste qui défile dans une liste qui défile se perd. La rangée du sous-agent affiché porte `aria-current`. Le nombre de finis est celui des rangées gardées (30 au plus).
  - **Ouvrir sa conversation.** Un clic sur une rangée de la barre, sur la pile de points du bandeau « Plan » (d'un coup pour un seul sous-agent en cours, par un menu de tous ceux qui tournent pour plusieurs, liés à une tâche ou non ; les points se dessinent sur 16 px, empilés, dans un seul bouton dont la zone de clic fait 24 px au moins, WCAG 2.5.8 : des zones de 24 px par point se chevaucheraient), sur « ↳ nom » d'une tâche, sur le bouton ↗ de la ligne de son appel dans la conversation (« Ouvrir la conversation du sous-agent … ») ou sur « Ouvrir sa conversation » au-dessus d'une demande qu'il a faite (`sub`) : `app.openSubagent` sélectionne l'agent et fait afficher `SubagentView.svelte` à la place de sa conversation (`app.subView`, par agent, en mémoire de la session). Choisir l'agent dans la barre (sa carte) ramène à sa conversation. Un sous-agent d'un sous-agent s'ouvre aussi depuis le ↗ de son appel, dans la vue de son parent.
  - **La vue.** En-tête : fil d'Ariane « agent › sous-agent (› sous-agent de sous-agent) » (`nav`, 10 maillons au plus ; les maillons avant le dernier sont des boutons ; la chaîne s'arrête à un parent que ni le plan ni la conversation ne connaissent), état (En cours, Terminé, Échoué, Arrêté, Interrompu, ou Lancé quand rien ne le dit) et « Arrêter ». Le focus va sur le dernier maillon à l'ouverture ; Échap (pas derrière une boîte de dialogue ni un menu, pas dans un champ qui contient du texte) ou un clic sur le nom de l'agent ramènent à sa conversation, et le focus retourne là où il était quand la vue a été ouverte (sinon sur le ↗ de l'appel) ; ouverte depuis la pile de points du bandeau « Plan », par son menu ou non, il retourne sur le bouton de la pile, quels que soient les sous-agents qu'elle compte alors. Corps : type, modèle, tokens, outils, durée (qui court tant qu'il tourne) ; sa consigne (le `prompt` de l'appel), pliée au-delà de 360 caractères ou de 6 lignes (« Voir toute la consigne ») ; son fil (textes, réflexion, appels d'outils dépliables) et ses demandes de permission et ses questions, auxquelles on répond là comme dans la conversation de l'agent (elles y restent aussi) ; « Le sous-agent travaille… » tant qu'il tourne ; à la fin son rapport (Markdown), ou « Ce sous-agent n'a pas rendu de rapport. » (rien quand son état est inconnu). Un sous-agent que ni le plan ni la conversation ne connaissent : « Ce sous-agent n'est plus dans la conversation de l'agent. ». Titres, consignes, rapports et ce qu'ils font sont les mots de l'agent : jamais traduits.
  - **Arrêter.** `stop_subagent(id, appel)` envoie la requête de contrôle `stop_task` de Claude Code sur la tâche du sous-agent (15 s pour répondre) ; la fin arrive par les frames qui suivent, comme toute fin (état « Arrêté »). Elle est refusée si le sous-agent ne tourne pas, s'il travaille au premier plan (« Ce sous-agent travaille au premier plan : l'agent l'attend, et « Arrêter » de l'agent l'arrête avec son tour. »), si sa tâche n'est pas connue, en vue Claude Code et si l'agent n'a pas de process. « Arrêter » est réservé aux sous-agents en arrière-plan : arrêter seul un sous-agent au premier plan n'a jamais été essayé sur un vrai flux, son agent l'attend, et « Arrêter » de l'agent l'arrête avec son tour. Le bouton n'est donc là que pour un sous-agent en arrière-plan qui tourne (jamais en vue Claude Code, ni pour un sous-agent au premier plan) ; sans tâche connue, il reste visible, grisé (`aria-disabled`), avec une infobulle qui dit pourquoi. Arrêter un sous-agent coûte un tour de l'agent (Claude Code le lui fait faire pour constater la fin).
  - **Lui écrire.** Claude Code 2.1.300 refuse `send_task_message` : le message va à l'agent, que `message_subagent(id, appel, texte)` charge de le transmettre au sous-agent avec son outil `SendMessage` (« Transmets ce message au sous-agent « <titre> » (agentId <tâche>) avec l'outil SendMessage, tel quel, puis reprends ce que tu faisais : », une ligne vide, le texte ; dans la langue des textes pour Claude). Essayé sur un vrai flux (Claude Code 2.1.300, Haiku, 2026-10-15, `tests/fixtures/real-run-send-message.jsonl`, 0,01 $ environ) : l'agent charge l'outil par `ToolSearch`, l'appelle avec `{ to: <tâche>, message }`, Claude Code répond « Message queued for delivery to … at its next tool round… » et le rapport final du sous-agent cite le message mot pour mot. Le champ « Lui écrire, par <agent> », qui dit que le message passe par l'agent, n'est proposé que pour un sous-agent en arrière-plan qui tourne et dont la tâche est connue, jamais en vue Claude Code ni pour un agent archivé. Le backend refuse un texte vide, un agent archivé, la vue Claude Code, un sous-agent au premier plan (le message ne lui arriverait qu'à sa fin) et un sous-agent dont la tâche est inconnue ; il ne regarde pas s'il tourne encore. `Ctrl+Entrée` envoie le message sans répondre à une demande qui attend (`data-own-keys`). Le message coûte un tour de l'agent, paraît dans sa conversation et ne sert jamais à le nommer. Le brouillon est gardé par sous-agent, en mémoire de la session, quand le sous-agent finit ou qu'on change de vue ; une fois fini, le champ reste tant qu'il y a un brouillon, et dit qu'il ne peut plus être envoyé.
  - **Après coup.** Sur l'élément de l'appel, la conversation garde la consigne (`input.prompt`, 16 000 octets au plus ; les autres textes d'une entrée d'outil sont coupés à 4 000), le rapport (`report`, 16 000 octets : le `handback_report` de la `task_notification` ou, quand le sous-agent finit sans `SubagentHandback` (aucun champ `handback`, état `completed`), le `summary` de sa notification, qui est alors son rapport : mesuré sur 2.1.300 ; la ligne générique des versions plus anciennes, `Agent "<titre>" finished` (ou `completed`, `failed`, `stopped`, point final permis), n'est pas un rapport et n'est pas gardée) et son bilan (`run` : état, tokens, outils, début, fin). Les coupures se font en octets (`truncate`, « … » à la fin). Le rapport d'un sous-agent au premier plan, lui, est le texte du résultat de son appel (`result.text`, 8 000 octets au plus, même coupe : `MAX_TEXT`), que la fenêtre lit quand l'appel n'a pas de `report`. La conversation d'un sous-agent fini se lit donc encore après un redémarrage ou une remise à zéro du plan, quand la barre ne le liste plus ; un appel resté « en cours » dans le journal, sans `run` ni rangée, est dit interrompu.
  - **Vue Claude Code (lecture seule).** La conversation d'un sous-agent se lit depuis son propre transcript, `<dossier du transcript de l'agent>/<session>/subagents/agent-<tâche>.jsonl`, trouvé par la tâche de sa rangée, sinon par le `toolUseId` du `agent-<tâche>.meta.json` voisin (`subagent_transcript`) ; il est lu à l'ouverture de la vue, puis toutes les 2 s tant que le sous-agent tourne, et une dernière fois à sa fin. La vue le dit (« Lecture seule : son transcript, tel que Claude Code l'écrit. On agit sur ce sous-agent dans l'interface de Claude Code. ») ; ni « Arrêter » ni « Lui écrire » (le backend les refuse). Son rapport est celui de l'appel, sinon le `message` de son dernier `SubagentHandback`. Sa fin et son rapport viennent du transcript de l'agent (voir « Sous-agents » du réducteur, plus haut). Disposition vérifiée sur une vraie session interactive (Claude Code 2.1.283, `entrypoint: cli`) en plus des sessions du flux.
- **Réglage** : Réglages › Claude Code › groupe « Processus » › « Les agents tiennent une liste de tâches » (`Settings.todoTools`, activé par défaut ; un `settings.json` sans le champ le lit activé). Activé, le lancement d'un agent ajoute `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` (`Settings::agent_env`) : sans elle, les modèles actuels n'ont aucun outil de liste de tâches ; avec elle, `TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate`. Désactivé, rien n'est ajouté et la valeur contraire n'est jamais forcée (l'environnement de l'utilisateur reste maître). Les autres `claude` (nom de l'agent, message de commit, « ✦ Remplir automatiquement », connexion d'un compte) ne la reçoivent pas. S'applique aux agents lancés ensuite. Contrepartie : les outils prennent un peu de place dans le prompt de chaque agent ; la variable est lue dans le binaire de Claude Code, pas dans sa documentation, et peut changer (si elle disparaît, le bandeau continue avec les sous-agents et les fichiers).
- **Limites.**
  - Le réglage rend la liste possible, pas certaine : les outils de tâches sont différés dans Claude Code (le modèle doit les charger par `ToolSearch`), et sur les trois plans superpowers essayés avec le réglage actif (Claude Code 2.1.296, Sonnet 5.5, effort bas, `subagent-driven-development`) il ne l'a jamais fait : la liste venait des fichiers. Un agent sans liste ni plan de fichiers n'a pas de bandeau.
  - Fichiers : le registre est lu à la lettre (`Task <id>: …` en début de ligne, sans puce) ; une tâche annoncée par un seul en-tête (« Tasks L3 à L9 ») n'existe pas ; un plan sans registre montre ses tâches « à faire » ; un contrôleur qui n'écrit pas la dernière ligne du registre ni ne supprime le dossier laisse le plan à « 1/2 » ; plusieurs agents sans worktree dans un même dépôt lisent le même dossier de travail (l'un peut montrer le plan de l'autre, `since` limite les faux positifs aux dossiers touchés depuis le début de sa conversation) ; une édition de plan qui garde sa taille dans la même milliseconde passe inaperçue jusqu'au changement suivant ; un chemin écrit par l'agent sous un nom court ou par un lien n'est rapproché que si son dossier est le dépôt.
  - Le sous-agent d'une tâche n'est lié que si sa consigne la nomme ou si une seule tâche est en cours ; sinon il compte dans le bandeau, avec son point, sans « ↳ nom » sur une tâche. Le nombre d'outils d'un sous-agent ne s'actualise dans la fenêtre qu'avec un autre changement (exact à sa clôture).
  - **Conversation des sous-agents** : la barre latérale ne liste que les rangées gardées (30 au plus), et son nombre de finis est celui de ces rangées (`launched` dirait tous ceux lancés depuis la remise à zéro) ; au-delà de 6 sous-agents qui tournent, le bandeau « Plan » n'en dessine que 6 (il les compte tous, la barre les liste tous) ; les sous-agents ne sont pas dans la vue d'ensemble ; une réponse donnée à une demande dans la vue d'un sous-agent ne rend pas le focus à un champ de saisie (la carte part avec lui, et la vue n'en a pas). « Lui écrire » est une demande faite à l'agent : rien n'oblige son modèle à appeler `SendMessage` (il l'a fait dans l'essai, un seul). « Arrêter » n'a été essayé que sur un sous-agent en arrière-plan, et n'est proposé que pour ceux-là. En vue Claude Code, la fin d'un sous-agent repose sur sa `task-notification` ou son hand-back rejoués dans le transcript de l'agent (aucune `task-notification` de sous-agent n'a été vue dans la session interactive observée, 2.1.283).
  - **Workflows de Claude Code** : gardés dans l'état, jamais montrés ; un plan qui n'est fait que d'un workflow n'a pas de bandeau (pas de vue propre aux workflows en 1.7).
  - Vérifié sur de vrais flux (4 lancements de l'application, Claude Code 2.1.296, superpowers 6.4.1) : outils de tâches, sous-agents en arrière-plan (tous ceux qui ont été lancés l'étaient), registre. Puis, le 2026-10-15 (Claude Code 2.1.300), « Arrêter » (`stop_task`), les demandes d'un sous-agent (`agent_id`) et « Lui écrire » (`SendMessage`) : voir `docs/PROTOCOL.md`, « Un sous-agent, sa conversation et son arrêt ». **Jamais vus sur un flux réel** : les sous-agents au premier plan et les workflows, qui reposent sur le binaire et le faux `claude` des tests (`tests/fixtures/fake-claude.mjs`, scénarios « plan superpowers », « sans liste » et « interrompu »).

## Git & fichiers

- Panneau « Non commités » : portée « Cet agent » / « Tout le projet », attribution par worktree (ou par outils Edit/Write de l'agent hors mode worktree). Clic → diff ; bouton `</>` ou clic droit → éditeur. La liste dessine les 500 premiers fichiers, puis « … et N autres fichiers » ; le compte de l'onglet, « Voir le diff » et les commits les prennent tous.
- Onglet « Historique » du même panneau : git graph des 300 derniers commits de tout le dépôt (branches locales et distantes, tags, branches `ccm/…` des agents étiquetées de leur nom). La branche de l'agent (son worktree, sinon la branche courante) est mise en avant, le reste atténué. Clic sur un commit → son diff (contre le premier parent pour un merge) dans la vue diff. Rafraîchi à chaque commit, merge ou branche.
- « Voir le diff » : vue diff plein écran (unifiée / côte à côte ; choix partagé avec le volet de la disposition moitié / moitié et les diffs de la conversation, et mémorisé). En portée « Tout le projet », exactement les fichiers de la liste : ceux du dossier du projet et ceux du worktree de chaque agent, chacun étiqueté avec le nom de son agent (un même chemin peut y figurer pour deux dossiers) ; « Aucune différence. » seulement quand la liste est vide. Un worktree que git n'a pas pu lire fait échouer la vue avec sa raison (« Diff du worktree de « refacto-auth » non lu : … »), au lieu de laisser ses fichiers de côté sans rien dire ; un agent ou un dossier de worktree disparu entre-temps (validation, archivage) est laissé de côté. Les chemins passés à git sont découpés en lignes de commande de 16 000 caractères au plus.
- Gros diffs : le diff d'un fichier (suivi, non suivi, ou dans un commit) qui dépasse 4 Mo n'est pas transmis à la fenêtre ; le fichier reste listé, avec son état, et affiche « Diff trop volumineux pour être affiché. » (sans compteurs +N −M). Au-delà de 4 Mo de diff en tout, les fichiers non suivis suivants ne sont plus lus mais listés de la même façon, les 500 premiers, puis une entrée « … et N autres fichiers ». Un fichier non suivi est binaire s'il contient un octet nul, quelle que soit sa taille. Un nom de fichier qui contient un guillemet, une barre oblique inverse ou un caractère de contrôle est écrit dans l'en-tête comme git l'écrit (entre guillemets, échappé) : il ne peut pas y écrire de lignes à lui. Un diff de plus de 1 500 lignes est replié (« Diff volumineux (N lignes) » et « Afficher »), puis se déplie par tranches de 500 (« Afficher 500 lignes de plus », la dernière tranche dit le vrai reste), le focus restant sur le bouton puis sur le diff ; déplié, il le reste pendant que l'agent édite le fichier.
- « Commit… » / « Commit tout… », selon le réglage « Commit » du projet (groupe « Git » de l'onglet « Projets ») : « Rédigé par l'agent » (défaut) envoie à l'agent une demande de commit de ses changements (il rédige le message) ; « Direct, avec un message proposé » ouvre la modale « Commit », même sans agent : portée (« Modifications de <agent> » : son worktree, sinon ses fichiers dans le dossier du projet ; « Modifications de <projet> » : tout le dossier du projet, sans les worktrees), liste des fichiers (500 au plus, puis « … et N autres fichiers » ; les fichiers copiés laissés de côté sont nommés : « Jamais commité : .env (copié dans les worktrees). »), champ « Message » pré-rempli par Haiku (`claude -p`, 90 s au plus, diff des 200 premiers fichiers plafonné à 60 Ko, style des 10 derniers sujets de commit du dépôt ; « Haiku rédige le message… » pendant que le champ reste éditable, « Régénérer », « Pas de proposition : <raison>. » en cas d'échec), puis « Commiter », désactivé tant que le message est vide : jamais de commit sans ce clic. Échap, un clic à côté, × ou « Annuler » ferment la modale tout de suite quand le message est vide ou est la proposition telle qu'elle a été mise dans le champ ; sinon ils demandent « Abandonner le message ? » (« Le message que tu as écrit pour ce commit sera perdu. », « Abandonner »), dont « Annuler » ramène la modale avec le message (sans nouvelle proposition). Pendant le commit, le bouton dit « Commit… » et la modale ne se ferme pas ; un refus de git (un hook) s'y affiche et laisse l'index tel qu'il était. Seuls les chemins listés sont commités. Les fichiers copiés dans les worktrees ne le sont jamais : motif du réglage et ignorés par git (même forcés dans l'index), ou, dans un worktree, pris par la copie (même si l'agent ne les ignore plus). Haiku ne lit le contenu d'aucun fichier qui correspond aux motifs du réglage. Une mise à jour automatique attend la fin d'une proposition ou d'un commit. Seuls les chemins que la portée liste encore au moment du clic sont commités (« Plus rien à commiter : ces fichiers n'ont plus de modification. » sinon ; message vide : « Écris le message du commit. ») ; les hooks de git tournent ; ce que l'utilisateur avait indexé à part reste indexé et hors du commit (`git commit --only`, chemins passés par l'entrée standard, git 2.26 au moins). Réussi : toast « Commit <hash> créé ». « Commit tout… » ne commite pas les worktrees (« Aucune modification dans le dossier du projet : le worktree d'un agent se commite depuis « Cet agent ». » quand seuls eux ont des changements). Limites : un commit direct n'est pas refusé pendant que l'agent travaille ; dans le dossier du projet, un `.env` qu'un agent sans worktree a sorti du `.gitignore` est listé (et peut être commité si on le laisse), mais Haiku ne le lit pas.
- Mode worktree : `<projet>/.claude/worktrees/<agent>`, branche dédiée `escouade/<agent>`, avec les fichiers du projet ignorés par git qui correspondent aux « Fichiers copiés dans les worktrees » (`.env*` par défaut). Bouton « Merger <branche> → <base>… » (confirmation « Merger <branche> dans <base> ? », option « Squash (un seul commit) ») : les commits sont comptés depuis la branche de base de l'agent et mergés dans celle-ci. Si le dossier du projet est sur une autre branche (ou en HEAD détachée), une seconde confirmation propose « Basculer sur « <base> » ? » (« Le projet est sur la branche « <courante> ». Escouade bascule sur « <base> » puis merge « <branche> ». »), bouton « Basculer et merger » (`git switch --no-guess` : jamais une branche créée depuis un dépôt distant) ; un refus de git (fichiers qui gêneraient, base prise par un autre worktree) s'affiche tel quel et rien n'est mergé ; une base disparue est refusée (« La branche de base « X » n'existe plus : « Y » ne peut pas être mergée dedans. »). Suppression de l'agent → nettoyage worktree + branche.
- Dossier des worktrees et préfixes des branches (groupe « Git » de l'onglet « Projets ») : « Dossier des worktrees » (vide par défaut : `.claude/worktrees`, comme `claude --worktree`) prend un chemin relatif au dossier du projet (`../app-worktrees` : un dossier voisin du dépôt ; `.worktrees`), au dossier personnel (`~/worktrees/app`) ou complet, `.` et `..` résolus tels qu'écrits, des guillemets autour retirés (« Copier en tant que chemin ») ; sous le champ, « Le prochain : <chemin>\<nom> ». Refusés à la frappe, comme à l'enregistrement : le dossier du projet lui-même (« C’est le dossier du projet lui-même. »), un dossier qui le contient (`..`, `../..` : « Ce dossier contient celui du projet : choisis-en un à côté (../app-worktrees) ou dedans (.worktrees). »), un dossier dans un `.git` (« Ce dossier est dans un dossier .git. ») et, sous Windows, un chemin ni relatif ni complet (`D:wt`, `\wt` : « Écris un chemin relatif au dossier du projet, ou un chemin complet (C:\…). »). Un dossier qui contient des fichiers suivis par git (`src`) est refusé à la création du worktree (« Le dossier des worktrees src contient des fichiers suivis par git : choisis-en un autre dans les réglages du projet. ») : exclu, les nouveaux fichiers du projet y seraient laissés hors des commits. Y vont les worktrees des nouveaux agents, ceux des tickets, d'une copie d'agent et d'un agent sur une branche existante, et le worktree temporaire d'une validation (`.merge-<projet>-<clé>`, sinon à la racine du dépôt ; un reste d'une validation coupée, `.merge-…`, est reconnu où qu'il soit). Un nom de dossier déjà pris (par un autre dépôt dans un dossier partagé, ou tenu par un agent de l'app dont le worktree a disparu pour l'instant) passe au suivant (`-2`…) : la branche d'un agent avec lui, mais la branche d'un ticket garde son nom (celui de sa PR) tant qu'elle-même est libre. Ceux déjà créés restent où ils sont, et un agent restauré retrouve le sien à son ancien chemin ; si un autre worktree a pris ce dossier entre-temps, le sien est recréé à côté (`-2`…), et sa conversation le dit (« Le dossier <ancien> est pris par un autre worktree : celui de l'agent est recréé dans <nouveau>. »). Un dossier dans le dépôt est ajouté à `.git/info/exclude` depuis la racine du dépôt (`/.worktrees/`, `packages/web/.claude/worktrees/` pour un projet dans un sous-dossier) ; un dossier hors du dépôt n'y touche pas. Un dossier hors de celui du projet est surveillé lui aussi : les compteurs git des agents s'y rafraîchissent comme pour `.claude/worktrees`. Hors du dossier du projet, la vue Claude Code demande d'abord la confiance du dossier de chaque worktree (voir `PROTOCOL.md`). « Préfixe des branches des agents » (`escouade/` par défaut) et « Préfixe des branches des tickets » (`ticket/` par défaut), avec un exemple sous chacun (« Branche d’un nouvel agent : escouade/<nom>. Vide : son nom seul. ») : vide, la branche est le nom de l'agent ou la clé du ticket seuls ; un préfixe dont aucun nom de branche ne peut partir (espace, `..`, `~`, `^`, `:`, `?`, `*`, `[`, `\`, `@{`, `-` ou `/` au début, `//`, une partie qui commence par `.` ou finit par `.lock`) est refusé à la frappe et à l'enregistrement. Un agent renommé d'après son premier message garde le préfixe de son projet, une copie aussi ; le texte des actions du Kanban (« push ticket/* », « Pousse ticket/<clé>… ») et le champ « Branche » d'un ticket (« Nouvelle branche ticket/<clé> ») suivent le préfixe des tickets ; la barre latérale montre la branche d'un agent sans le préfixe de son projet.
- Agent sur une branche qui existe déjà (« Nouvel agent sur une branche… » à côté de « + Nouvel agent », ou clic droit sur une branche du sélecteur : « Lancer un agent sur cette branche ») : le sélecteur de branche s'ouvre pour choisir, et l'agent a un worktree sur cette branche, vers la même base qu'un agent ordinaire (la branche cible du Kanban si elle existe, sinon la branche du dossier). Une branche distante (`origin/x`) se prend par la branche locale qui la suit, créée au besoin. Refusé pour la branche du dossier du projet (« C’est la branche du dossier du projet : un agent sans worktree y travaille déjà, ou change de branche d’abord. », grisée dans le sélecteur) pour la branche cible du Kanban du projet (celle où les tickets validés sont mergés : ni un agent ni un ticket ne la prend) et pour celle d'un autre worktree (« La branche « X » est utilisée par l’agent N, dans son worktree. »). La branche est celle de l'utilisateur : supprimer l'agent avec « Supprimer aussi le worktree (la branche X est conservée) » ne supprime que le dossier, et Haiku ne la renomme jamais d'après le nom de l'agent.
- « Intégrer <base> » (bouton sous « Merger… » dans la liste des fichiers, menu de l'agent) : la branche de base de l'agent entre dans sa branche, par merge (stratégies « Merge commit » et « Squash », où il n'y a rien à écraser) ou rebase (stratégie « Rebase »), dans son worktree. Refusé pendant son tour (« Attends la fin du tour de <nom> pour intégrer <base>. »), avec des changements de fichiers suivis (« Commite ou mets de côté les changements de l’agent d’abord. »), avec un merge ou un rebase déjà en cours dans son worktree, pour un agent archivé ou sans worktree, quand la validation de son ticket tourne, et si la base a disparu. Sans conflit : toast « <base> intégrée dans <branche>. » (« <branche> a déjà tout ce qu’il y a dans <base>. » s'il n'y avait rien à intégrer). Un conflit de merge est laissé dans le worktree et l'agent reçoit la demande de le résoudre (`conflict_message` du Kanban avec les fichiers pour l'agent d'un ticket, « Le merge de <base> dans ta branche a des conflits sur : … Résous-les, puis commite le merge. » sinon) ; un conflit de rebase est annulé et l'agent reçoit « Rebase ta branche sur <base> et résous ses conflits. » (`rebase_message` pour un ticket).
- Préparation des worktrees (onglet « Projets » des réglages) : des commandes (shell, ligne de commande, sous-dossier du worktree ; réordonnables avec « Monter » / « Descendre » ou `Alt+↑` / `Alt+↓` depuis l'un de leurs champs) lancées sans fenêtre, l'une après l'autre, dans chaque nouveau worktree (agent créé par l'utilisateur ou par un ticket, worktree recréé à la restauration), avec `ESCOUADE_PROJECT_DIR`, `ESCOUADE_WORKTREE_DIR`, `ESCOUADE_BRANCH` (et les ports réservés d'un ticket) ; 20 min max chacune. Pendant ce temps l'agent montre « Préparation… » (barre latérale), « Préparation du worktree · 1/2 · npm ci » avec « Voir la sortie » (conversation : la sortie en direct de l'étape, voir *Conversation*), « Prépare le worktree · … » (carte du Kanban) ; la sortie complète de chaque étape va dans `logs/<agent>-setup.log` du dossier de données (réécrit à chaque préparation, un en-tête « ── 1/2 · npm ci » puis « ── terminée en N s » ou « ── échec : … » par étape ; gardé à l'archivage et quand le projet se ferme avec son historique, supprimé avec l'agent, ou avec le projet quand son historique est effacé) ; son process Claude Code ne démarre qu'une fois la préparation finie (ses hooks et serveurs MCP la trouveraient à moitié faite), et ses messages attendent. Un agent archivé ou supprimé pendant sa préparation l'arrête, et ne prend jamais le ticket qui l'attendait. La première qui échoue arrête la préparation : « La préparation du worktree a échoué sur `<commande>` (code N). » et ses dernières lignes dans la conversation, suivies de « Sortie complète : <chemin du log> » quand il a pu être écrit, et à la suite du premier message d'un ticket ; une sortie qui n'a pas pu être lue jusqu'au bout fait échouer l'étape (« la sortie de la commande n'a pas pu être lue : … ») ; sinon « Worktree préparé (n commandes, x s). ». Supprimer ou archiver l'agent, fermer le projet ou quitter l'app arrête la préparation et ce qu'elle a lancé. Les commandes de démontage tournent dans le worktree juste avant que l'app le supprime (agent supprimé avec son worktree, ticket validé), toutes même après un échec (5 min max chacune) ; un échec est signalé (« Agent supprimé, mais le démontage du worktree a échoué sur … ») sans empêcher la suppression. « ✦ Remplir automatiquement » : un `claude -p` (Sonnet, outils Read, Glob et Grep seulement, lecture refusée hors du projet, sans session, réglages ni MCP) lit le projet dans son dossier et propose les deux listes (dépendances avec le gestionnaire du lockfile, code généré ; démontage souvent vide) ; une commande dont le dossier sort du projet est écartée, comme une commande qui ne tient pas sur une ligne simple (mêmes règles et mêmes messages que pour les commandes de lancement, voir *Barre latérale projet* : ces commandes tournent seules dans chaque nouveau worktree). La proposition s'affiche d'abord en entier sous la rangée (région « Commandes de worktree proposées » : « Proposition de Claude : relis chaque commande en entier. Elles remplacent les deux listes et, une fois enregistrées, tournent seules : la préparation à l'ouverture de chaque nouveau worktree, le démontage avant sa suppression. », chaque commande lisible jusqu'au bout avec son shell et son dossier, « Aucune commande. » pour une liste vide) ; « Remplacer les commandes » met les deux listes à la place du brouillon, « Ignorer » le laisse tel quel.
- Restaurer un agent archivé dont le dossier du worktree a disparu (supprimé après une PR ou un push) le recrée depuis sa branche, avec les fichiers copiés et la préparation ; sans sa branche, il reste tel quel.
- Compteurs git rafraîchis par watcher de fichiers (debounce), pas par polling.
- Synchro du checkout principal du projet avec son dépôt distant : commits à tirer / à pousser par rapport à la branche suivie. Fetch en arrière-plan peu après le démarrage puis toutes les 5 min, un dépôt à la fois, sans jamais demander d'identifiants (ni fenêtre Git Credential Manager) ; échecs seulement journalisés. Pull en avance rapide uniquement (branches divergées : message clair, rebase ou merge à faire à la main), Push (une branche sans branche suivie, ou dont la branche distante a été supprimée, est publiée sur origin, ou l'unique dépôt distant), Fetch à la demande. Rien à synchroniser en HEAD détachée ou sans dépôt distant.

### Branches

- Base du projet : la branche cible du Kanban si elle existe en local, sinon la branche du dossier, sinon HEAD ; avec la branche que cette base suit (une branche mergée par une pull request, récupérée par fetch mais pas encore tirée, compte comme mergée). Une branche est « mergée » quand son bout est un ancêtre de la base, ou que la merger dans la base ne changerait rien (squash-merge, cherry-pick : `git merge-tree --write-tree`, git 2.38 au moins ; avec un git plus ancien, une branche squash-mergée compte comme non mergée, jamais l'inverse). La base elle-même n'est jamais « mergée en elle-même ».
- Sélecteur de branche (le bouton de branche de la barre d'état l'ouvre au-dessus de la barre, dans tout dépôt git, avec ou sans dépôt distant) : champ de recherche (focus à l'ouverture, filtre approché comme « Ouvrir un fichier »), « Locales » (la courante cochée, en tête, puis par nom) puis « Distantes » (`origin/HEAD` exclu) ; chaque ligne dit ses commits à pousser et à tirer sur sa branche distante (« ↑2 ↓5 », aussi à côté du nom dans la barre), « distante supprimée » quand sa branche suivie a disparu, « suivie par <locale> » pour une distante que cette locale suit déjà. Une branche prise par le worktree d'un agent (ou d'un autre worktree) montre « utilisée par l'agent X », n'est pas activable, et dit pourquoi au survol et sous le curseur. ↑ ↓ Entrée Échap, clic ; clic droit (touche Menu, Maj+F10) → « Supprimer la branche… » (jamais pour la courante ni une branche de worktree), précédé de « Lancer un agent sur cette branche » pour une branche libre. Au pied : « Nouvelle branche… », « Branches mergées… », et la synchro : « Récupérer » (pull), « Pousser » (« Publier » sans branche suivie ou si elle a été supprimée du dépôt distant), « Fetch » ; l'action en cours s'affiche sur le bouton de la barre (« Envoi… »), puis un toast résume (« 3 commits tirés ») et le focus revient au bouton de branche.
- Changer de branche (le dossier du projet) : refusé s'il reste des changements non commités sur des fichiers suivis (« Mettre de côté (stash) et changer » : le stash s'appelle « escouade: avant de passer sur <branche> », un toast le dit) ou si un agent sans worktree travaille dans le dossier (du projet, ou d'un autre projet ouvert sur le même dépôt). Il l'est aussi pendant un merge, un cherry-pick, un revert ou un rebase en cours, depuis une HEAD détachée dont les commits n'appartiennent à aucune branche (le texte dit combien), et quand des fichiers non suivis seraient écrasés (ils sont nommés) ; les fichiers non suivis, eux, ne comptent pas comme changements et ne vont pas dans le stash. Si le changement échoue après le stash, les changements reviennent de leur propre stash, ou l'erreur dit où ils sont. Une distante se prend par la branche locale qui la suit, quel que soit son nom, créée au besoin (`git switch --track` ; refusé si une locale du même nom existe sans la suivre). La fenêtre lit les refus par des codes : `DIRTY`, `IN_WORKTREE:<id>:<nom>`, `AGENT_WORKING:<id>:<nom>`, `UNMERGED:<n>`.
- Nouvelle branche : nom vérifié à la frappe comme le fait git (`git check-ref-format` ; refusés aussi : un nom qui commence par `-` ou `@`, ou comme une branche distante, `origin/…`), « À partir de » (la branche courante, une autre, ou le commit donné par le graphe), « et y passer » coché par défaut (les changements non commités suivent si on part du commit courant, sinon le choix du stash est proposé). La branche ne suit aucune branche distante, même créée depuis `origin/main` ; une révision comme `main~1` n'est pas une branche. Nom, existence et point de départ sont vérifiés avant tout stash, et si le changement échoue la branche créée est supprimée et le stash remis.
- Supprimer une branche : une confirmation ; si son travail n'est pas dans la base du projet, une seconde dit combien de commits ne sont dans aucune autre branche (« Supprimer quand même » ; aucun : « Elle n'est pas mergée dans la base du projet, mais ses commits sont dans une autre branche. »). Jamais la branche du dossier du projet (même forcée) ni celle d'un worktree. « Supprimer aussi origin/… » quand la branche distante a le même nom : la copie ne part que si c'est bien celle de la branche (aucune autre locale ne la suit, ni la branche par défaut du dépôt ni la branche distante de la base), avec un bail (`--force-with-lease` : un commit poussé par quelqu'un d'autre depuis le dernier fetch n'est jamais supprimé sans avoir été vu) ; sinon seule la locale part, et l'app le dit. `origin/HEAD` n'est pas une branche : refusé. « Branches mergées… » liste les branches locales déjà dans la base du projet (toutes cochées, hors la base, la courante et celles d'un worktree) et les supprime ensemble, sans jamais forcer ; après une suppression en partie réussie, les cases décochées le restent. Le sélecteur sert aussi à nettoyer, avec ses confirmations, les branches qu'Escouade ne supprime jamais seule : celle qu'un ticket a reprise, celle d'un agent supprimé avec « Supprimer aussi le worktree ».
- Depuis le graphe git : clic droit sur un commit (ou touche Menu / Maj+F10 sur la ligne qui a le focus) : « Créer une branche ici… » (la fenêtre de nouvelle branche, ce commit comme point de départ) ; pour chaque branche locale du commit, « Passer sur <branche> » et « Supprimer la branche… » (le nom en indication quand le commit en porte plusieurs), grisés avec leur raison pour une branche qu'un worktree tient, absents pour la branche du dossier ; « Comparer avec la branche courante » (« Comparer avec HEAD » sur une HEAD détachée) ouvre la fenêtre de diff sur `git diff courante cible`, titrée « courante ↔ cible » : la cible est la branche du commit (une locale d'abord, sinon une distante), à défaut le commit (hash court). Rien à comparer sur le commit de HEAD. Le menu prend le focus quand il s'ouvre au clavier (↑ ↓ Début Fin, Entrée, Échap ou Tab le ferment et rendent le focus à la ligne). Les branches distantes d'un commit ne se changent ni ne se suppriment d'ici.
- Agent sur une branche qui existe déjà, champ « Branche » d'un ticket et « Intégrer <base> » : voir *Mode worktree* ci-dessus. Les menus contextuels ouverts au clavier (sélecteur, graphe, menu des terminaux) prennent le focus. Les commandes git de branche, de pull et de push tournent en anglais (`LC_ALL=C`) pour reconnaître leurs refus quelle que soit la langue du système.

## Éditeur

- Mode éditeur dans la zone principale d'un projet. Points d'entrée : « `</>` Éditeur » dans l'en-tête d'un agent et « Ouvrir dans l'éditeur » au clic droit sur un agent (son worktree, ou le projet sans worktree) ; « Parcourir » sur la ligne de la branche, dans le pied de la barre latérale, et « Éditeur » dans la barre d'onglets (branche du projet) ; bouton `</>` et clic droit sur un fichier non commité ; dans la conversation, le chemin du fichier des lignes Edit / Write / MultiEdit (ouvert à la première ligne modifiée) et les fichiers listés par la carte « Tâche terminée » ; « Ouvrir un fichier » (`Ctrl+P`, ci-dessous). Un fichier en dehors du dossier de la source ne s'ouvre pas (message). Remplace l'ouverture dans un éditeur externe.
- Choisir un agent dans la barre latérale bascule l'éditeur sur sa source ; « + Nouvel agent », un terminal, une commande de lancement, le Kanban, une notification, `Ctrl+J`, la vue d'ensemble ou un résultat de « Rechercher dans les conversations » ferment l'éditeur pour montrer ce qu'ils ouvrent (ses onglets sont gardés).
- Sélecteur de source : branche du projet ou worktree d'un agent (nombre de modifications) ; onglets avec point « non enregistré ». Pour un agent dont le worktree a été supprimé (après une pull request ou un push), l'arborescence, la recherche et l'ouverture d'un fichier disent « Le worktree de l'agent n'existe plus » ; rien n'est recréé à son chemin. L'éditeur et les terminaux refusent un agent d'un autre projet. Deux onglets ouverts de même nom montrent en gris le plus court dossier qui les distingue (« index.ts · editor », « index.ts · board ») ; l'infobulle donne le chemin complet, et le bouton de fermeture porte le même nom (« Fermer index.ts · board »).
- Colonne de gauche : deux vues, « Fichiers » et « Rechercher dans les fichiers » (boutons en haut de la colonne, « Vue de la colonne »), gardées toutes les deux (défilement de l'arbre et dépliage des résultats retrouvés). Elle se redimensionne par une poignée entre elle et le code (séparateur « Largeur de la colonne des fichiers ») : glisser, ← → par 16 px, Début / Fin jusqu'aux bornes, double-clic pour revenir à 240 px ; de 160 px à la moitié de l'éditeur. La largeur choisie vaut pour tous les projets (préférence locale `escouade.editor.treeWidth`) ; une fenêtre trop étroite la dessine plus petite sans l'oublier. Un relâchement perdu (bouton relâché hors de la fenêtre, fenêtre qui perd le focus) termine le glissement.
- Arborescence à la manière de l'explorateur de VS Code : fichiers connus de git (ignorés exclus), dossiers d'abord ; chevrons, guides d'indentation, icône colorée par type de fichier ; nom coloré et lettre M / A d'un fichier modifié ou ajouté, point coloré sur ses dossiers ; un dossier qui ne contient qu'un dossier partage sa ligne (`src/lib/editor`) ; le fichier affiché est amené à l'écran. Les fichiers ignorés par git qui correspondent aux « Fichiers copiés dans les worktrees » du projet (motifs lus depuis la racine de l'arborescence et, pour un projet dans un sous-dossier de son dépôt, depuis ce dossier) sont montrés en grisé, avec l'infobulle « Ignoré par git » : à la racine du projet comme dans un worktree, ils s'ouvrent, se modifient et se retrouvent avec `Ctrl+P` ; aucun autre fichier ignoré n'apparaît, un dossier entièrement ignoré n'est pas parcouru, et ces fichiers restent hors des commits. Clavier : ↑ ↓ Début Fin, → déplie un dossier ou y entre, ← le replie ou remonte au parent, Entrée ouvre un fichier ou (dé)plie un dossier, `F2` renomme la ligne, `Suppr` (`⌘⌫` sous macOS) la supprime (avec une touche de modification, ni l'un ni l'autre). En tête : « Nouveau fichier », « Nouveau dossier », « Actualiser », « Tout réduire ».
- Clic droit sur une ligne : « Nouveau fichier… », « Nouveau dossier… », « Ouvrir un terminal ici » (dans le dossier, ou celui du fichier, de la source affichée ; nommé d'après le dossier), « Afficher dans l'Explorateur » (nommé comme le système : « Afficher dans le Finder » sous macOS, « Ouvrir le dossier contenant » sous Linux ; le gestionnaire de fichiers s'ouvre avec le fichier ou le dossier sélectionné), puis « Renommer… » (F2), « Supprimer » (Suppr), puis « Copier le chemin », « Copier le chemin relatif ». Sur l'espace libre : le premier groupe seulement, à la racine (la racine ne se renomme ni ne se supprime) ; « Afficher dans l'Explorateur » y ouvre le dossier de la source, comme un terminal (celui du projet, ou le worktree de l'agent), et s'appelle « Ouvrir le dossier » sous Linux. Un worktree disparu est refusé (« Ouverture du gestionnaire de fichiers impossible : Le worktree de l'agent n'existe plus »).
- Créer un fichier : « Nouveau fichier » (dans le dossier de la dernière ligne cliquée, sinon celui du fichier affiché) ou clic droit (dans le dossier, à côté du fichier, ou à la racine sur l'espace libre). Le nom se tape dans l'arbre, icône comprise ; `dossier/nom.ts` crée les dossiers. Entrée crée le fichier vide et l'ouvre, le curseur dedans ; Échap annule ; quitter le champ crée si le nom est valide (passer à une autre fenêtre ne décide rien) ; un refus du disque s'affiche sous le champ, Entrée réessaie. Refusés, avec la raison sous le champ : un nom déjà pris (casse ignorée ; « « .env » existe déjà à cet endroit (ignoré par git). » pour un fichier copié montré grisé), un chemin qui commence ou finit par `/`, `.` ou `..`, et sous Windows un nom qu'il modifierait ou réserve (`a.`, `?`, `CON`…). Un fichier ignoré par git s'ouvre, avec un message : l'arborescence ne le montre pas.
- Nouveau dossier : même champ, sans icône de fichier ; refusé quand quoi que ce soit est déjà là. Le dossier créé s'affiche vide jusqu'à ce qu'un fichier y soit (oublié au changement de source), et devient le dossier du prochain « Nouveau fichier ».
- Renommer : le champ prend la place de la ligne, prérempli et l'extension hors de la sélection (le nom entier pour un dossier ou `.env`) ; une ligne qui regroupe des dossiers (`src/lib/editor`) renomme le plus profond. `dossier/nom.ts` déplace dans des dossiers créés au besoin (un déplacement refusé par le disque retire ceux de ces dossiers qui sont restés vides). Un gros dossier se déplace sans retenir le reste de l'app. Refusés : un nom pris par autre chose (un dossier vide compris), sauf un simple changement de casse d'un fichier ou d'un dossier que git ne suit pas (pour ce que git suit : « git suit « src/App.ts » sous ce nom : pour n'en changer que la casse, passe par git mv dans un terminal. ») ; un dossier dans lui-même ; les noms que Windows modifierait ; le chemin d'un fichier ouvert avec des modifications non enregistrées (« « x » est ouvert avec des modifications non enregistrées. »). Le déplacement ne remplace jamais ce qui apparaîtrait entre-temps à l'arrivée (déplacement sans écrasement du système). Les onglets du fichier, ou des fichiers du dossier, suivent tout de suite, avec leur texte non enregistré, leur historique d'annulation, leur curseur et leur comparaison ; l'historique de navigation, les fichiers récents de `Ctrl+P` et les dossiers dépliés aussi. Un fichier non enregistré apparu au nouveau chemin pendant le renommage laisse les onglets à l'ancien nom (« Les onglets restent à l'ancien nom : « x » est ouvert avec des modifications non enregistrées. »). Toasts : « env.txt n'est plus ignoré par git : il peut être commité. » (un fichier copié renommé hors des motifs de git), « debug.log est ignoré par git : l'arborescence ne le montre pas. ».
- Supprimer : vers la corbeille du système (sous macOS par NSFileManager, sans demander de piloter le Finder ; « Remettre » n'y est donc pas proposé), après « Supprimer « nom » ? » (« Il part dans la corbeille. », « Le dossier part dans la corbeille. », « Le dossier et son fichier partent dans la corbeille. », « Le dossier et ses N fichiers partent dans la corbeille. », comptés dans l'arborescence affichée). Les fichiers concernés non enregistrés sont demandés d'abord, l'un après l'autre (« Enregistrer », « Ne pas enregistrer », ou annuler, qui arrête tout) ; un fichier dans lequel on tape pendant la suppression garde son onglet et son texte, sous « Ce fichier a été supprimé. ». Un lien est supprimé, pas sa cible. Refus de la corbeille : « Suppression impossible : un fichier est peut-être ouvert ailleurs ou protégé » ou « Suppression impossible : le fichier est introuvable ou inaccessible » (le texte du système va au journal) ; un autre refus (un dossier protégé, voir ci-dessous) s'écrit de même, « Suppression impossible : <raison> ».
- Ni renommés, ni supprimés (et rien n'y est créé depuis la source du projet : ni dossier, ni nouveau fichier, ni fichier recréé en enregistrant ; un fichier de worktree déjà là, ouvert par un lien, s'enregistre) : les worktrees des agents (`.claude/worktrees` à toute profondeur, le « Dossier des worktrees » du projet quand il est dans la source, ceux que `git worktree list` donne pour le dépôt, ceux des agents de l'app), le dossier de chaque projet de l'app qui se trouve dans la source, et un dossier qui en contient un (« packages/web est le dossier d'un projet », « packages contient le dossier d'un projet », « sub contient le worktree d'un agent ») ; vérifié sur le chemin écrit et sur le chemin réel (liens suivis, noms courts Windows comme `WORKTR~1`). Un renommage ou une suppression en cours retient le redémarrage automatique pour mise à jour. Limites : sur un partage réseau sans corbeille, Windows peut supprimer pour de bon alors que la confirmation parle de corbeille ; les résultats de recherche gardent les anciens chemins jusqu'à la recherche suivante.
- CodeMirror 6 aux couleurs du design : coloration, recherche (Ctrl+F), indentation détectée, marques des lignes modifiées par rapport à HEAD (projet) ou à la branche de départ (worktree), compte dans le fil d'Ariane (« N lignes modifiées vs main »). `Alt+clic` (Option+clic) ajoute un curseur. « Ln, Col » de la barre d'état compte en caractères (un emoji en vaut un), comme toute colonne de la navigation et de la recherche.
- Ctrl+S ou « Enregistrer » enregistre (fins de ligne et BOM conservés, écriture atomique). Un fichier changé sur le disque se recharge s'il n'est pas modifié ; sinon un bandeau « Ce fichier a changé sur le disque. » propose « Recharger », « Comparer » ou « Garder ma version ». « Garder ma version » n'écrit que par-dessus la version du disque pour laquelle le bandeau est apparu (ou celle qu'un enregistrement refusé a trouvée) : si l'agent a écrit depuis, rien n'est enregistré, le texte reste (« Le fichier a encore changé sur le disque : rien n'est enregistré, tes modifications sont toujours là. ») et le bouton attend une seconde avant d'écraser cette nouvelle version ; le disque revenu à la version ouverte : « Rien n'a été enregistré : le fichier est revenu à la version que tu avais ouverte. ». Un fichier supprimé du disque : bandeau « Ce fichier a été supprimé. » avec « Fermer » ou « Le recréer en enregistrant ». Fermer un onglet ou quitter avec des fichiers non enregistrés demande confirmation ; « Quitter Escouade ? », annulé, ramène la fenêtre qu'il avait remplacée (la modale « Commit » avec son message ; une autre, comme les réglages, se rouvre), sauf une fenêtre réglée entre-temps (commit lancé ou fait, mais un commit refusé par git revient ; confirmation dont le choix tourne ; mise à jour qui n'est plus prête). Supprimer un agent ou fermer un projet prévient des fichiers non enregistrés qui seront perdus. Une confirmation qui en enchaîne une autre ouvre une nouvelle fenêtre, qui prend le focus.

### Navigation de code

- `Ctrl+clic` (Cmd+clic) ou `F12` (depuis le curseur) suit ce qui est sous la souris ; touche enfoncée, la zone est soulignée et le curseur devient une main (relâcher la touche, quitter la zone ou la fenêtre retire le soulignement ; jamais avec AltGr ni Maj). Résolveurs essayés dans l'ordre :
  - niveau A (liens) : imports relatifs ou aliasés en JS/TS/JSX/TSX/Svelte/Vue (`import … from`, `export … from`, `import()`, `require()` ; extensions `.ts .tsx .d.ts .js .jsx .mjs .cjs .svelte .vue .json`, puis `index.*` ; un `./x.js` trouve `x.ts` ; `compilerOptions.paths` et `baseUrl` du `tsconfig.json`, sinon du `jsconfig.json`, de la racine, lus en JSON avec commentaires quand la source s'affiche, et `$lib` → `src/lib`) ; CSS/SCSS `@import`, `@use`, `@forward` (partiels `_x.scss`) et `url()` relatifs ; Rust `mod x;` (`x.rs` ou `x/mod.rs`, à côté ou dans le dossier du module parent) ; Python `from .x import`, `from ..x.y import`, `import a.b` (depuis la racine de la source ; `x.py` ou `x/__init__.py`) ; liens relatifs de Markdown (références comprises) et `src` / `href` de HTML ; partout, un chemin de l'arborescence suivi ou non de `:ligne` ou `:ligne:colonne` (`src/lib/x.ts:42:7`, aussi en fin de phrase ou avec des `\`). Un paquet (`react`, `@scope/x`) n'est pas navigable ; un alias à motif qui ne trouve rien non plus. Seuls les fichiers de l'arborescence sont des cibles : un import relatif vers un fichier absent donne « Fichier introuvable : <chemin> ».
  - niveau B (définitions, sans serveur de langage) : le mot sous la souris quand c'est un identifiant, hors commentaires, chaînes, nombres et mots-clés (mais dans les `${…}`), et hors fichiers de prose (`md`, `txt`…). D'abord dans le fichier, par l'arbre syntaxique (JS/TS, Svelte, Vue, Rust, Python, Go) : la définition la plus proche avant le clic dans une portée qui le contient. Puis, si c'est un import, dans le fichier importé (JS/TS, Python `from … import`, Rust `use crate::` / `self::` / `super::` et chemins Rust 2018), lu dans son onglet ouvert s'il l'est ; un import de paquet va à la ligne de l'import, un fichier qui ne définit pas le nom (import par défaut, `* as`) s'ouvre en haut. Sinon une recherche dans les fichiers du même langage, par un motif de définition (git grep), vérifiée ligne par ligne, rangée : même fichier, même dossier, le reste.
- Une cible : le fichier s'ouvre dans la même source, curseur à la ligne et à la colonne, ligne centrée. Plusieurs : liste « Définitions de « X » » sous le mot (au-dessus s'il n'y a pas la place ; 50 au plus, « chemin:ligne » et la ligne), ↑ ↓ (en boucle), Entrée ou clic, Échap ou un clic ailleurs la ferment. Aucune : « Aucune définition trouvée pour « X ». ». Une erreur : « Navigation impossible : <erreur> ». Seule la réponse du dernier clic compte, et une réponse arrivée après un changement de fichier, une modification du texte ou la fermeture de l'éditeur est oubliée.
- Historique, par projet et par source (50 places, en mémoire) : chaque saut (navigation, résultat de recherche, `Ctrl+P`) note d'où il part. `Alt+←` / `Alt+→` (sous macOS `⌃-` / `⌃⇧-`, avec la touche Contrôle et non Cmd), et les boutons « précédent » / « suivant » de la souris au-dessus de l'éditeur, reculent et avancent ; un nouveau saut vide la pile « suivant », une place dont le fichier a disparu est sautée. Ces touches ne sont prises que dans l'éditeur (jamais dans un terminal ni le composer).
- Limites : `extends` du tsconfig n'est pas suivi, et un `tsconfig.json` modifié ne compte qu'à l'affichage suivant de la source ; pas de réexport (`index.ts` qui rassemble), pas de membre d'un autre fichier (`obj.methode`), pas de `import x` Python vers sa définition ; les mots d'un fichier HTML, CSS, JSON ou YAML sont soulignés mais mènent le plus souvent à « Aucune définition trouvée… ».

### Recherche dans les fichiers

- `Ctrl+Maj+F` (éditeur affiché seulement ; dans un terminal, la touche reste au shell) ouvre la vue « Rechercher dans les fichiers » (titrée « Recherche »), le curseur dans le champ « Rechercher », avec le texte sélectionné dans le code s'il tient sur une ligne et que le focus est dans le code (échappé quand « Expression régulière » est activée). Options dans le champ : « Respecter la casse », « Mot entier », « Expression régulière ». La recherche part 250 ms après la frappe (Entrée : tout de suite, et de nouveau), dans la source affichée ; elle repart au changement de source ; seule la réponse de la dernière compte, et les résultats précédents restent, atténués, jusqu'à elle. Elle est gardée par projet tant que l'app tourne, même éditeur fermé.
- Backend (`code_search`) : `git grep` dans la racine de la source, sur les fichiers suivis et nouveaux (ignorés exclus ; dossier sans git : ses fichiers sans ceux que l'arborescence saute, `node_modules`, `target`…), jamais dans les worktrees des agents (`.claude/worktrees` à toute profondeur, et le « Dossier des worktrees » du projet) ; 2 000 lignes demandées (5 000 au plus), 10 s au plus, git arrêté au-delà (avec ce qu'il lance). Une expression s'écrit comme en JavaScript : `git grep -P` quand git l'a, sinon traduite (`\d`, `\s`, `\w`…) ; ce qui ne se traduit pas est refusé (« Cette expression n'est pas prise en charge par git sur ce poste : \b »), une expression invalide aussi (« Expression régulière invalide. », sous le champ), comme un motif sur plusieurs lignes. Chaque ligne trouvée arrive avec chaque correspondance, dans une fenêtre de 300 caractères autour de la première.
- Résultats : un groupe par fichier (icône, nom, dossier, nombre, repliable), puis ses lignes, chaque correspondance surlignée. En bas : « Recherche… », « N résultats dans M fichiers » (lignes), « Aucun résultat. », et « Résultats limités aux 2 000 premiers. » ou « Recherche arrêtée après 10 s : résultats partiels. ». Clic ou Entrée sur une ligne : le fichier à la ligne et à la colonne, dans l'historique de navigation. Clavier : ↓ depuis le champ, ↑ ↓ Début Fin entre les lignes, ↑ depuis la première revient au champ, → déplie un fichier ou entre dans ses lignes, ← le replie ou remonte au fichier.
- `Maj+F12` (« Trouver les références ») cherche le nom sous le curseur, où qu'il soit, en « Mot entier » et « Respecter la casse », « Expression régulière » désactivée.
- Limites : la recherche lit le disque, pas les onglets non enregistrés ; les résultats ne suivent pas les fichiers modifiés depuis (Entrée relance) ; « Mot entier » suit les lettres ASCII de git (`caf` trouve `café`) ; une correspondance au-delà des 300 caractères montrés n'est pas surlignée.

### Ouvrir un fichier

- `Ctrl+P` (Cmd+P sous macOS) ouvre « Ouvrir un fichier » sur la source de l'éditeur s'il est ouvert, sinon le worktree de l'agent sélectionné, sinon le projet (rappelée à droite du champ) ; l'arborescence est relue à chaque ouverture. La saisie trie les fichiers (nom qui commence par elle, nom qui la contient, chemin qui la contient, puis lettres dans l'ordre dans le nom, puis dans le chemin ; début de mot favorisé, chemins courts d'abord), 50 au plus ; `nom:42` ouvre à la ligne 42 (« · ouvre à la ligne 42 »), `nom:42:7` aussi à la colonne. Champ vide : les fichiers ouverts récemment (30 par source, en mémoire), sauf celui affiché, puis les autres. Nom en gras, dossier en gris, « ignoré par git » pour un fichier copié. Statut : « Chargement des fichiers… », « N fichiers · liste tronquée », « Aucun fichier ne correspond. », « Les 50 premiers résultats : précise ta recherche. ». ↑ ↓ (en boucle), Entrée, clic, Échap ou clic dehors.
- `Ctrl+P` et `Ctrl+Maj+P` n'impriment jamais la page (retenus avant tout champ, même derrière une boîte de dialogue, où `Ctrl+P` n'ouvre rien) ; la touche P est reconnue à sa place sur un clavier d'un autre alphabet (cyrillique, grec), pas sur Dvorak, Colemak ou Workman où elle tape autre chose. Dans un terminal interactif sous Windows, `Ctrl+P` reste au shell (commande précédente) ; dans le journal en lecture seule d'une commande de lancement, il ouvre la palette.

### Voir les changements, comparer avec le disque

- « Voir les changements », à droite de « N lignes modifiées vs main », quand la version de référence existe (pas pour un nouveau fichier ni hors d'un dépôt) : bouton enfoncé (`aria-pressed`) tant que les changements sont montrés dans le texte (vue de fusion de CodeMirror) : les lignes supprimées au-dessus de chaque bloc, les lignes et caractères changés teintés ; le texte reste modifiable. Il vaut pour la vue de l'éditeur, d'onglet en onglet. « Annuler ce bloc » remet le bloc de la référence, sans enregistrer (Ctrl+Z le reprend) ; au clavier, Échap puis Tab atteignent les boutons des blocs. Le diff se fait par lignes ancrées sur les lignes uniques communes, puis par caractères, chaque morceau borné : chaque changement d'un lockfile a son bloc, et taper dans un long bloc réécrit reste instantané.
- « Comparer » (fichier modifié changé sur le disque) : « Comparaison avec la version du disque. », la même vue contre la version du disque, sans toucher au texte ; « Prendre ce bloc » copie un bloc du disque ; « Garder ma version » enregistre le texte, mais seulement par-dessus la version montrée ; « Recharger » prend celle du disque. Le bandeau reste jusqu'au choix. Une version plus récente arrivée pendant la comparaison (l'agent écrit encore) la remplace dans la vue, sans toucher au texte : « Le fichier a encore changé sur le disque : la comparaison montre sa nouvelle version. » dans le bandeau et dans un toast (aussi en revenant sur l'onglet), et « Garder ma version » attend une seconde ; trouvée par un enregistrement refusé : « Le fichier a encore changé sur le disque : rien n'est enregistré, la comparaison montre sa nouvelle version. ». Le disque revenu à la version ouverte : « Rien n'a été enregistré : le fichier est revenu à la version que tu avais ouverte. ». Échec : « Comparaison impossible : … ».
- Limites : dans un fichier fait de longues suites de lignes vides, un bloc vide ou sans effet peut rarement apparaître (de l'ordre d'une paire de textes sur 240 000, passager après une frappe) ; au-delà d'environ 63 000 lignes distinctes, ou dans un fichier de lignes répétées, un passage entier peut faire un seul bloc ; une nouvelle version du disque qui n'est pas du texte laisse la comparaison sur la précédente ; tous les boutons des blocs portent le même nom.

## Kanban

- Sélecteur « Agents | Kanban » en haut de la barre latérale (pastille jaune = tickets « À tester »). Le Kanban d'un projet remplace la zone principale (l'éditeur se ferme) : À faire · En cours · À tester · Terminé ; en-tête « <projet> · N tickets · k en boucle », places libres (« n places libres », « Toutes les places sont prises », ou « Quota atteint — reprise à HH:MM »), « ⚙ Après validation : … » (les réglages, sur l'onglet « Kanban » du projet) et « Pilote auto ». Sans Claude Code, « Claude Code introuvable — aucun ticket ne démarre » prend la place des places libres ; de même quand la branche cible ne peut donner aucun ticket : « <cible> n'a encore aucun commit — aucun ticket ne démarre » (dépôt neuf : son premier commit lance la file) ou « Branche cible <cible> introuvable — aucun ticket ne démarre », les cartes « À faire » disant alors « En attente de la branche cible ». Pilote auto en pause (voir *Planificateur*) : une ligne sous l'en-tête le dit, « Pilote auto en pause : quota hebdo à 96 % (reprise à 14:00) », « … quota de 5 h à 100 % (reprise à 14:00) » ou « … limite d'usage atteinte (reprise vers 14:30) » (avec le jour quand ce n'est pas aujourd'hui), avec « Reprendre maintenant » ; les places libres ne s'affichent pas pendant ce temps. Choisir un agent, un terminal ou une commande revient aux agents.
- Fenêtre du ticket : « + » en tête de « À faire » (« Nouveau ticket »), un clic sur une carte « À faire » ou « Modifier » au clic droit (« Modifier <clé> ») ouvrent une grande fenêtre (760 px de large, 88 % de la hauteur au plus et 860 px, corps défilant, pied fixe en bas), et non un formulaire dans la colonne. Titre sur toute la largeur ; « Description » (12 lignes, 10 quand la fenêtre de l'app fait moins de 820 px de haut ; elle grandit avec le texte jusqu'à 60 % de la hauteur, puis défile) ; « Critères d'acceptation » (6 lignes, 5) ; dessous, « Boucles max » et « Branche » à gauche, « Après » (recherche et liste) à droite. Le focus est sur le titre à l'ouverture et revient au « + » ou à la carte à la fermeture. `Ctrl+Entrée` (`Cmd+Entrée`) ajoute ou enregistre depuis n'importe quel champ quand le titre est rempli, sans écrire de ligne dans un champ de texte et sans valider deux fois (ni sur une touche maintenue) ; Entrée dans le titre valide aussi ; le rappel « Ctrl+Entrée pour ajouter » (« … pour enregistrer » en modification) est au pied, avec « Annuler » et « Ajouter » / « Enregistrer ». Le ticket est créé dans le projet d'où la fenêtre s'est ouverte, même si un autre est sélectionné entre-temps. Elle ne se ferme pas pendant l'enregistrement ; un refus la laisse ouverte avec ce qui était saisi (la raison est dans un toast). Les raccourcis de l'app sont coupés derrière elle ; Échap dans le sélecteur de branche ou son menu ne ferme que ceux-là. Images : une image se colle (`Ctrl+V`) ou se dépose n'importe où dans la fenêtre (ses champs, son en-tête et son pied, la fenêtre elle-même), ou se choisit avec « Joindre une image » (à côté du libellé « Description ») ; les vignettes (64 px) sont sous la description, chacune avec une croix « Retirer <nom> » (« Retirer image.png (2/3) » quand il y a plusieurs images : le rang s'ajoute au nom, car les captures s'appellent toutes image.png) ; après une croix, le focus va à la croix suivante, sinon à la précédente, sinon à la description. Mêmes formats et limites que le chat (PNG, JPEG, GIF, WebP ; 5 Mo par image, 18 Mo en tout ; 20 images au plus par ticket), le type étant lu dans le contenu : une image dont le contenu n'est d'aucun de ces formats est refusée (« « x.png » n'est pas une image : un ticket prend les images PNG, JPEG, GIF et WebP. »). Un texte collé reste un texte, même accompagné d'une image de lui (les cellules d'un tableur). La description cède trois lignes aux vignettes. Les images d'un ticket modifié sont lues à l'ouverture (« Chargement de <nom>… » en attendant) ; celle dont le fichier a disparu est nommée dans un toast et retirée du ticket à l'enregistrement suivant (ce retrait n'est pas une modification : la fenêtre se ferme sans demander) ; les images du ticket ne sont envoyées que si elles ont changé.
- Ticket : clé `<PRÉ>-<n>` (3 premières lettres du projet, `TIC` à défaut ; numéro jamais réutilisé), titre, description, critères (défaut : « Implémentation conforme au ticket », « Tests verts »), boucles max 3 / 5 / 8, et « Après » : les tickets du projet qu'il attend (ci-dessous). Il a aussi, quand `start_ticket` du serveur MCP les lui a donnés (la fenêtre du ticket ne les règle pas), son propre modèle et son propre effort, qui passent avant ceux du Kanban pour son agent : sa carte, dans toutes les colonnes, les montre dans une étiquette à côté de sa clé (« Opus · Max », et au survol comme pour un lecteur d'écran « Modèle de ce ticket : Opus, effort Max (avant celui du Kanban) ») sans l'effort quand le modèle de son agent (celui du ticket, sinon du Kanban, sinon de l'app) n'en prend pas, comme Haiku (« Haiku » seul ; un effort seul sur un Kanban en Haiku : pas d'étiquette) ; il les garde s'il est renvoyé puis relancé. « À faire » : clic → modification, clic droit → Modifier, Passer en tête, Supprimer (« Supprimer DEM-1 ? », « Le ticket et sa description sont supprimés. », plus « Il ne sera plus importé depuis Jira. » pour un ticket importé ; avec des images, « Le ticket, sa description et ses 2 images sont supprimés. », « … et son image … » pour une seule ; bouton « Supprimer »). Sur la carte, un trombone avec le nombre d'images (« 2 images jointes » au survol, et la description de la carte pour un lecteur d'écran). Échap, × ou un clic à côté de la fenêtre d'un ticket modifié (titre, description, images, critères, boucles, « Après »), comme « Annuler », demandent « Abandonner les modifications ? » (« Ce que tu as saisi dans ce ticket ne sera pas enregistré. », bouton « Abandonner ») : la fenêtre disparaît derrière la confirmation, et « Annuler » la ramène avec tous ses champs (« Quitter Escouade ? », annulé, aussi) ; sans changement, elle se ferme tout de suite. Tickets et réglages sont enregistrés avec l'état de l'app.
- Images d'un ticket : ce sont des fichiers de `<données>/tickets/<id>/` (seuls leurs noms sont dans le JSON des tickets), effacés avec le ticket, ou quand l'historique de son projet fermé est effacé (fermer le projet les garde avec son historique) ; l'agent du ticket les reçoit comme des blocs image avant le texte de son premier message (au démarrage, et à la reprise d'un agent qui ne l'a jamais reçu) ; ils restent dans sa session pour les boucles suivantes. Le serveur MCP les joint (`create_ticket`, `update_ticket`), les liste (`get_ticket`), les lit (`get_ticket_image`) et les transmet (`split_ticket`), aux mêmes limites et avec les mêmes refus que la fenêtre (voir *Serveur MCP*).
- Dépendances : « Après » liste les autres tickets du projet pas encore « Terminé » (« DEM-n Titre », du plus ancien au plus récent), avec « Rechercher une clé » (la clé interne, ou la clé externe d'un ticket importé ; les tickets cochés restent visibles ; « Aucun ticket pour cette clé ») ; la section n'apparaît que s'il y a un candidat. Cocher un ticket qui attend déjà celui-ci, directement ou non, est refusé (« DEM-3 attend déjà DEM-5 (directement ou non). ») ; le backend refuse aussi une boucle, et ne garde que des tickets du projet, chacun une fois, jamais le ticket lui-même. Supprimer un ticket le retire des tickets qui l'attendaient. Sur la carte « À faire » : « ⏸ après DEM-3 » (« ⏸ après DEM-3 et DEM-4 ») tant qu'un ticket attendu n'est pas « Terminé » ; « Lancer » demande alors « Lancer DEM-5 ? » (« DEM-5 attend DEM-3, pas encore terminé. Le lancer quand même ? », bouton « Lancer quand même »), et un ticket lancé à la main part sans l'attendre. « Pris dès qu'une place se libère » va à la première carte qui n'attend rien. Le premier ticket fixe la branche cible : celle du projet, même sans commit ; sur une HEAD détachée, il est refusé (« Le projet n'est sur aucune branche : choisis la branche cible dans les réglages du Kanban. »).
- Avancement : à chaque bilan, l'agent donne la liste succincte de ce qui est en place (3 à 8 éléments courts) ; le dernier bilan remplace le précédent, un bilan sans liste garde la précédente. La carte « En cours » montre les 3 derniers éléments (« +n » pour les autres), la carte « À tester » toute la liste sous « Ce qui a été fait ». La carte « Bilan des critères » de la conversation et le corps de la PR la reprennent ; elle nourrit le message de commit généré.
- Planificateur : tant que les tickets « En cours » non bloqués sont sous le maximum (1 à 6, 2 par défaut), le premier ticket « À faire » qui n'attend aucun ticket non terminé part (pilote auto) ou ceux lancés à la main (« Lancer ») ; rien ne part tant qu'un agent attend la fin de sa limite d'usage, ni pendant une pause du pilote auto (tickets lancés à la main compris : « Lancer » n'est alors pas proposé ; une passe déjà en cours revérifie avant chaque départ). Pause :
  - quota : « Pause au-delà du quota » (réglage de l'app, 80 / 90 / 95 / 100 %, 100 % par défaut ; une autre valeur écrite à la main vaut 100 %) ; une fenêtre (5 h ou hebdomadaire) à ce seuil ou au-delà, dont la fin est connue et pas encore passée, retient les tickets jusqu'à sa fin plus 30 s, ou jusqu'à ce qu'une lecture des quotas la redonne sous le seuil ; avec plusieurs comptes Claude, la pause se calcule compte par compte (voir *Comptes Claude*) ;
  - limite d'usage : l'agent d'un ticket arrêté par la limite sans reprise prévue (reprise automatique coupée ou annulée, clé API, heure inconnue) bloque son ticket, et le pilote auto se met en pause 30 min avant que la place libérée serve, au lieu de lancer le ticket suivant sur la même limite ;
  - « Reprendre maintenant » lève la pause de limite et chaque fenêtre au-delà du seuil jusqu'à la fin qu'elle avait (une fenêtre suivante, ou qui repasse le seuil, retient de nouveau ; un agent qui attend sa propre reprise retient toujours) ; la pause (fenêtres lues et levées comprises) est gardée dans `state.json` et tient après un redémarrage ;
  - pendant la pause, les cartes « À faire » disent « En attente : pilote auto en pause » (« En attente de la branche cible » et « ⏸ après … » passent avant). Limite : une fenêtre dont la fin n'est pas connue ne met jamais en pause.
- Départ : un agent `<clé>-<titre>` (modèle et effort du ticket, sinon du Kanban, sinon de l'app ; mode du Kanban, sinon de l'app ; avec Haiku, qui n'a ni effort ni mode Auto, l'agent part sans effort et, si son mode serait Auto, en mode « Demander ») dans un worktree `ticket/<clé>` (« Préfixe des branches des tickets » du projet) créé depuis la branche cible (ou, si le formulaire du ticket dit « Reprendre une branche existante… » dans son champ « Branche », dans un worktree sur cette branche, qui doit exister, libre et n'être ni celle du dossier du projet à ce moment-là ni la branche cible du Kanban, sinon le ticket est bloqué avec la raison ; « Nouvelle branche ticket/<clé> » par défaut ; l'entrée « Reprendre une branche existante… » dit au survol « Escouade ne supprime jamais cette branche, même une fois le ticket validé. » ; si l'agent précédent du ticket, archivé, a encore la branche dans son worktree, ce dossier est supprimé avant le départ quand il n'a aucun changement non commité — la branche reste, et restaurer l'agent recrée le dossier si la branche est libre —, sinon le ticket est bloqué avec « L’agent <nom>, archivé, garde la branche « <branche> » dans son worktree avec des changements non commités : commite-les ou supprime l’agent, puis reprends le ticket. »), un bloc de 10 ports (depuis 4100 ; aucun quand isola gère le projet : voir *Lancement de test*), les fichiers ignorés par git copiés (`.env*` par défaut, réglable dans l'onglet « Projets » des réglages ; un fichier seulement non suivi ne l'est jamais : il apparaîtrait comme une modification à commiter), sa préparation (voir *Git & fichiers*), le protocole du ticket passé par `--append-system-prompt` (sur une ligne), puis, la préparation finie, le premier message avec les critères numérotés (suivi de l'échec de la préparation, s'il y en a un).
- Boucle : chaque fin de tour est lue (dernier bloc `escouade` du texte de l'assistant) : tous les critères atteints → « À tester » ; limite de boucles → « À tester » avec « Objectif partiel » ; sinon boucle suivante avec les critères manquants et leurs notes. Sans bilan : un rappel, puis « Bilan des critères manquant ». Stop → « Interrompu » ; erreur ou process mort → « Erreur : … » ; limite d'usage → la reprise automatique s'en charge. Un ticket bloqué libère sa place ; « Reprendre » relance son agent. Au démarrage, un tour coupé par l'arrêt de l'app est repris ; une validation coupée laisse « Validation interrompue ».
- Carte « En cours » : « Boucle n/max », critères ✓ / ○, barre de progression, derniers éléments de l'avancement, et l'activité en direct de l'agent (« Lit src/db.ts », « Lance npm test », « Réfléchit »…) ou « Question en attente de ta réponse » ; au-dessus, la ligne d'état que l'agent a donnée par `report_progress`, s'il en a donné une (voir *Serveur MCP*). Les cartes « En cours » et « À tester » portent aussi le coût cumulé du ticket (tous ses agents, archivés compris ; rien tant que rien n'a été dépensé) : exact pour les tours finis, « ≈ » quand un tour tourne, comme la barre de statut ; « Terminé » garde « n boucles · coût », le coût de tous ses agents figé à la validation (jamais moins que celui de l'agent qui valide). Un agent supprimé ne compte plus dans le coût d'un ticket. Dans une colonne étroite, le pied de la carte garde le nom de l'agent (une douzaine de caractères au moins) et passe le coût et « n/N critères » (ou « n boucles · coût ») dessous ; « ≈ », le montant et « $ » ne se séparent jamais d'une ligne à l'autre. Seules les cartes du Kanban montrent cette activité ; dans la barre latérale, la carte de l'agent porte « ▸ ATL-42 · boucle 2/5 ».
- Validation (« Valider et merger », « Valider + PR », « Valider et pousser », « Valider ») : refusée tant que l'agent travaille (ses fichiers seraient commités en cours d'écriture) ; arrêt des lancements de test (et aucun lancement de test ne part tant que le ticket est en validation) ; tests facultatifs (commande du Kanban, 20 min max, `ESCOUADE_PORT_BASE` défini ; en échec, le ticket repart chez son agent avec les 80 dernières lignes) ; commit des modifications restantes (message Conventional Commits généré par Haiku avec la clé, `feat: <titre> [<clé>]` à défaut ; fichiers copiés exclus) ; sans aucun commit de plus que la cible (aucune modification, ou des modifications défaites), le ticket passe « Terminé » avec « ∅ Aucune modification », sans merge, PR ni push ; refus si un fichier copié du projet y est commité (« … est commité dans la branche », « … est dans l'historique de la branche » s'il en a été retiré depuis) ; puis merge (merge commit, squash ou rebase ; dans le dossier du projet si la cible y est extraite, sinon un worktree temporaire), PR, push, ou rien. Une fois validé (merge, PR, push ou aucune modification ; réglable), le worktree est supprimé après ses commandes de démontage, et sa branche avec lui après un merge ou sans modification (poussée ou proposée, elle reste ; une branche reprise, qui existait avant le ticket, est celle de l'utilisateur : elle n'est jamais supprimée, quel que soit le réglage et quoi que devienne le ticket) ; s'il ne peut l'être, l'issue finit par « · worktree gardé » ; l'agent est archivé (sauf « laisser »). Conflit : me demander (« L'agent résout » / « Annuler »), l'agent résout, annuler. « Renvoyer » rend le ticket au même agent avec « Ce qui ne va pas » ; refusé lui aussi tant que l'agent travaille.
- PR : push de la branche du ticket, puis `gh pr create --repo <propriétaire>/<dépôt>` quand le dépôt distant est sur GitHub et que `gh` est installé (corps passé par l'entrée standard : description, avancement, critères en cases à cocher ; brouillon réglable) ; sans `gh` (ou s'il échoue), la page de comparaison GitHub s'ouvre dans le navigateur, titre et corps remplis, à finaliser ; autre hébergeur : push seul.
- Archiver ou supprimer l'agent d'un ticket « En cours » ou « À tester » le renvoie « À faire » ; l'archiver depuis la barre latérale demande d'abord « Archiver <agent> ? » (« Son ticket <clé> repartira « À faire ». »). Sur une carte « Terminé », « n boucles » compte toutes les boucles de son agent, renvois compris.
- Lancement de test (tout agent à worktree) : « Préparer le lancement » demande la recette à l'agent avec ses ports (pas tant que son ticket est « En cours » : son bilan la donne déjà) ; « ▶ Tester » ouvre une modale qui montre d'abord la recette (« Préparation » : commandes et dossier ; « Lancement » : nom, commande, dossier, variables et adresse de chaque processus ; « Ouverture » : l'adresse ouverte ; « Ces commandes ont été écrites par <agent>. Elles tournent dans ton shell, hors du mode de permission de Claude Code. ») : rien ne tourne avant « Lancer » (« Annuler » ferme la modale). L'approbation est gardée avec l'agent (`state.json`, la recette entière) : une recette identique se lance directement, une recette modifiée (une commande, une variable, un dossier, l'adresse) redemande, et le backend refuse de lancer une étape d'une recette non approuvée. Les caractères invisibles ou de direction (retour chariot, séquence d'échappement, espace de largeur nulle, lettres de droite à gauche) sont écrits en clair, les suites de lignes vides ou d'espaces comptées (« ⟨12 lignes vides⟩ ») et le texte est lu dans l'ordre où le shell le lit ; une recette (ou un `.isola.toml`) qui change pendant qu'elle est lue le dit (« La recette vient de changer : relis-la avant de lancer. ») et garde « Lancer » fermé une seconde. Une fois approuvée, la modale prépare (une fois par recette), lance chaque processus dans un terminal en lecture seule (groupe au nom de l'agent dans « Lancement »), attend qu'il réponde en HTTP (toutes les 500 ms, 3 min max) puis ouvre le navigateur sur la page de la fonctionnalité. Les lancements de test s'arrêtent à la validation, à l'archivage, à la suppression de l'agent, à la fermeture du projet, et quand l'agent donne une nouvelle recette (qui remplace l'ancienne). Quand son ticket passe « Terminé », ses terminaux de test quittent la section « Lancement », avec leurs logs (et la modale « Tester » de l'agent se ferme).
- isola (github.com/cyucelen/isola) : quand le CLI `isola` est dans le PATH (cherché au plus toutes les 30 s) et que le worktree a un `.isola.toml` (pour un ticket : committé sur la branche cible), isola lance ses services sur ses propres ports et adresses `*.localhost`. Alors : pas de bloc de ports pour un ticket (le protocole dit d'utiliser `isola up` / `isola ls --json` / `isola down` et de donner seulement `"lancement": {"ouvrir": …}`), pas de « Préparer le lancement » ; « ▶ Tester » montre d'abord le `.isola.toml` du worktree (fichier que l'agent peut écrire ou modifier, et dont `isola up` lance les services et les commandes `setup` dans ton shell, hors du mode de permission de Claude Code), sous « Configuration isola (.isola.toml) », avec l'adresse « ouvrir » : rien ne tourne avant « Lancer ». L'approbation garde le contenu entier du fichier et l'adresse avec l'agent ; un fichier modifié (une ligne, un caractère) redemande, et le backend refuse `isola up` quand le `.isola.toml` n'est plus celui qui a été approuvé. Une fois approuvé, « ▶ Tester » lance `isola up` dans un terminal en lecture seule (groupe de l'agent ; entrée hors terminal, isola ne demande jamais de mot de passe), lit `isola ls --json` (les services de la branche du worktree), attend que chaque service réponde sur son propre port (le proxy d'isola répond avant lui), puis ouvre l'adresse « ouvrir » de l'agent ou celle du premier service (par le proxy) ; relancé, il revérifie tout. « Tout arrêter », la validation, l'archivage et la fermeture du projet lancent `isola down` ; la suppression du worktree, `isola destroy` (après les commandes de démontage).
- Conversation : un bloc `escouade` s'affiche comme une carte « Bilan des critères » (✓ / ○, critère, note ; puis l'avancement), suivie de « Lancement de test » s'il y a une recette.

## Intégrations (Jira, Trello, GitHub Issues)

- Comptes (onglet « Intégrations » des réglages, connectés tout de suite, hors du brouillon « Enregistrer ») : Jira Cloud (site en https, http seulement vers cette machine, e-mail, jeton d'API ; vérifié par `GET /rest/api/3/myself`), Trello (clé d'API et jeton, « Obtenir un jeton pour cette clé » ouvre la page d'autorisation ; `GET /1/members/me`), GitHub (jeton, ou vide : celui de `gh auth token`, « · via gh » ; `GET /user`). Un refus s'affiche sous le formulaire (« Jira refuse ces identifiants (401) — … »). Les secrets (jetons, clé et jeton Trello) vivent dans le trousseau du système (Gestionnaire d'identification Windows, Trousseau macOS ; service `dev.gagnaire.escouade`, un compte par intégration : `jira`, `trello`, `github`, qui garde un JSON `{"key","token"}`) ; le reste des comptes dans `~/.escouade/integrations.json`, à part des réglages. Ils ne repassent jamais par la fenêtre (elle ne reçoit que « Connecté · <compte> ») ni par le journal. « Connecter… » écrit dans le trousseau et relit avant d'enregistrer le fichier sans eux ; « Déconnecter » les y efface ; GitHub via `gh` n'y laisse rien (l'ancien jeton d'un compte passé à `gh` est effacé). Un effacement refusé est noté dans le fichier (`toForget` : les noms des services, jamais un secret ; un service que cette version ne connaît pas, noté par une plus récente, y est ignoré au lieu de rendre tout le fichier illisible) et retenté au démarrage suivant, sauf si le service a de nouveau un compte avec son propre jeton ; « Déconnecter » le dit dans un toast quand le jeton était dans le trousseau (« Le jeton <service> n'a pas pu être retiré du trousseau du système : Escouade réessaiera au prochain démarrage, ou retire-le à la main (son nom contient « escouade »). »). Aucune autre entrée n'est jamais effacée, même d'un service qu'aucun compte ne cite (fichier réécrit après un fichier illisible, autre version) : elle peut être la seule copie d'un jeton. Au chargement, un secret trouvé dans le fichier (version d'avant 1.6, ou refusé la fois précédente) est écrit dans le trousseau, relu pour vérifier, et seulement alors retiré du fichier (réécrit d'un coup, sur le disque avant de remplacer l'ancien). Trousseau indisponible (ou absent, hors Windows et macOS) : le secret reste dans le fichier (droits 0600 sous Unix), l'onglet le dit sous le compte (« Trousseau du système indisponible : le jeton reste dans ~/.escouade/integrations.json. »), et le démarrage suivant retente. Trousseau qui ne rend pas les secrets d'un compte au démarrage (hors d'atteinte, refus, entrée effacée ou illisible ; GitHub via `gh` n'en a pas) : rien n'est réécrit ni effacé, le compte reste connecté mais aucun appel ne part sans eux (GitHub ne prend pas le jeton de `gh` à la place) ; l'appel échoue avec « Trousseau du système illisible : relance Escouade ou reconnecte le compte <service>. » et l'onglet dit sous le compte « Trousseau du système illisible : relance Escouade ou reconnecte le compte. ». Une exécution isolée (`ESCOUADE_DATA_DIR` : tests e2e, démo) range les siens sous `dev.gagnaire.escouade.sandbox`, jamais à la place de ceux de l'utilisateur. Une build de développement sur le dossier de l'utilisateur (non isolée) les écrit dans le trousseau mais les laisse aussi dans le fichier : l'app installée, peut-être plus ancienne, les y lit (une build de développement ne déplace jamais les données de l'utilisateur). Appels par le proxy des réglages ; `ESCOUADE_TRELLO_API` et `ESCOUADE_GITHUB_API` remplacent les adresses des API (tests, démo).
- Sources liées (par projet, enregistrées avec lui) : pour chaque compte connecté, un projet Jira, un tableau Trello ou un dépôt GitHub (le dépôt `origin` du projet en tête, « (dépôt du projet) »), ou « Aucun ». Choisir une source pré-remplit la correspondance : « En cours » et « À tester » → l'état qui ressemble à « en cours », « Terminé » → celui qui ressemble à « à tester », « À faire » inchangé.
- Correspondance des statuts : par colonne du Kanban et par source, l'état externe donné au ticket qui y arrive (statut Jira par sa transition, liste Trello, et pour GitHub « Ouverte », « Fermée » ou une étiquette « ◆ … » qui remplace les autres étiquettes de la correspondance) ou « — inchangé » ; par colonne, « Commenter » (défaut : « À tester » et « Terminé ») : pris par un agent (branche), prêt à tester (critères ✓ / ○, ce qui a été fait), terminé (issue de la validation et son lien), revenu « À faire ». Ces commentaires, comme le résumé de chaque boucle, sont écrits dans la « Langue des textes rédigés par Claude » (voir *Langues*).
- Synchronisation (toute l'app) : « Mettre à jour le statut externe » (défaut : oui), « Publier un résumé à chaque boucle » (défaut : non), « Extraire les critères d'acceptation » (défaut : oui : éléments sous « Critères d'acceptation » / « Acceptance criteria » / « Definition of done », sinon les cases à cocher ; Trello : la checklist de ce nom, sinon toutes). Une synchro à la fois, dans l'ordre des changements (une file, un worker) ; un échec est journalisé et noté sur la carte (⚠ et sa raison), sans bloquer le ticket. L'opération ratée (transition, commentaire) est gardée dans `sync-queue.json` (dossier de données, sans aucun jeton) ; à la lecture, une opération que cette version ne connaît pas (laissée par une version plus récente) est écartée seule, pas toute la file. Un échec qui peut passer plus tard (service injoignable ou trop lent, erreur 5xx, 429, identifiants refusés 401 / 403) est retenté 1, 5, 15 puis 60 min après chaque échec, puis toutes les heures, 24 h au plus après le premier échec, ainsi qu'au démarrage de l'app et au changement suivant du ticket ; les opérations d'un ticket gardent leur ordre (celles qui suivent un échec l'attendent), les autres tickets continuent. Un refus que redemander ne changerait pas (400, 404, 410, 422, Jira sans transition vers l'état) est mis de côté tout de suite, comme un échec au bout de 24 h : plus retenté de lui-même ni au démarrage, il ne retient plus les opérations suivantes du ticket, et reste gardé pour « Resynchroniser ». Une transition remplace celle du même ticket pas encore passée (mise de côté ou non). Un retour en arrière l'emporte aussi quand la colonne où revient le ticket laisse l'état « — inchangé » (« À faire » compte toujours comme un retour, sinon une colonne avant celle de la transition) : envoyée plus tard, elle mettrait le ticket externe là où le ticket n'est plus ; ce qui l'attendait part aussitôt. Passé à une colonne suivante laissée « — inchangé » (« À tester », « Terminé »), le ticket la garde : le ticket externe y serait si le service avait répondu. Les opérations d'un ticket supprimé sont oubliées. Le ⚠ reste tant qu'une opération du ticket attend ou est de côté ; il se déplie : la raison et « Resynchroniser » (retente tout de suite celles qui attendent et celles de côté ; s'il n'en reste aucune, ⚠ laissé par une version précédente, redonne l'état de sa colonne ; un échec le dit dans un toast) ; quand tout est passé, le ⚠ disparaît. Un commentaire peut être publié deux fois : quand son envoi expire, le service l'a peut-être reçu, et il est renvoyé.
- Import automatique : « Importer les tickets étiquetés » (défaut : non), « Étiquette » (défaut `claude-ready`), « Vérifier toutes les » 5 / 15 / 60 min : premier passage 30 s après le démarrage, les tickets ouverts des sources liées qui portent l'étiquette (la première page de chaque source) arrivent dans « À faire » (5 boucles max) avec un toast « 2 tickets importés depuis Jira dans <projet> » ; un ticket déjà importé dans le projet, même supprimé depuis, n'est jamais ramené.
- « ⤓ Importer » (en-tête du Kanban, l'icône seule dans une fenêtre étroite) : sans source liée, « Aucune source liée à ce projet » et « Lier une source » ; sinon une pastille par source (nombre de tickets cochés), « ⚙ Gérer les sources », recherche (300 ms après la frappe : JQL `text ~` ou clé pour Jira, recherche GitHub, filtre local pour Trello), filtres du service (Jira : Assignés à moi, Sprint actif, À faire ; Trello : Mes cartes, une par liste ; GitHub : Assignées à moi, une par étiquette), « Tout sélectionner », ligne : clé externe, titre, type, priorité · assigné · statut, « ✓ n critères détectés » ; « Déjà dans le Kanban » grisé. Par pages (Jira et la recherche GitHub : 50, la liste GitHub : 100, Trello : tout le tableau d'un coup) : « Afficher plus » en bas de la liste quand le service en a d'autres (Jira `nextPageToken`, GitHub `page`), et « 50 affichés sur 312 » dès que le service en compte plus que la liste n'en montre, dernière page comprise (la recherche GitHub s'arrête à 1 000) ; total : le compte approximatif de Jira (jamais moins que la liste) ou celui de la recherche GitHub, aucun quand une pastille d'étiquette GitHub trie les résultats sur place ; « 50 affichés » quand il en reste sans total, « n résultats » quand tout est là ; une nouvelle recherche repart de la première page. Pied : boucles max 3 / 5 / 8, « Importer n tickets » → fin de « À faire », toast « 3 tickets importés depuis Jira et Trello ».
- Ticket importé : clé interne `<PRÉ>-<n>` (branche, agent), référence externe gardée ; titre externe, description (Jira : document ADF converti en markdown) suivie de « Ticket Jira ATL-1287 : <adresse> », critères extraits ou ceux par défaut. Importé une fois par projet (même service, même id ; Jira : l'id du ticket, qui reste quand il change de projet). La recherche GitHub d'un numéro (« #42 ») donne l'issue elle-même. Sa carte porte la pastille du service et la clé externe (clic : le ticket externe dans le navigateur).

## Comptes Claude

- Modèle : un compte = un dossier de configuration de Claude Code (`CLAUDE_CONFIG_DIR` : configuration, identifiants, historique des sessions) + un exécutable optionnel (défaut : celui des réglages ; un chemin propre au compte qui ne trouve rien n'a pas de repli) + « Actif » + son rang. `Settings.accounts` (l'ordre est la priorité), `AgentMeta.account`, `Project.account` (« Compte préféré », vide = Automatique) ; un ancien `settings.json` ou `state.json` se charge sur Principal. Au premier lancement de la 1.7, le Claude Code habituel devient le compte **Principal** (id `principal`, nom « Principal » / « Main » tant qu'il n'est pas renommé), créé en tête s'il manque et jamais supprimé ; il faut toujours un compte actif (sinon Principal l'est).
- **Principal sans `CLAUDE_CONFIG_DIR`.** Il se lance sans la variable, même vers `~/.claude` et même si un dossier a été écrit à la main dans les réglages (il est vidé à chaque chargement et enregistrement) : sous macOS, Claude Code range sa connexion dans le trousseau sous le service `Claude Code-credentials` quand la variable n'est pas définie, et `Claude Code-credentials-<h>` sinon, `<h>` étant les 8 premiers caractères hexadécimaux du SHA-256 de sa valeur normalisée en NFC (`CLAUDE_SECURESTORAGE_CONFIG_DIR`, s'il est défini, prend le pas) ; la définir changerait le nom de l'entrée et déconnecterait l'utilisateur. Chaque dossier de config a donc sa connexion, et les comptes multiples marchent sous macOS ; un autre compte reçoit exactement la chaîne enregistrée, dont Escouade calcule le hachage. Pour Escouade, le dossier de Principal est le `CLAUDE_CONFIG_DIR` de l'environnement de l'app s'il en a un (ses process l'héritent), sinon `~/.claude` ; son `.claude.json` est `~/.claude.json` (à côté de ce dossier), sauf si la variable est définie (`<dossier>/.claude.json`). Sous Windows, Claude Code écrit `<dossier>/.credentials.json` (un drapeau distant, `tengu_windows_credman`, pourrait le faire passer au Gestionnaire d'identification avec les mêmes noms : hors périmètre). Limite : un `CLAUDE_SECURESTORAGE_CONFIG_DIR` hérité de l'environnement de l'app s'appliquerait à tous les comptes, qui partageraient alors une seule connexion ; non traité. Non vérifié sur un Mac avec un second compte connecté : le nom de l'entrée d'un compte ajouté est lu dans le binaire de Claude Code, pas observé, et un compte pourrait donc s'afficher « Pas connecté » sous macOS alors qu'il l'est.
- Réglages › Comptes Claude (après « Claude Code »), enregistré à chaque changement et hors du brouillon (une création ou une suppression touche le disque, « Annuler » ne pourrait pas la reprendre) : par compte, nom modifiable (unique sans tenir compte de la casse), dossier (`~` pour le dossier personnel), exécutable (« Celui des réglages »), état (« Vérification… », « Connecté · <e-mail> », « Pas connecté », « Pas connecté par un compte claude.ai (clé d’API ?) » pour Principal, « Inactif »), « Actif » (grisé pour le dernier compte actif), « Monter » / « Descendre », « Se connecter… » / « Se reconnecter… », « Supprimer ». Le dossier d'un compte est celui du backend, jamais celui que la fenêtre envoie. Supprimer est refusé pour Principal et tant qu'un agent non archivé s'en sert (« Le compte sert encore à N agents. ») ; sinon le compte part avec son quota, est retiré des « Compte préféré » des projets et de la config de Claude Code (entrée du serveur MCP), mais son dossier reste sur le disque, avec sa connexion et ses conversations (« Supprimer le compte « Pro » ? »).
- « Ajouter un compte… » : nom, puis ce qui est repris du dossier de Principal parmi ce qui existe, `settings.json` et `CLAUDE.md` (fichiers), `skills`, `agents`, `commands`, `plugins`, `hooks`, `output-styles` (dossiers) : « Lier (un changement vaut pour les deux comptes) » (défaut) ou « Copier » (chacun a ensuite le sien). Le compte reçoit le dossier `~/.escouade/claude/<nom>` (jamais un dossier déjà présent : celui d'un compte supprimé garde sa connexion et ses sessions). Dossiers liés par une jonction sous Windows (`mklink /J`, sans droits d'administrateur ; `cmd /v:off` pour qu'un `!` d'un chemin ne soit pas lu comme une variable ; un chemin avec `%` n'est pas lié, la fenêtre propose « Copier ») et par lien symbolique sous macOS ; fichiers liés par lien symbolique sous macOS, copiés sous Windows (un lien de fichier y demande des droits d'administrateur, ce que la fenêtre dit). **Jamais partagés** : la connexion (`.credentials.json` ou entrée du trousseau), `.claude.json` (où vit aussi l'entrée du serveur MCP d'Escouade, propre à chaque compte), et tout le reste du dossier, dont l'historique des conversations (`projects/`) : une session vit dans le dossier de son compte, et deux process ne reprennent jamais la même session en même temps.
- Connexion : « Créer et se connecter » et « Se connecter… » lancent le `claude` du compte, directement (sans shell), dans un terminal de la fenêtre (xterm.js, depuis le dossier personnel, avec le `CLAUDE_CONFIG_DIR` du compte ; Échap reste au terminal). Escouade lit la connexion toutes les 2 s : « Connecté au compte <e-mail> » (l'e-mail est `oauthAccount.emailAddress` du `.claude.json` du compte), 1,5 s plus tard le terminal est fermé (et le process avec) et le quota lu. Sur un compte déjà connecté ou dont la connexion a expiré, elle attend une vraie nouvelle connexion (la lecture d'avant est refaite une fois quand la première échoue, pour qu'une connexion expirée ne passe pas pour celle qu'on vient de faire). Fermée avant : le compte reste « Pas connecté ». « Claude Code s'est arrêté avant la connexion. » → « Relancer ». Sous macOS, l'état d'un compte dont le trousseau est refusé reste « Pas connecté » pendant 10 minutes (le compte reste utilisable : Claude Code lit son trousseau lui-même).
- Un agent garde son compte : il se lance avec le `claude` et le dossier du compte, y reprend sa session (`--resume`) après un arrêt ou un redémarrage, et sa copie reste sur le même compte (la session forkée est rangée dans ce dossier). Haiku (nom de l'agent, message de commit) passe par le compte de l'agent, « ✦ Remplir automatiquement » par celui où partirait un nouvel agent du projet. Un agent dont le compte a disparu est restauré sur Principal : sa session n'y est pas, il repart d'une nouvelle (« Session Claude introuvable… »).
- **Quota par compte.** Pour chaque compte, dans l'ordre des réglages : un process vivant du compte (même au repos) est interrogé (`get_usage`) ; sinon, pour un compte actif, l'endpoint de `/usage` avec la connexion de ce compte (sous macOS le trousseau avant le fichier `.credentials.json`, comme Claude Code ; ailleurs le fichier du dossier du compte), au plus une fois toutes les 5 minutes par compte (un compte « Pas connecté » est relu dès la lecture suivante, une connexion expirée reste espacée de 5 minutes). Les `rate_limit_event` du stream d'un agent mettent à jour son compte. « Pas connecté », « Connexion expirée : relance Claude Code pour ce compte. » ; une coupure du réseau garde les dernières valeurs. Les fenêtres gardées d'un lancement à l'autre (`state.json`) le sont par compte ; celles d'avant la 1.7 sont celles de Principal. Le compte en cours (barre d'état, `get_usage`) est celui où partirait un nouvel agent en « Automatique ». Le coût du jour est celui de chaque compte (le panneau) et leur total (la barre d'état).
- **Choix du compte.** Nouvel agent ou ticket : le compte demandé s'il est actif (puce « Compte » du champ de saisie ; une copie garde celui de son original, même désactivé depuis) ; sinon le « Compte préféré » du projet s'il est actif ; sinon le premier compte actif, dans l'ordre des réglages, dont aucune fenêtre n'a passé « Pause au-delà du quota » et qui n'est ni sous la pause qui suit une limite d'usage ni retenu par un agent qui attend sa remise à zéro ; tous au seuil, le premier actif (de préférence un compte que « Reprendre maintenant » a libéré). La présence de Claude Code se vérifie sur le compte où partirait l'agent. La puce « Compte : Pro » (avec plusieurs comptes seulement, juste après le modèle) propose « Automatique (Pro) » (le compte préféré du projet, sinon le compte en cours) puis les comptes actifs (« Équipe (inactif) » pour un compte désactivé depuis) tant que l'agent n'a ni session, ni message, ni copie d'origine, ni tour en cours : son process préchauffé repart alors avec le nouveau compte ; ensuite elle est en lecture seule (« Le compte d’un agent ne change plus après son premier message (sa conversation est rangée dans ce compte). »). Le « Compte préféré » du projet est masqué avec un seul compte. Un toast dit une fois, quand le compte en cours quitte un compte qui vient de passer le seuil pour un compte sous le seuil : « Le compte Pro a atteint 95 % : les nouveaux agents partent sur Principal. » (le pourcentage est celui de la fenêtre qui va le plus loin) ; rien quand il redevient le premier utilisable, quand un compte est désactivé ou supprimé, ni quand tous les comptes ont passé le seuil (c'est la bannière de pause qui parle).
- **Pause du pilote auto, compte par compte.** Elle ne tombe que quand aucun compte n'est utilisable pour le projet (tous les comptes actifs en « Automatique », le compte préféré seul sinon) ; elle dure jusqu'à la plus proche remise à zéro. Un compte est retenu par une fenêtre au-delà du seuil, par la pause de 30 min qui suit une limite d'usage sans reprise prévue, ou par un agent à lui qui attend sa remise à zéro : cet agent ne retient plus que les tickets du compte (« Quota atteint — reprise à HH:MM » à la place des places libres, seulement quand tous les comptes du projet attendent). La bannière ajoute, avec plusieurs comptes, « Les comptes Principal et Pro ont passé le seuil. » (rien après une limite d'usage). « Reprendre maintenant » lève tous les comptes.
- **Reprise sur un autre compte.** Un tour arrêté par la limite d'usage propose, sur sa carte de fin de tour (dernier tour, agent ni au travail ni archivé), « Reprendre sur <compte> » pour le premier autre compte actif, connecté (un compte pas encore lu compte comme connecté) et sous « Pause au-delà du quota » (un compte au-delà n'est pas proposé : l'agent y retrouverait la limite), et un menu « Reprendre sur un autre compte » quand il y en a plusieurs ; « Reprise automatique à … / Annuler la reprise » reste à côté. Le clic (le backend vérifie seulement que le compte est connu, actif et autre que celui de l'agent) : sous le verrou de lancement de l'agent, son process est détaché, son entrée fermée et sa sortie attendue (10 s, puis `kill` et 5 s de plus ; échec lisible, rien n'est copié) ; **ensuite seulement** la session (`projects/*/<id>.jsonl` du dossier du compte et le dossier voisin `<id>/` : sous-agents, résultats d'outils) est copiée dans le dossier de l'autre compte, sous le même nom de dossier de projet : le plus récent gagne fichier par fichier (un fichier de destination au moins aussi récent est gardé), la copie reprend la date de la source et passe par un fichier `.part` ; `file-history/`, `todos/` et `session-env/` ne sont pas copiés ; un identifiant de session qui n'est pas `[A-Za-z0-9_-]+` est refusé. Puis l'agent change de compte, sa reprise planifiée est effacée, une note le dit dans la conversation (« L’agent reprend sur le compte Équipe (il était sur Pro). ») et il reçoit « continue » comme à la reprise automatique. Jamais deux process sur la même session ; un message envoyé pendant le déplacement attend sa fin.
  - Échec : si le tour qui suit échoue (connexion absente, erreur de l'API) ou si Claude Code s'arrête avant de démarrer (session introuvable, connexion refusée), la carte dit « La reprise sur Pro a échoué : <erreur>. » et propose « Revenir sur Principal » (si ce compte existe et est actif) : le déplacement inverse recopie la session avec ce que le tour raté y a ajouté, puis remet l'attente de la remise à zéro du compte quitté, même quand son quota n'est plus lisible (sauf reprise automatique coupée depuis ; pour un agent de ticket sans reprise possible, le ticket est bloqué comme après toute limite sans reprise). La session de l'agent n'est jamais vidée par cet échec. Le compte d'avant est oublié à la fin du premier tour qui n'est pas une erreur.
  - Automatique pour un agent de ticket « En cours » arrêté par la limite (jamais un agent ordinaire, jamais un ticket bloqué) : réglage Claude Code › « Reprendre sur un autre compte un agent de ticket arrêté par la limite » (désactivé par défaut, parce que la reprise sur un compte réel n'a pas été vérifiée : voir la limite ci-dessous ; visible avec plusieurs comptes) : l'agent part sur le compte que choisit la règle ci-dessus (compte préféré du projet compris), s'il est autre que le sien, connecté, sans agent qui attend sa remise à zéro, sans pause ni fenêtre au-delà du seuil ; sinon, ou si le projet préfère le compte de l'agent, il attend la remise à zéro comme avant. Le compte quitté est retenu jusqu'à la remise à zéro que sa reprise attendait, sinon 30 min : il ne reçoit ni nouveau ticket ni le retour de cet agent à la limite suivante, même si ses fenêtres sont inconnues (sans quoi deux comptes limités se renverraient l'agent). Un déplacement qui échoue laisse l'agent attendre (« Reprise sur un autre compte impossible : … »).
  - **Limite connue : non vérifié avec un second compte réel.** Vérifié : `claude -p --resume <id>` lancé depuis le même dossier de travail avec un autre `CLAUDE_CONFIG_DIR` trouve une session copiée dans son `projects/<cwd encodé>/` (sans connexion le refus porte sur la connexion, « Not logged in » ; un identifiant inconnu donne « No conversation found with session ID »). Non vérifié : que l'API accepte une conversation commencée sur un autre compte (blocs de réflexion signés) ; un refus arrive comme une erreur du premier tour, le cas que la carte sait dire et défaire.
- **Réservations et projet fermé.** « Réservé aux projets » (`Account.projects`, les ids des projets) : fermer un projet en gardant son historique le laisse dans la liste de chaque compte (le fichier `closed-projects/<id>.json` ne retient plus les comptes) ; il n'en sort que quand son historique est effacé (la case « Effacer aussi son historique » à la fermeture, ou « Effacer l'historique… » d'un projet fermé). Un compte réservé seulement à un projet fermé ne sert donc aucun projet ouvert (la règle des réservations, sans exception). Réglages › Comptes Claude le montre : la liste « Réservé aux projets » du compte garde ce projet, coché et marqué « {nom} (fermé) » (“{name} (closed)”), qu'on peut décocher comme un projet ouvert (le compte l'oublie alors, comme avant). Le nom vient de `closed_projects`, lu à l'ouverture de l'onglet ; un id que ni les projets ouverts ni les fermés ne connaissent (ni un fichier illisible) reste invisible. Le groupe s'affiche aussi sans projet ouvert quand le compte est réservé à un projet fermé, et « Tous les projets » ne s'affiche que si la liste du compte est vide. Rouvrir le projet (même id) ne remet rien : les comptes n'ont pas bougé ; son « Compte préféré », s'il n'existe plus, repasse sur Automatique. Voir *Fermer un projet, retrouver son historique*.
- Statistiques et compte : chaque tour et chaque prompt est enregistré avec le compte de l'agent à ce moment (colonne `account` de `turns` et `prompts`, ajoutée à la première ouverture d'une ancienne base, qui compte pour Principal ; un agent repris sur un autre compte compte chaque tour pour le compte de ce tour). Voir *Stats*.
- Serveur MCP : déclaré dans chaque compte actif, avec le `claude` et le dossier du compte ; un compte ajouté plus tard le reçoit aussi (voir *Serveur MCP*).

## Serveur MCP

- Escouade sert ses outils à Claude (un terminal, un autre outil, ses propres agents) : un Claude lit l'état d'Escouade et agit dessus. Serveur MCP « Streamable HTTP » (SDK `rmcp` 3.5 derrière `hyper`), sans état, réponses JSON, sur `http://127.0.0.1:<port>/mcp`, la boucle locale seulement. Il tourne quand « Claude et les agents peuvent piloter Escouade » est activé, et s'arrête avec l'app. Port : libre, entre 47000 et 47999, choisi au premier démarrage et gardé dans les réglages (`mcpPort`) pour que la config de Claude reste valable d'un démarrage à l'autre ; s'il est pris au démarrage suivant, un autre est choisi, enregistré, et la déclaration refaite. Les deux poignées de main passent (`initialize` en `2025-11-25`, et le chemin `2026-07-28` que prend Claude Code 2.1.296). Pas de pont stdio en 1.7 (Claude Desktop n'est pas pris en charge).
- **Jeton et garde-fous.** Chaque requête est vérifiée avant le SDK : un `Host` autre que `127.0.0.1:<port>` ou `localhost:<port>` (ou absent) → 403 (contre le DNS rebinding) ; un en-tête `Origin` (une page web) → 403 ; `Authorization: Bearer` absent ou inconnu → 401 (comparaison à temps constant) ; un autre chemin que `/mcp` → 404. Une connexion a 10 s pour envoyer sa requête, 64 connexions au plus à la fois. Jetons de 32 octets aléatoires : celui de Claude hors Escouade (trousseau du système, entrée `mcp`, ou `mcp-token.json` lisible par son seul propriétaire quand le trousseau refuse), et celui de chaque process d'un agent d'Escouade (en mémoire et dans son fichier de config) ; le jeton dit qui appelle, et l'identité d'un agent ne s'imite pas.
- **Déclaration dans Claude Code.** Réglages › Claude Code › « Escouade dans Claude » : l'interrupteur « Claude et les agents peuvent piloter Escouade » (enregistré tout de suite, hors brouillon ; « Claude peut piloter Escouade » jusqu'à la 1.7) démarre le serveur, le donne aux agents d'Escouade (ci-dessous) et le déclare dans la config de **chaque compte actif**, par `claude mcp add --scope user --transport http escouade http://127.0.0.1:<port>/mcp --header "Authorization: Bearer <jeton>"` lancé avec le `claude` et le `CLAUDE_CONFIG_DIR` du compte (jamais pour Principal, dont l'entrée va dans `~/.claude.json`). Escouade compare en lisant l'entrée `mcpServers.escouade` du `.claude.json` du compte (la CLI ne sert qu'à écrire : `claude mcp get` se connecte au serveur) : identique, rien n'est lancé ; absente, `add` ; différente (autre port, autre jeton), `remove` puis `add`. Un compte ajouté ou réactivé plus tard reçoit la déclaration, un changement de port la refait partout, et l'app la relit à chaque démarrage. L'onglet dit « Déclaré dans Claude · compte Principal, compte Pro » ; pour un compte où ça échoue : la raison et la commande à lancer à la main (jeton masqué à l'écran, « Copier la commande » copie la vraie, écrite pour PowerShell ou pour sh). Le jeton est écrit **en clair** dans le `.claude.json` du compte, ce que l'onglet dit (`headersHelper` est écarté pour la 1.7). Désactiver change d'abord le jeton externe, dès que l'interrupteur est coupé (l'ancien n'ouvre plus rien tout de suite, quoi que fassent les commandes qui suivent), oublie les jetons des agents avec leurs fichiers (les agents déjà lancés perdent les outils tout de suite ; rallumé dans la même session, l'interrupteur ne les leur rend qu'au prochain démarrage de leur process : « Outils d'Escouade au prochain démarrage »), puis retire l'entrée de chaque compte ; supprimer un compte retire la sienne.
- **Agents d'Escouade.** Le même interrupteur les sert, ceux de tous les projets (décision du 2026-10-15, ESC-91 : il n'y a plus de réglage par projet ; « Serveur MCP › Les agents peuvent utiliser Escouade », dans les réglages d'un projet jusqu'à la 1.7, a disparu, et un `agentsUseEscouade` resté dans `state.json` est ignoré). Activé et serveur en marche : leur process reçoit `--mcp-config <dossier de données>/mcp/<id>.json` avec un jeton à lui, nouveau à chaque lancement, dans un fichier privé (0600 sous Unix), oublié quand ce process se termine, à la suppression de l'agent, à la fermeture du projet et à l'arrêt de l'app. Désactivé, ou activé alors que le serveur est arrêté : l'agent est tenu à l'écart du serveur, car une entrée `escouade` de la config de l'utilisateur peut rester déclarée et l'agent l'hériterait (il agirait comme « Claude (hors Escouade) ») : `--disallowedTools mcp__escouade` lui refuse les outils, et `--settings <dossier de données>/mcp-refused.json` (`{"deniedMcpServers": [{"serverName": "escouade"}]}`) empêche Claude Code de charger le serveur, faute de quoi l'agent recevrait ses instructions sans aucun de ses outils (constaté, ESC-91) ; en vue Claude Code, ce refus entre dans le fichier `--settings` des hooks (Claude Code ne lit que le dernier `--settings`). Un serveur passé par `--mcp-config` remplace celui du même nom de la portée `user`. Ce n'est **pas un cloisonnement** : un agent qui a les outils n'agit que dans son propre projet, mais lit les autres (sauf les images de leurs tickets), et il agit toujours par ses autres outils.
- **Outils d'Escouade au prochain démarrage.** Un agent dont le process (ou l'interface, en vue Claude Code) a démarré sans les outils alors qu'un démarrage les lui donnerait maintenant (l'interrupteur activé depuis) le dit : `escouadeNext` dans sa vue, recalculé à chaque changement de l'interrupteur ou du serveur (`Core::mark_escouade_next`), jamais vrai sans process vivant. Sa conversation montre « Outils d'Escouade au prochain démarrage » avec « Relancer » (`restart_agent_process`) : agent au repos seulement (ni tour en cours, ni question ou autorisation en attente, ni préparation de worktree, ni sous-agent ou workflow en arrière-plan : sinon « Il pourra être relancé quand il aura fini ce qu'il fait. » et le bouton attend ; refusé aussi pour un agent archivé), son process s'arrête (entrée fermée, tué au bout de 10 s), puis le suivant reprend la même session (`--resume`) : la conversation reste, une commande lancée en arrière-plan s'arrête ; en vue Claude Code, « Relancer » redémarre son interface sur sa session. Le process n'est jamais relancé tout seul. Sous l'interrupteur, Réglages › Claude Code compte ces agents (« 1 agent déjà lancé aura les outils au prochain démarrage de son process : « Relancer » sur sa conversation. »).
- **Outils** (annotés lecture seule ou non ; réponse : un bloc de texte JSON, clés en camelCase, sauf `get_ticket_image` qui répond un bloc image puis un bloc de texte JSON ; formats dans `docs/PROTOCOL.md`). sans lui, c'est l'état de chaque ticket à l'appel qui sert de comparaison ; un client qui annule la requête, ou coupe la connexion, arrête l'attente). Le remote control se lit, sans outil de plus (ESC-103) : `list_agents` (chaque agent) et `get_agent_summary` donnent `remoteControl` (vrai quand il est en vigueur pour l'agent maintenant, donc sa session est joignable depuis claude.ai, son process restant debout), `remoteSource` (ce qui l'a allumé : `"hand"`, l'utilisateur au clic droit de l'agent ; `"project"`, le réglage du projet ; `"global"`, le réglage de tous les agents, qui passe avant celui du projet quand les deux sont allumés ; `"off"`, l'agent que l'utilisateur a mis à part par « Désactiver le remote control » au clic droit, à qui aucun réglage ne le redonne, redémarrage compris, tant qu'il ne l'allume pas à la main ; `null` quand il n'est pas en vigueur et que l'agent n'est pas mis à part : `remoteControl: true` va donc avec `"hand"`, `"project"` ou `"global"`, `remoteControl: false` avec `"off"` ou `null`), `remoteState` (l'état du lien avec claude.ai que Claude Code rapporte pour l'agent : `"ready"`, en attente de connexion ; `"connected"` ; `"unavailable"`, en vue Claude Code, quand l'interface tourne mais que Claude Code n'a pas ouvert le remote control : compte sans abonnement claude.ai, réseau, proxy ou règle de l'organisation ; `null` sans lien en cours) et `interfaceRemote` (pour un agent en vue Claude Code : vrai quand son interface tourne et a été lancée avec le remote control, donc liée à claude.ai jusqu'à son prochain lancement, même si `remoteControl` est repassé à faux après une désactivation ; faux quand elle tourne sans ; `null` quand aucune interface ne tourne, agent hors vue Claude Code ou interface pas lancée) ; `list_projects` (chaque projet) donne `remoteControl` (le réglage « Remote control pour les agents de ce projet ») et `remoteControlAll` (le réglage « Remote control pour tous les agents », le même sur chaque ligne : allumé, il couvre tous les agents de tous les projets et l'interrupteur du projet est grisé dans la fenêtre). Actions : `create_ticket` (avec, au choix, des images : leur contenu en base64 ou le chemin d'un fichier local), `update_ticket` (ajoute des images à la fin, en retire par leur fichier ou leur rang ; celles qu'on ne nomme pas sont gardées), `move_ticket` (réordonne un ticket « À faire » : en tête, en bas, avant un autre), `start_ticket` (avec, au choix, le modèle et l'effort de ce ticket seul, qui passent avant ceux du Kanban pour son agent : garder Opus sur un ticket d'architecture quand le Kanban est sur Sonnet ; `""` remet ceux du Kanban ; le ticket garde son choix s'il est renvoyé puis relancé ; la réponse dit avec quoi son agent part, sans `effort` quand le modèle de son agent n'en prend pas, comme Haiku, dont l'agent part aussi en mode « Demander » si son mode serait Auto), `set_board` (règle le Kanban d'un projet : n'importe lesquels de après validation, branche cible, stratégie, brouillon, nettoyage, commits conventionnels, conflit, en parallèle, pilote auto, modèle, effort, mode et tests d'abord ; les champs laissés de côté ne changent pas, `""` pour le modèle, l'effort ou le mode remet celui de l'app ; la fenêtre se met à jour et le Kanban replanifie, allumer le pilote auto peut démarrer des tickets ; cela vaut pour les prochains agents de tickets, pas pour ceux déjà lancés ; un agent qui mène le Kanban (un « chef d'escouade ») peut ainsi passer les agents de tickets sur Sonnet pour ménager le quota ; **décidé le 2026-10-15 (ESC-98) : un agent d'Escouade règle le Kanban de son propre projet comme la fenêtre, mode compris** (`auto`, `default`, `plan`, `acceptEdits`), `bypassPermissions` restant refusé ; sa réponse est le Kanban après le changement, et le journal d'activité garde pour chaque appel réussi chaque champ changé avec sa valeur avant et après, ou « Aucun changement »), `create_agent` (projet, message de départ, worktree ou non, modèle), `send_message`, `stop_agent`, `answer_permission` (autoriser ou refuser une permission, avec un message au refus ; approuver ou renvoyer un plan, comme la carte de la fenêtre) et `answer_question` (répondre à une question avec les libellés des options ou un texte libre, au format de la carte de question). Le flux du Kanban, comme les boutons de la fenêtre : `approve_ticket` (« Valider… » : les tests si le Kanban les lance, le commit, puis ce que dit l'action à la validation du projet — merge dans la branche cible, push et pull request, push de la branche ou branche gardée ; une branche déjà fusionnée à la main dans la cible est close sans fusionner de nouveau ; il répond une fois la validation partie, la suite se suit par `wait_ticket` ou `get_ticket`), `reject_ticket` (« Renvoyer » : le ticket repart « En cours » avec le même agent et le même worktree, le commentaire lui est envoyé), `resume_ticket` (« Reprendre » un ticket bloqué « En cours »), `resolve_conflict` (« L'agent résout » : un ticket « À tester » arrêté sur un conflit de merge), `dismiss_block` (« Annuler » : le blocage d'un ticket « À tester », conflit ou étape en échec, s'efface, le ticket reste en place) et `delete_ticket` (« Supprimer », quelle que soit la colonne ; refusé tant que la validation du ticket tourne). `approve_ticket`, `reject_ticket`, `resume_ticket`, `resolve_conflict` et `dismiss_block` répondent aussi `since` : le curseur de `wait_ticket` du ticket tel qu'il était avant l'action, à lui passer pour que la suite, une validation rapide comprise, soit dite aussitôt. Réservés aux agents d'Escouade (refusés à Claude hors Escouade, notés « refusé ») : `report_progress` (une ligne d'état de 120 caractères au plus, sans caractère caché, affichée sous le nom de l'agent, dans la vue d'ensemble et sur la carte de son ticket « En cours » jusqu'au prochain appel) et `split_ticket` (1 à 10 tickets créés en fin de « À faire », après celui de l'agent : à la suite l'un de l'autre, ou tous en parallèle ; chacun reprend, en copies à lui, toutes les images du ticket de l'agent, ou seulement celles qu'il nomme, ou aucune ; par défaut, une image dont le fichier a disparu est sautée, la réponse le dit). Un projet ou un agent se nomme par son nom (sans tenir compte de la casse) ou son id, un ticket par sa clé ou son id ; un nom inconnu ou ambigu donne une erreur qui propose jusqu'à cinq choix.
- **Exclus volontairement.** Aucun outil ne lance une commande de l'appelant ni ne supprime un projet ou un agent : un agent poussé par un contenu piégé pourrait s'en servir pour monter en droits. Plus tard, éventuellement, avec une confirmation dans la fenêtre. Les tests, le merge et la suppression d'un ticket ne partent que par les outils du flux du Kanban, qui font ce que font les boutons de la fenêtre (ESC-90) : `approve_ticket` est ouvert à tout client du serveur, Claude hors Escouade comme les agents de tous les projets (un agent d'Escouade seulement dans son propre projet, et jamais sur son propre ticket), et `delete_ticket` supprime comme la fenêtre, un ticket de n'importe quelle colonne. C'est une montée en droits assumée : un agent poussé par un contenu piégé peut valider ou supprimer le ticket d'un autre agent de son projet. Seuls `answer_permission` et `answer_question` répondent à la place de l'utilisateur, et **jamais par « Toujours autoriser »** : `answer_permission` n'offre que `allow` et `deny`, et `always` est refusé avec la raison (une règle de permission durable reste la décision de l'utilisateur, à prendre dans la fenêtre) ; de même, `set_board` ne met pas le mode `bypassPermissions` (lancer des agents sans aucune demande de permission, comme « Toujours autoriser », est la décision de l'utilisateur, dans la fenêtre ; refusé sauf s'il est déjà le mode du Kanban) et ne règle pas la commande de test (une commande que le Kanban lancerait : `testsFirst: true` sans commande de test est refusé pour l'allumer, la commande se règle dans la fenêtre). Le remote control se lit seulement (décidé le 2026-10-15, ESC-103) : aucun outil ne l'allume, ne l'éteint ni ne le règle, pour un agent, un projet ou tous, parce que l'allumer expose une session sur internet (joignable depuis claude.ai et l'app mobile) ; cela reste la décision de l'utilisateur, dans la fenêtre (Réglages › Claude Code, Réglages › Projets, clic droit d'un agent), comme le mode `bypassPermissions` et la commande de test du Kanban, que les outils ne règlent pas non plus. Les descriptions de `list_projects`, `list_agents` et `get_agent_summary` le disent. Une fois l'interrupteur « Claude et les agents peuvent piloter Escouade » allumé, tout client du serveur voit les demandes (lecture ouverte à tous les projets) et peut y répondre, Claude hors Escouade comme les agents de tous les projets, sans réglage de plus ni limite de ce qu'il peut autoriser (décidé le 2026-10-15, ESC-92) ; un agent d'Escouade ne répond qu'aux demandes des agents de son propre projet, jamais aux siennes. C'est une montée en droits assumée : un agent poussé par un contenu piégé peut autoriser une commande demandée par un autre agent de son projet, une demande à la fois, jamais durablement et jamais hors de son projet.
- **Garde-fous de l'action**, ceux de la fenêtre et du pilote auto : `start_ticket` et `create_agent` ne sont refusés pour la pause que si aucun compte n'est utilisable pour le projet, `send_message` que si le compte de l'agent visé est retenu (le refus dit jusqu'à quelle heure) ; le maximum « En parallèle » du projet n'est pas dépassé ; un ticket qui attend d'autres tickets n'est pas lancé, une dépendance qui ferait attendre deux tickets l'un l'autre est refusée ; un ticket parti n'est ni modifié, ni déplacé, ni relancé ; un agent ne s'écrit pas et ne s'arrête pas lui-même, et on n'écrit pas à un agent archivé. Un agent ne répond jamais à ses propres demandes ; une demande qui n'attend plus de réponse (l'utilisateur dans la fenêtre ou un autre client y a répondu, l'agent ne tourne plus) est refusée avec ce motif, jamais deux réponses ; un agent en vue Claude Code n'a rien à répondre ici (ses demandes sont dans son terminal) et le refus le dit. **`set_board` a les contrôles de la fenêtre** : modèle connu, effort parmi `low`, `medium`, `high`, `xhigh` et `max`, mode parmi `auto`, `default`, `plan` et `acceptEdits`, branche cible = une branche locale du projet, « En parallèle » de 1 à 6 ; refusés : `bypassPermissions` (sauf s'il est déjà le mode du Kanban) et `testsFirst: true` sans commande de test, pour l'allumer seulement ; aucun champ donné : erreur. L'aller-retour `get_board` → `set_board` passe toujours : une cible égale à celle du Kanban (même vide, sur une HEAD détachée) ou à celle que `get_board` montre est laissée telle quelle, sans contrôle, même si la branche a été supprimée depuis, toute autre doit être une branche locale du projet (une cible vide qui diffère de celle du Kanban est une erreur), et un `testsFirst` déjà allumé passe. `start_ticket`, qui n'a pas de mode, donne les mêmes contrôles au modèle et à l'effort d'un ticket, et à eux seuls. Un agent d'Escouade règle le Kanban de son propre projet comme la fenêtre, mode compris (`bypassPermissions` refusé). **Un agent d'Escouade n'agit que dans son propre projet** (tickets, agents, messages, réponses aux demandes, Kanban) et lit les autres ; Claude hors Escouade agit sur n'importe quel projet. Les outils passent par la même fonction du cœur que la fenêtre : mêmes événements, synchro Jira / Trello / GitHub, replanification du Kanban.
- **Garde-fous du flux du Kanban.** Chaque outil est refusé là où la fenêtre refuse : `approve_ticket` et `reject_ticket` pour un ticket qui n'est pas « À tester », dont l'agent travaille ou dont la validation tourne déjà ; `resume_ticket` pour un ticket qui n'est pas « En cours », qui n'est pas bloqué ou dont l'agent attend la remise à zéro de son quota (le refus dit jusqu'à quand) ; `resolve_conflict` pour un ticket « À tester » sans conflit ; `dismiss_block` pour un ticket « À tester » qui n'est pas bloqué, ou dont la validation tourne ; `delete_ticket` pour un ticket dont la validation tourne (« La validation de ce ticket est en cours : attends sa fin pour le supprimer. »). `reject_ticket` refuse un commentaire vide (« Dis ce qui ne va pas. »), et le commentaire que l'agent lit est suivi de « (renvoyé par <auteur> via Escouade) », jamais pris pour les mots de l'utilisateur. Un message que le flux envoie à un agent (`reject_ticket`, `resolve_conflict`, `resume_ticket`) n'est remis que tant que le compte Claude de cet agent n'est pas retenu, comme `send_message` ; `resume_ticket` d'un ticket dont l'agent a disparu, qui repart avec un nouvel agent, est refusé quand aucun compte n'est utilisable pour le projet. **Un agent d'Escouade ne valide ni ne renvoie son propre ticket** (valider, ce serait fusionner son travail sans relecture), et n'agit pas non plus sur lui avec `resume_ticket`, `resolve_conflict`, `dismiss_block` et `delete_ticket` : c'est à l'utilisateur ou à un autre client de le faire. Il n'agit que dans son propre projet, comme pour les autres outils. Chaque appel passe dans le journal d'activité du serveur, refusé ou non.
- **Images d'un ticket (ESC-102).** `create_ticket`, `update_ticket` et `split_ticket` passent par les fonctions du cœur de la fenêtre, donc par ses limites et ses refus : PNG, JPEG, GIF et WebP (le type est lu dans le contenu, pas dans celui qu'on déclare), 5 Mo par image, 18 Mo en tout, 20 images au plus par ticket, les gardées comptées ; une image refusée ne laisse rien (ni ticket, ni clé, ni fichier). Le total de 18 Mo est tenu avant de lire : l'image qui le ferait dépasser est refusée avant d'être lue, pas après avoir lu toute la liste. `update_ticket` vérifie d'abord que le ticket est « À faire » et refuse sinon sans lire les fichiers donnés. Une image à joindre est donnée par son contenu en base64 (`data`, avec un `name`) ou par le chemin d'un fichier local (`path`). **Un agent d'Escouade n'attache par `path` qu'un fichier sous son dossier de travail** (les liens, symboliques ou jonctions, qui en sortent sont refusés, la vérification se faisant sur le fichier ouvert) : c'est un garde-fou du serveur, pas une frontière de sécurité (un agent qui a la main sur sa machine a d'autres voies), et un fichier hors du dossier reçoit le même refus qu'il existe ou non, pour ne rien dire de son existence ; Claude hors Escouade lit n'importe quel chemin absolu. Sont refusés : un chemin relatif, un chemin réseau ou de périphérique Windows (`\\…`, `//…`), ce qui n'est pas un fichier ordinaire, un fichier de plus de 5 Mo (refusé sur sa taille, avant d'être lu). Le nom d'une image est nettoyé (ce qui suit le dernier `/` ou `\`, sur une ligne, sans caractère caché ; 100 caractères au plus) : il s'affiche et part dans le premier message de l'agent. Une image se désigne par son `file` ou son `index`, jamais par un chemin : une référence qui ne correspond à aucune image du ticket est refusée sans rien toucher. `update_ticket` garde les images qu'il ne nomme pas, et un ticket parti garde les siennes (il ne se modifie pas). `split_ticket`, par défaut, saute une image du ticket d'origine dont le fichier a disparu et le dit dans sa réponse (`{ tickets, skipped }`, le tableau des clés quand rien n'est sauté) ; une image nommée dans `images` dont le fichier manque reste une erreur, sans rien créer. Un appel dont les arguments ne collent pas au schéma est noté au journal d'un message fixe et ne renvoie au client que le texte de l'erreur coupé avant toute valeur citée (jamais un chemin ni du base64), 300 caractères au plus. Le journal d'activité garde combien d'images (`images: 2`, `addImages: 1 · removeImages: 2`), jamais leur contenu ni un chemin.
- **Origine toujours dite.** Un texte venu du serveur n'est jamais pris pour les mots de l'utilisateur : `send_message` et le premier message de `create_agent` sont remis à l'agent, et montrés dans sa conversation, sous « Message de <auteur> : » (« Message from <author>: »), l'auteur étant le nom de l'agent qui appelle ou « Claude (hors Escouade) » ; un texte qui commence par `/` n'est plus une commande, et l'en-tête ne compte pas dans le nom que Haiku donne à l'agent. La description d'un ticket créé par `create_ticket` ou `split_ticket` se termine, après une ligne vide, par « Créé par <auteur> via Escouade » : visible sur la carte et dans le protocole de son agent. `update_ticket` termine de même la description qu'il écrit, par « Modifié par <auteur> via Escouade » (pas quand il ne change que des images ou des dépendances) ; une ligne d'origine finale de la description donnée (« Créé par … » ou « Modifié par … ») est remplacée, jamais empilée. Une demande à laquelle le serveur a répondu le dit de même : la carte de la demande, dans la conversation de l'agent qui la posait, montre « Autorisé par <auteur> via Escouade », « Refusé par <auteur> via Escouade » ou « Répondu par <auteur> via Escouade » (« Allowed by <author> through Escouade »…), l'auteur étant celui du journal d'activité ; rien de tel quand c'est l'utilisateur qui a répondu dans la fenêtre. Une approbation (`allow`, un plan approuvé) arrive à Claude sans auteur : c'est Claude Code qui écrit lui-même « User has approved… », rien de ce que le serveur envoie n'y est lu ; seuls les refus et les réponses aux questions sont signés pour Claude, et la carte de la conversation dit toujours qui a approuvé. Un refus dit aussi à Claude qui a refusé (« Refusé par <auteur> via Escouade : <message> »), jamais que l'utilisateur l'a fait. Une réponse à une question de même : chaque réponse que Claude Code reçoit est suivie de « (réponse de <auteur> via Escouade) » (« (answer from <author> through Escouade) »), les options choisies comme le texte libre, dans la langue des textes pour Claude ; la carte garde la réponse telle qu'elle a été choisie, et une réponse de l'utilisateur dans la fenêtre n'a pas de suffixe. L'événement de l'agent est envoyé comme pour une réponse de la fenêtre : la pastille d'attente s'en va et l'agent repasse en cours.
- **Autorisations.** Les outils d'Escouade passent par les mêmes demandes de permission que les autres (`mcp__escouade__*`). La carte nomme l'outil en clair (« Escouade · Créer un ticket », « Escouade · Lancer un agent »…) et liste ce que Claude lui donne, un argument par ligne, les textes sur plusieurs lignes tels quels, 2 000 caractères au plus chacun (au-delà, la carte dit combien ne sont pas montrés et renvoie à la conversation) ; la vue d'ensemble n'y répond pas (« À lire dans la conversation avant de répondre. »).
- **Activité.** Réglages › Claude Code › « Activité MCP » : les 200 derniers appels et refus, en mémoire, les plus récents en tête (heure, appelant, outil, résumé, résultat « Fait » / « Refusé » / « Erreur »), mis à jour en direct, avec « Effacer » ; jamais un jeton. Chaque appel y figure, un outil inconnu ou des arguments invalides compris, et chaque requête refusée avant d'atteindre un outil. Pour chaque `set_board` réussi, le résumé garde ce qui a été demandé et le journal garde chaque champ changé avec sa valeur avant et après (« model: opus → sonnet · effort: (défaut) → medium »), ou « Aucun changement ».

## Notifications

- Déclencheurs : question de Claude (AskUserQuestion / permission), fin de tour, erreur (tour en erreur, limite d'usage, process arrêté), et les tickets (ci-dessous).
- Titre : « <projet> · <agent> ». Les textes suivent la langue de l'interface (« Autoriser Bash : npm test ? » / « Allow Bash: npm test? »). Corps (120 caractères au plus, « … » à la coupe, sur une ligne) : autorisation « Autoriser <Outil> : <argument> ? » (le premier de la commande Bash, du fichier depuis le dossier de l'agent, de l'URL, de la requête, du motif, de la description… ; sans argument « Autoriser <Outil> ? ») ; plan à approuver (ExitPlanMode) « Approuver le plan : <première ligne du plan, sans markdown> ? », ou « Approuver le plan ? » sans texte ; question : le texte de la première question, sans markdown (« Claude attend ta réponse » à défaut) ; fin de tour : la première ligne de la réponse finale (le texte après le dernier outil du tour), sans markdown, sinon « Tâche terminée » ; erreur : « Erreur : <raison> » (« Claude Code s'est arrêté (code N) » pour un process mort). Le texte entre accents graves est repris tel quel (`*.log`, `__init__.py`). Limite : un outil MCP s'affiche sous son nom brut (`mcp__serveur__outil`).
- Réglages › Notifications › « Me prévenir pour » : « Questions et autorisations », « Tâches terminées », « Erreurs », « Tickets (prêt à tester, bloqué) », tous activés par défaut. Désactivé, un type n'a ni notification système ni carillon (« Désactivé : ni notification système ni carillon pour ce type ; l'onglet, la carte et la barre des tâches signalent toujours l'agent. », « le Dock » sous macOS) ; l'onglet et la carte de l'agent clignotent quand même, et la barre des tâches (le Dock) signale toujours l'agent.
- Kanban : « ATL-42 prêt à tester », « ATL-42 bloqué : <raison> » (clic → Kanban du projet) ; pas de notification par fin de tour d'un agent de ticket « En cours » (ses questions notifient).
- Dans l'app : pastilles pulsantes (onglet, carte agent, barre de statut) + carillon du design (2 notes synthétisées), coupable via « ♪ On/Off ».
- App en arrière-plan / tray : toast Windows (clic → ouvre l'agent) + clignotement barre des tâches + badge tray. Sous macOS : notification du système, rebond de l'icône du Dock, badge dans la barre des menus.
- Redémarrage pour mise à jour : « Escouade redémarre pour se mettre à jour » 30 s avant, avec un bouton « Plus tard » sous Windows, envoyée quel que soit le réglage des notifications système (voir *Livraison*).

## Barre de statut

Actifs · en attente · terminés │ `5h <barre> reset 3h01` · `7j <barre> reset 4j 12h` (en anglais `5h … reset 3h01` · `W … reset 4d 12h`) │ Coût du jour │ ⎇ branche ↑ à pousser ↓ à tirer │ mise à jour │ ♪ · ⚙ (réglages).

- Quotas : ceux du compte en cours, celui où partiraient les nouveaux agents (le premier compte actif sous le seuil de « Pause au-delà du quota », sinon le premier actif) : la fenêtre de 5 h (`5h`) et la fenêtre hebdomadaire (`7j`, `W` en anglais), chacune une barre puis « reset » et le temps restant. Le pourcentage n'est pas écrit : il est dans une infobulle avec la remise à zéro (« 42 % · remise à zéro le 10/10 à 18:00 »), au survol de la barre et à son focus clavier. La barre est un `role="meter"` (sa valeur est lue par les lecteurs d'écran) et passe à la couleur d'alerte au-delà de 80 % (pas à 80 %). Quota non lu : « Quota indisponible ». Les libellés, l'infobulle et le panneau suivent la langue de l'interface.
- Plusieurs comptes : le nom du compte en cours précède les quotas (« Pro · 5h … » ; coupé à 160 px, entier dans l'infobulle) et tout le groupe est un bouton (`aria-haspopup`, nommé « Quotas par compte (compte en cours : Pro) », les deux fenêtres dites aux lecteurs d'écran ; infobulle au focus clavier seulement, que Échap retire) qui ouvre le panneau « Quotas des comptes Claude » au-dessus de la barre. Le compte en cours y est en tête, marqué « en cours », puis les autres dans l'ordre des réglages, chacun avec ses deux fenêtres (barre, pourcentage écrit, remise à zéro) et « Aujourd'hui : 1,20 $ » (« ≈ » tant qu'un tour tourne ; la somme des comptes est le « Coût du jour » de la barre) ; « au-delà du seuil de pause » pour un compte qui a passé « Pause au-delà du quota » ; un compte inactif, pas connecté (« Pas connecté ») ou à la connexion expirée (« Connexion expirée : relance Claude Code pour ce compte. ») est grisé avec sa raison. Échap, un clic dehors ou un nouveau clic sur le groupe le ferment ; le focus va dans le panneau à l'ouverture et revient au bouton à la fermeture. Avec un seul compte, le groupe n'est pas un bouton (et n'écrit pas de nom).
- Coût du jour : le total de tous les comptes.

- Mise à jour : « Mise à jour X… » pendant le téléchargement, puis « Mise à jour X prête · Redémarrer » (ouvre la modale de la mise à jour), et pendant les 30 s qui précèdent un redémarrage automatique « Redémarrage dans N s » avec « Plus tard » (voir *Livraison*).

- Branche et synchro git : pour le projet affiché, si son dossier est un dépôt git (une HEAD détachée s'écrit « HEAD détachée »). Avec un dépôt distant : ↓ en couleur d'attente quand il y a des commits à tirer ; infobulle : branche suivie et dernier fetch ; « non publiée » ou « distante supprimée » sans branche suivie. L'avance et le retard s'écrivent à côté du nom (« ↑2 ↓5 »). Clic → le sélecteur de branche, au-dessus de la barre (voir *Branches*).

- Quotas : lus compte par compte (voir *Comptes Claude*) ; les `rate_limit_event` du stream d'un agent mettent à jour les fenêtres de son compte.
- Coûts : équivalent API (compte Max). Le coût exact de chaque tour vient de Claude Code à la fin du tour ; pendant le tour, tokens et coût (préfixé « ≈ ») montent en direct, estimés à partir des tarifs publics (`pricing.rs`), puis remplacés par le chiffre exact. Les statistiques n'enregistrent que les coûts exacts.

## Claude Code installé dans WSL (Windows)

But : sous Windows, faire tourner les agents avec un Claude Code installé seulement dans une distribution WSL (ticket GitHub #3), sans script intermédiaire.

- **Chemin** (Réglages › Claude Code, ou l'exécutable d'un compte) : `\\wsl.localhost\<distribution>\…` ou `\\wsl$\<distribution>\…` (la distribution du chemin, jamais lancé comme un programme de Windows), un chemin Linux `/home/<utilisateur>/…`, ou `~/…`. `~` désigne d'abord un programme de Windows sous `%UserProfile%` (`~/.local/bin/claude` y trouve le `claude.exe` de l'installeur natif), sinon le dossier personnel Linux de l'utilisateur par défaut de la distribution. Un chemin Linux va à la distribution de Réglages › Terminaux › « Distribution WSL », sinon à celle par défaut. Partout, `~` est le dossier personnel, et sous Windows `.exe` ou `.cmd` peut être omis. Champ vide : le `claude` de Windows (PATH, installeurs), sinon celui de la distribution, cherché dans `~/.local/bin`, `~/.claude/local`, `/usr/local/bin` puis `/usr/bin`.
- **Recherche** : distributions et distribution par défaut lues dans le registre de WSL. L'utilisateur sous lequel `wsl.exe` lance est celui que nomme `[user] default` de `/etc/wsl.conf` (une distribution importée, dont le registre dit root), sinon celui du registre (`DefaultUid`). Son dossier personnel vient de `/etc/passwd`, sinon il est demandé à la distribution (`$HOME`). La racine des lecteurs vient de `[automount] root` de `/etc/wsl.conf` (`/mnt/` par défaut). Ces fichiers sont lus par le partage `\\wsl.localhost`. Le programme y est présent s'il est un fichier ou un lien (Windows ne suit pas les liens de WSL, et `~/.local/bin/claude` de l'installeur natif en est un). Sinon, la distribution elle-même le confirme (`[ -f <chemin> ]`, 20 s au plus), ce qui suit un dossier lien comme `/bin`. Regarder dans une distribution arrêtée la démarre : chaque compte actif cherche donc son `claude` au démarrage, hors du fil de la fenêtre. Un programme trouvé reste trouvé. Un programme introuvable est recherché de nouveau 5 min plus tard, ou tout de suite quand la ligne sous le champ le demande. Enregistrer un chemin fait tout rechercher de nouveau.
- **Lancement** : `wsl.exe -d <distribution> --exec /bin/sh -c '<script>' <claude> <dossier Linux> <arguments>`. Le script entre dans le dossier de l'agent (`cd`) ou s'arrête (code 126), car `wsl.exe`, lui, tomberait sans un mot sur le dossier personnel ou sur `/`. Un dossier qui n'a pas de chemin dans WSL (un partage réseau, le dossier d'une autre distribution) est refusé : « Le dossier <dossier> n'est pas joignable depuis WSL (Ubuntu) : le Claude Code qui y est installé ne peut pas y travailler. » Une variable posée sur `wsl.exe` n'atteint Linux que si `WSLENV` la nomme, donc chacune y est nommée (réseau, liste de tâches, `CLAUDE_CONFIG_DIR`, `ESCOUADE_HOOK_TOKEN`, `TERM` et `COLORTERM` des terminaux). Aucune ne passe sur la ligne de commande, ni un jeton ni le mot de passe d'un proxy. `WSL_UTF8=1` fait écrire ses propres messages à `wsl.exe` en UTF-8 plutôt qu'en UTF-16. `--mcp-config`, `--settings` et `CLAUDE_CONFIG_DIR` passent par leur chemin Linux. Sans shell entre les deux, aucun argument n'est lu comme du code. `wsl.exe` refuse un argument vide (`--tools ""`, `--setting-sources ""`) : un marqueur le remplace, que le script remet à vide. Le script met aussi le dossier du programme en tête du `PATH` (une installation npm sous nvm y trouve son `node`). Les cinq lancements y passent : agent, `claude -p` (réponse JSON cherchée aussi après une ligne d'avertissement), `claude mcp add|remove`, vue Claude Code et connexion d'un compte. Les lignes de sa sortie qui ne sont pas des trames (un message de `wsl.exe`) rejoignent son message de fin, avec sa sortie d'erreur. Tuer `wsl.exe` (le Job de l'agent) arrête le processus Linux et ce qu'il a lancé, sauf ce qui s'est détaché (`setsid`).
- **Dossier de Claude Code** : celui de Principal est le `~/.claude` (et `~/.claude.json`) du dossier personnel Linux. L'app le lit par `\\wsl.localhost\<distribution>\home\…` : sessions de la vue Claude Code, connexion et quota, e-mail, déclaration MCP. La commande MCP à lancer à la main est écrite pour le shell de la distribution. Un compte ajouté garde son dossier sous `~/.escouade/claude/<compte>` de Windows, donné à Claude par son chemin `/mnt/c/…`. Partager les éléments de Principal depuis WSL se fait par copie (une jonction ne mène pas dans WSL). Une session ne passe pas d'un compte qui fait tourner Claude Code sous Windows à un compte où il tourne dans WSL, ni l'inverse : Claude Code range une session sous le dossier où il tourne, que WSL écrit autrement. « Reprendre sur… » le refuse : « Le compte « Pro » fait tourner Claude Code dans WSL, celui de l'agent sous Windows : sa session ne passe pas de l'un à l'autre. » La reprise automatique d'un agent de ticket ne choisit qu'un compte du même côté.
- **Chemins que donne Claude** : `/mnt/<lecteur>/…` se lit `<lecteur>:/…` (fichiers touchés, plans, autorisations) ; le `transcript_path` des hooks de la vue Claude Code se lit par le partage. Le texte d'une copie de conversation (« … travaillait dans <dossier> ») donne les dossiers en `/mnt/c/…`.
- **Worktrees** : git de Windows écrit `gitdir: C:/…` dans le `.git` d'un worktree, chemin que git de Linux ne suit pas. Avant chaque démarrage d'un `claude` de WSL, le `.git` du worktree de l'agent est donc réécrit en chemin relatif (`gitdir: ../../../.git/worktrees/<nom>`), que les deux lisent.
- **Réseau** : le serveur MCP et les hooks de la vue Claude Code écoutent sur 127.0.0.1 de Windows, que WSL ne joint qu'en réseau miroir (`networkingMode=mirrored` sous `[wsl2]` dans `%UserProfile%\.wslconfig`). En NAT (le défaut), les conversations marchent, mais pas les outils MCP d'Escouade ni le suivi en direct de la vue Claude Code (son transcript reste lu).
- **Réglages › Claude Code** : sous le chemin, une ligne dit où est son `claude`, redemandée 250 ms après chaque frappe (une réponse à un chemin d'avant est écartée) : « Trouvé : <chemin> », « Trouvé dans WSL (<distribution>) : <chemin> », ou « Introuvable. Indique le chemin de claude.exe, ou de Claude Code installé dans WSL : ~/.local/bin/claude, /home/<utilisateur>/…, ou \\wsl.localhost\<distribution>\…. » (sous macOS et Linux : « Introuvable. Indique le chemin de claude. »). Pour un `claude` de WSL en NAT, une note sous le groupe : « Le réseau de WSL est en NAT : le serveur MCP d'Escouade et le suivi de la vue Claude Code ne joignent pas l'app. Passe-le en mode miroir (networkingMode=mirrored sous [wsl2] dans %UserProfile%\.wslconfig), puis lance wsl --shutdown. » Enregistrer un autre chemin ou une autre distribution met à jour le bandeau « Claude Code introuvable » du Kanban et l'indice du champ, sans redémarrer.
- **Limites** : Claude Code est lancé sans le profil du shell (`~/.profile`, `~/.bashrc` ne sont pas lus) : une variable ou un `PATH` qui n'y est posé (clé d'API, nvm d'un serveur MCP) lui manque. git de WSL lit sa propre configuration (`user.name`, `core.autocrlf` : un dépôt extrait en CRLF par Windows peut y paraître modifié). Le lien du dépôt vers un worktree (`.git/worktrees/<nom>/gitdir`) reste en `C:/…` : git de WSL tient ce worktree pour absent dans `git worktree list`. Les fichiers sous `/mnt/c` sont plus lents qu'en Linux. Une racine des lecteurs autre que `/mnt/` n'est pas reconnue dans les chemins que donne Claude. Les éléments de Principal qui sont des liens dans WSL ne sont ni proposés ni copiés à la création d'un compte. Un projet rangé dans la distribution (`\\wsl.localhost\…`) n'est pas pris en charge.

## Réglages (⚙ barre de statut ou `Ctrl+,` → modale)

Une seule modale pour toute l'app : ses onglets à gauche (point sur un onglet modifié, version d'Escouade en bas), un onglet à la fois sous son titre et sa description. « Enregistrer » enregistre d'un coup ce qui a changé dans tous les onglets et tous les projets, chaque partie par-dessus ce que l'app a alors (le Kanban avance seul) ; refusé, avec la raison, tant qu'un projet n'a pas de nom, qu'une commande de lancement n'a pas de nom ou de ligne de commande, ou que son dossier des worktrees ou un préfixe de branche n'est pas valide ; ce qui n'a pas pu être enregistré reste dans la modale. « Annuler », Échap ou × jettent tout.

- **Application** (en tête) : « Langue de l'interface » (« Système (…) » par défaut, « English », « Français ») et « Langue des textes rédigés par Claude » (« Comme l'interface » par défaut) : voir *Langues* ; groupe « Dictée » : modèle et langue parlée (voir *Dictée*).
- **Claude Code** : chemin de `claude` (avec, dessous, où est le `claude` de ce chemin : voir *Claude Code installé dans WSL*), modèle / effort / mode par défaut des nouveaux agents, reprise automatique après la limite d'usage, « Reprendre sur un autre compte un agent de ticket arrêté par la limite » (avec plusieurs comptes : voir *Comptes Claude*), « Les agents tiennent une liste de tâches » (activé par défaut : voir *Avancée d'un agent qui exécute un plan*), arrêt des process inactifs ; puis les groupes « Remote control » (« Remote control pour tous les agents » : voir *Barre latérale projet*), « Escouade dans Claude » (« Claude et les agents peuvent piloter Escouade ») et « Activité MCP » (voir *Serveur MCP*).
- **Comptes Claude** : la liste des comptes, « Ajouter un compte… », « Se connecter… » (voir *Comptes Claude*).
- **Notifications** : « Me prévenir pour » (questions et autorisations, tâches terminées, erreurs, tickets), notifications Windows, son (activé, « ▶ Tester »).
- **Projets** (sélecteur de projet, celui affiché par défaut) : nom, dossier (« Ouvrir »), couleur, « Compte préféré » (avec plusieurs comptes) ; « Remote control pour les agents de ce projet » (groupe « Remote control », grisé et allumé tant que le réglage global l'est : voir *Barre latérale projet*) ; Git : « Commit » (« Rédigé par l'agent » par défaut, ou « Direct, avec un message proposé » : voir *Git & fichiers*) ; worktree par agent, dossier des worktrees, préfixes des branches des agents et des tickets (voir *Git & fichiers*), fichiers copiés dans les worktrees, commandes de préparation et de démontage des worktrees (« ✦ Remplir automatiquement » ; « Monter » / « Descendre ») ; commandes de lancement (« ✦ Remplir automatiquement » aussi ; chacun des deux boutons est décrit par le texte de sa rangée pour les lecteurs d'écran) ; « Fermer le projet… » (sa confirmation, avec la case « Effacer aussi son historique (conversations, tickets, réglages) » décochée par défaut, revient aux réglages, acceptée ou non, brouillon intact ; voir *Fermer un projet, retrouver son historique*) ; en dessous, le groupe « Projets fermés » (seulement s'il y en a) avec, par projet, « Rouvrir » (la fenêtre d'ajout, sur son dossier et sur cet historique-là) et « Effacer l'historique… », et « Historique illisible » avec « Effacer » pour un fichier que l'app ne sait pas lire. Rien sur le serveur MCP : l'interrupteur de l'onglet « Claude Code » sert les agents de tous les projets (voir *Serveur MCP*).
- **Kanban** (même sélecteur) : action à la validation (branche cible, stratégie ou PR en brouillon), commande de tests et « Relancer les tests avant », suppression du worktree une fois validé, message de commit généré (avec son aperçu), conflit, pilote auto, « Pause au-delà du quota » (« pour tous les projets » : un réglage de l'app, qui marque aussi cet onglet comme modifié), agents en parallèle et leurs modèle / effort / mode.
- **Intégrations** (même sélecteur) : comptes Jira, Trello, GitHub, sources liées au projet, correspondance des statuts, synchronisation et import automatique (voir *Intégrations*).

- **Réseau** : proxy et certificats (ci-dessous).
- **À propos** : version, « Rechercher une mise à jour », « Installer les mises à jour automatiquement » (activé par défaut : « Escouade redémarre d'elle-même quand aucun agent ne travaille et que tout est enregistré. »), données locales.

- **Certificats** : les requêtes de l'app (intégrations, quotas, mises à jour) font confiance aux autorités habituelles et à celles du magasin du système (le certificat d'un proxy d'entreprise qui y est installé) ; Claude Code garde sa propre liste. « Ignorer la vérification des certificats TLS » (désactivé par défaut), pour un proxy qui déchiffre le trafic avec un certificat que le système ne reconnaît pas (« UnknownIssuer ») : plus aucun certificat vérifié pour les intégrations, les quotas, les mises à jour, ni les process `claude` (`NODE_TLS_REJECT_UNAUTHORIZED=0`, au prochain démarrage de leur process, hérité par les commandes que lancent les agents) ; les terminaux et les commandes des worktrees ne sont pas concernés. Les mises à jour sont donc vérifiées et installées par le backend (le plugin de mise à jour ne lit ce réglage qu'à la compilation), avec les réglages réseau du moment.
- Les coûts enregistrés viennent directement de Claude Code (`costUSD` par modèle). La grille de `pricing.rs` ne sert qu'à l'estimation en cours de tour ; un modèle absent de la grille n'a simplement pas d'estimation.

## Dictée (ESC-96, issue #8)

Dicter un prompt au lieu de le taper. Design : `docs/superpowers/specs/2026-10-15-dictee-vocale-design.md`.

- Bouton micro du compositeur (entre le trombone et « Envoyer ») et, en vue Claude Code, de l'en-tête de l'agent ; `Ctrl+Maj+M` (`⌘⇧M`) partout, terminal compris. Bascule : un clic écoute, un second arrête et transcrit. Pendant l'écoute, bouton rouge et jauge du niveau ; en vue Claude Code, un indicateur sur le terminal (« Dictée en cours · ⌘⇧M pour arrêter », puis « Transcription… »). `Échap` dans le compositeur annule la dictée (rien n'est inséré, Claude n'est pas interrompu).
- Une dictée à la fois (un micro), pour la cible fixée au départ : le compositeur d'un agent (texte inséré à la place de la sélection ou au curseur, espace ajoutée avant s'il suit un mot et après seulement devant une lettre ou un chiffre, jamais envoyé ; l'agent n'est plus affiché : ajouté à la fin de son brouillon) ou son terminal en vue Claude Code (collé, pas validé ; terminal fermé : copié dans le presse-papiers, toast). Un clic ou le raccourci pendant une écoute l'arrête, quelle que soit sa cible.
- Capture côté Rust (`voice::capture`, cpal, dans un fil à lui ; mono, rééchantillonné en 16 kHz) ; transcription locale par Whisper (`voice::transcribe`, whisper-rs) : rien ne part en ligne. Modèle chargé à la première dictée, libéré après 5 minutes sans dictée. Silence : rien n'est transcrit (« Rien entendu »). Arrêt automatique à 5 minutes (toast), micro débranché : ce qui a été capté est transcrit. Sous macOS, l'accès au micro est demandé au système avant d'écouter (`AVCaptureDevice`, la première fois) ; refusé, ou une seconde de zéros exacts (micro coupé ailleurs) : arrêt, toast « Escouade n'a pas accès au micro » et, sous macOS, « Ouvrir les réglages » (Confidentialité › Micro). Les `.part` d'un téléchargement interrompu (app quittée) sont effacés à la liste suivante des modèles.
- Modèles (`voice::models`) : Tiny (78 Mo), Base (148 Mo), Small (`small-q5_1`, 190 Mo, défaut et recommandé), Large turbo (574 Mo), téléchargés depuis Hugging Face à la demande dans `<données>/voice/` (en `.part`, SHA-256 vérifié, par le proxy des réglages, sans limite de durée). Le modèle choisi absent : fenêtre « Dictée vocale » (les quatre, le réglage présélectionné, choix enregistré avant le téléchargement, progression, « Réessayer » après une erreur), puis l'écoute démarre. Fichier illisible : supprimé, retéléchargé à la dictée suivante.
- Réglages › Application › Dictée : « Modèle » (télécharger, progression et annuler, supprimer ; le choix suit « Enregistrer ») et « Langue parlée » (langue de l'interface par défaut, détection automatique, français, anglais, espagnol, allemand, italien, portugais, néerlandais).
- macOS : `NSMicrophoneUsageDescription` (anglais, français par `fr.lproj/InfoPlist.strings`) et droit `com.apple.security.device.audio-input` (`Entitlements.plist`). Linux : `libasound2-dev` en CI et au release. Build : cmake (whisper.cpp).
- Plus tard : le formulaire des tickets, un service de transcription en ligne avec la clé de l'utilisateur.

## Raccourcis (défauts)

Sous macOS, `Ctrl` devient `Cmd` (sauf `Ctrl+Tab`) ; `Ctrl+Alt` (AltGr) n'est jamais un raccourci.

- App : `Ctrl+1..9` projets · `Ctrl+Tab` / `Ctrl+Maj+Tab` agent suivant / précédent · `Ctrl+N` nouvel agent · `Ctrl+T` nouveau terminal · `Ctrl+J` prochain agent en attente (le focus dans son champ de saisie) · `Ctrl+K` rechercher dans les conversations · `Ctrl+P` ouvrir un fichier · `Ctrl+Maj+A` vue d'ensemble · `Ctrl+Maj+B` panneau des fichiers · `Ctrl+Maj+L` disposition · `Ctrl+Maj+M` dicter (arrête la dictée en cours, sinon écoute pour l'agent à l'écran) · `Ctrl+,` réglages.
- Conversation : `Ctrl+Entrée` / `Ctrl+Maj+Entrée` autoriser / toujours autoriser · `Alt+1..9` option d'une question, `Ctrl+Entrée` pour valider · `Échap` interrompre · `↑` (champ vide) rappeler le dernier message.
- Vue d'un sous-agent : `Échap` revient à la conversation de l'agent (sauf dans un champ qui contient du texte) · `Ctrl+Entrée`, dans « Lui écrire », envoie le message (il ne répond à aucune demande qui attend).
- Éditeur : `Ctrl+S` enregistrer · `Ctrl+F` chercher dans le fichier · `Ctrl+Maj+F` rechercher dans les fichiers · `Ctrl+clic` / `F12` aller à la définition · `Maj+F12` trouver les références · `Alt+←` / `Alt+→` revenir / avancer (macOS : `⌃-` / `⌃⇧-`, touche Contrôle) · `Alt+clic` ajouter un curseur · `F2` renommer et `Suppr` (`⌘⌫`) supprimer la ligne de l'arborescence.
- Fenêtre d'un ticket : `Ctrl+Entrée` ajouter / enregistrer le ticket depuis n'importe quel champ.
- Réglages : `Alt+↑` / `Alt+↓` déplacer une commande de préparation ou de démontage.
- Dans un terminal, les touches du shell lui restent (`Ctrl+C`, `Ctrl+R`, `Ctrl+N`, `Ctrl+K`, `Ctrl+P`…) ; l'app y prend `Ctrl+1..9`, `Ctrl+Tab`, `Ctrl+J`, `Ctrl+,`, `Ctrl+Maj+A` et `Ctrl+Maj+M`. Sous macOS, le shell ne reçoit jamais `Cmd` : les raccourcis de l'app y marchent, et `Cmd+C`, `Cmd+V`, `Cmd+A` restent au terminal (copier, coller, tout sélectionner).

## Livraison

- UI en français et en anglais, au choix des réglages, la langue du système par défaut (voir *Langues*).
- Installeur Windows (NSIS, par utilisateur, sans droits d'administrateur ; en anglais ou en français selon la langue du système), `.dmg` universel macOS (signé Developer ID et notarisé), AppImage et `.deb` Linux, mise à jour intégrée via GitHub Releases (`guillaume-gagnaire/escouade`). L'app cherche une nouvelle version 8 s après son lancement puis toutes les 5 minutes ; « Rechercher une mise à jour » dans les réglages vérifie à la demande. Un échec automatique se tait d'abord (un échec passager est réessayé, une erreur ne se montre qu'au bout d'une heure d'échecs) ; un échec demandé se montre toujours, avec sa cause (voir *Échecs* ci-dessous).
- Mises à jour (interface embarquée dans le binaire : pas de remplacement à chaud, une installation puis un redémarrage) :
  - une version trouvée est téléchargée tout de suite en arrière-plan (15 min au plus) et sa signature vérifiée ; ses octets sont gardés jusqu'à l'installation, une seule version prête à la fois (une plus récente remplace l'autre, une version retirée du serveur n'est jamais installée) ; un téléchargement raté relit `latest.json` et réessaie une fois, puis est retenté à la recherche suivante (*Échecs*, ci-dessous) ;
  - échecs, de la vérification comme du téléchargement :
    - une vérification est un essai (plus le repli sans proxy, voir plus bas) ; un échec passager (réseau, 403, 404, 408, 425, 429, 5xx, réponse illisible) est réessayé une fois après 3 s. Un téléchargement raté **relit `latest.json`** (nouvelle vérification) et, si la même version y est, réessaie une fois avec ce qu'elle donne ; sinon, ou s'il échoue encore, c'est l'échec ;
    - un échec **automatique** ne se montre qu'une fois les échecs enchaînés depuis au moins 1 h et au nombre d'au moins 3, et une seule fois par série ; une série dont le dernier échec date de plus de 30 min repart de zéro (un échec avant une mise en veille et deux au réveil ne font pas une alerte). La vérification et le téléchargement ont chacun leur série (un téléchargement refusé toutes les 5 min par un proxy finit par se dire, même si les vérifications passent) ; un succès termine la sienne (version trouvée ou rien de neuf pour la vérification, téléchargement réussi pour le téléchargement). « Rechercher une mise à jour » montre toujours l'échec, avec sa raison, et « Aucune mise à jour disponible. » seulement quand la vérification a répondu. Le toast d'un téléchargement raté propose « Télécharger dans le navigateur » et reste affiché 30 s : il ouvre la page de la release (`…/releases/tag/<tag>`, tirée du lien de téléchargement) seulement si ce lien, celui de `latest.json`, est sur github.com en https (ou sur la même origine, schéma, hôte et port, que l'endpoint de mise à jour ; jamais avec un identifiant dans l'adresse) ; sinon, la page des releases d'Escouade (`https://github.com/guillaume-gagnaire/escouade/releases/latest`) ;
    - la vérification et le téléchargement envoient `User-Agent: Escouade/<version> (<système>; <architecture>)` (Windows, macOS ou Linux), jamais celui d'un navigateur : Escouade ne déguise pas son trafic pour passer une règle de sécurité d'entreprise, elle s'annonce honnêtement pour qu'on puisse l'autoriser ;
    - le message (préfixé de « Vérification des mises à jour impossible : » ou « Téléchargement de la mise à jour impossible : ») dit le code HTTP, le domaine qui a répondu (après redirections), le proxy par lequel la requête est passée, et ce que la réponse dit d'elle-même (`Proxy-Agent`, `Server` ou page de blocage d'un proxy connu : Zscaler, Netskope, Squid, Blue Coat, Forcepoint, Fortinet, Palo Alto, Umbrella, Sophos, Skyhigh…, puis le début de la page), et ajoute « bloqué par le réseau ou un proxy ? » pour un 403. Pour un 407, il dit que le proxy demande une authentification et qu'il faut mettre l'identifiant et le mot de passe dans l'adresse du proxy, dans Réglages › Réseau (et non « Télécharge-le dans le navigateur »). Pour cela, un échec du plugin de mise à jour est suivi d'une sonde (la même requête GET, avec les mêmes proxy, TLS, User-Agent et `Accept`). Un proxy d'entreprise qui refuse l'installateur est nommé : « le proxy de ton entreprise (Zscaler/6.2) a refusé l'installateur (403 Forbidden de release-assets.githubusercontent.com, par le proxy 127.0.0.1:9000). Télécharge-le dans le navigateur : il faudra peut-être confirmer l'avertissement du proxy. » Il ne l'est que d'après `Proxy-Agent`, ou un `Server` ou une page de blocage qui nomme un proxy connu ; un `Via` ne suffit pas (un proxy comme Squid l'ajoute à toute réponse, même à un refus de GitHub). Le nom est coupé à 160 caractères. Aucun lien signé (la requête `?sig=…` des liens de GitHub) n'apparaît dans un message ni dans le journal ;
    - le repli sans proxy ne vaut que quand **le proxy lui-même est injoignable** (proxy de Réglages › Réseau réglé mais arrêté, poste hors du réseau de l'entreprise : connexion refusée ou délai dépassé vers le proxy) : la requête est refaite une fois sans proxy, le journal dit que l'accès direct a marché, et un message d'échec dit les deux essais (« connexion impossible à github.com par le proxy 127.0.0.1:9000 (…) ; sans proxy : connexion impossible à github.com (…) »). Un refus venu du proxy (403, 407, tunnel refusé) n'entraîne **aucun** essai sans proxy : Escouade ne contourne jamais une règle de l'entreprise, et le message explique (un tunnel refusé : « le proxy 127.0.0.1:9000 a refusé d'ouvrir la connexion à github.com (tunnel CONNECT refusé) : une règle de ton entreprise le bloque peut-être. », plus « Télécharge l'installateur dans le navigateur. » pour un téléchargement) (sans proxy réglé, la mise à jour suit celui du système, comme avant, sans repli ni nom de proxy dans le message) ;
  - modale « Escouade X est prête » : les notes de la version (markdown), « Plus tard » et « Redémarrer maintenant », désactivé avec des fichiers non enregistrés (« Enregistre d'abord tes fichiers : N fichiers ne sont pas enregistrés. », refusé aussi par le backend) ; avec des agents en tour ou en attente : « N agents travaillent ou attendent ta réponse : leur tour en cours sera interrompu. Les agents de ticket reprennent d'eux-mêmes ; les autres attendent ton prochain message. » (au singulier : « 1 agent travaille ou attend ta réponse : son tour en cours sera interrompu. S'il travaille sur un ticket, il reprend de lui-même ; sinon, il attend ton prochain message. ») ;
  - redémarrage automatique (« Installer les mises à jour automatiquement », activé par défaut ; jamais dans une exécution isolée `ESCOUADE_DATA_DIR`) quand l'app est au repos : aucun agent en tour, en question ou en préparation de worktree, rien en cours qu'un redémarrage couperait (ticket qui démarre, validation, merge, message en cours d'envoi, création ou copie d'agent, proposition ou commit direct, renommage ou suppression dans l'éditeur), aucun lancement de test en préparation, aucune commande de lancement en cours, aucun terminal avec une entrée ou une sortie depuis 5 min (un terminal au repos ne compte pas), aucun fichier non enregistré, aucune modale ouverte, et ni clavier ni souris depuis 5 min (ou fenêtre non visible). Prévenu 30 s avant par la notification « Escouade redémarre pour se mettre à jour » (bouton « Plus tard » sous Windows) et le compte à rebours de la barre de statut ; « Plus tard » repousse de 30 min, et tout ce qui rend l'app occupée pendant ces 30 s annule le redémarrage (la première touche ou le premier geste de souris est signalé tout de suite, et le redémarrage est annulé au plus 2 s après). Les brouillons des composers sont écrits avant. Sous macOS, quand remplacer l'app demanderait le mot de passe d'un administrateur, l'app ne redémarre jamais d'elle-même ;
  - installation : toujours après l'arrêt propre de l'app (préparations arrêtées, agents et terminaux arrêtés, état sauvegardé), borné à 15 s, hors du runtime ; Windows : installeur NSIS en mode `quiet` (aucune fenêtre), lancé par le plugin après cet arrêt ; macOS : le paquet `.app` est remplacé en place, puis l'app redémarre. Une installation ratée avant l'arrêt laisse l'app tourner ; après, l'app redémarre telle qu'elle était. Redémarrée d'elle-même, l'app revient comme elle était (fenêtre cachée dans la zone de notification ou la barre des menus, réduite dans la barre des tâches ou le Dock, derrière une autre app sans prendre le focus, ou devant ; noté dans `update.json` du dossier de données) ;
  - quitter (« Quitter », et sous macOS aussi Cmd+Q ou le Dock, si le paquet est modifiable sans administrateur) avec une mise à jour prête l'installe sans relancer l'app ; pendant une installation déjà en cours, « Quitter » attend sa fin (2 min au plus) au lieu de fermer l'app sous elle, et sous macOS Cmd+Q aussi (1 min au plus), sauf pour une installation qui attend le mot de passe d'un administrateur : l'app se ferme alors tout de suite, sans rien installer. Une fin de session Windows n'installe rien ;
  - au démarrage suivant : « Escouade X est installée. » avec « Voir les nouveautés » (la modale « Nouveautés d'Escouade X », « Fermer »). Une installation ratée (vue au démarrage suivant, ou pendant que l'app tourne) n'est plus retentée d'elle-même pour cette version pendant la session : « La mise à jour vers X n'a pas pu s'installer. » avec « Réessayer » (la modale) ; « Redémarrer maintenant » la retente. « Réessayer » et « Voir les nouveautés » n'ouvrent jamais leur modale par-dessus une autre (le toast revient pour plus tard) ; une mise à jour qui n'est plus prête le dit : « La mise à jour vers X n'est plus prête : Escouade te la proposera de nouveau une fois téléchargée. ». Un clic sur le bouton d'un toast laisse le focus où il était.
- CI/CD GitHub Actions :
  - `ci.yml` (push / PR) : lint + typecheck + tests frontend, `cargo fmt --check`, `clippy`, `cargo test`, build de vérification ; sous Windows et sous macOS (tests de bout en bout sous Windows seulement).
  - `release.yml` (tag `v*`) : la release GitHub est créée **en brouillon** (une release déjà là pour le tag y repasse) ; `tauri-action` → builds Windows, macOS et Linux (AppImage et `.deb`), qui déposent chacun leurs fichiers dans le brouillon par son id, avec la signature des artefacts de mise à jour (secret `TAURI_SIGNING_PRIVATE_KEY`), l'installeur, le `.dmg`, l'AppImage, le `.deb` et `latest.json` consommé par l'updater. Un dernier job (`scripts/release-check.mjs`) vérifie `latest.json` (version du tag ; plateformes `windows-x86_64`, `darwin-aarch64`, `darwin-x86_64` et `linux-x86_64` ; signature et lien de chaque entrée ; chaque fichier désigné présent et entier), puis publie la release (« latest », sauf une pré-version) et relit ce que lit l'updater : l'updater ne voit donc jamais une release à moitié construite. Un build raté laisse le brouillon (« latest » reste la précédente) ; relancer les jobs ratés est sans danger. Les notes de la release sont la section de sa version dans `CHANGELOG.md`.
- Commits atomiques sur `main`, sans push.
