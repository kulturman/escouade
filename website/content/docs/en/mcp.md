# The MCP server

Escouade’s MCP server lets Claude (in a terminal, in another tool, or as an Escouade agent) read your projects, agents, and tickets, create, edit, start, approve, and delete tickets, set a project’s Kanban, and drive agents, including answering their requests, under the same guardrails as the autopilot.

## What it is for

MCP (Model Context Protocol) is the protocol through which Claude Code calls tools. Escouade embeds an MCP server: once declared in Claude Code, it gives Claude the tools listed below.

- **Claude in a terminal**: you run `claude` wherever you like and talk to it about Escouade (“list the tickets to review in the api project”, “create a ticket to limit login attempts, then start it”).
- **Another tool** that speaks MCP can connect the same way (see [Token and network](#token-and-network)).
- **An Escouade agent**, of any project, with a token of its own (see [Escouade’s agents and the server](#escouade-s-agents-and-the-server)).

The server runs on your machine alone. It only serves to read and to give orders; it runs no command of its own choosing and deletes no project or agent. For a ticket, it does what the Kanban’s buttons do, approving (the tests, then the merge) and deleting included. It can answer an agent’s request on your behalf, but never with “Always allow”: a lasting permission rule stays your decision, in the window.

## Turning on “Claude and the agents can drive Escouade”

One switch gives the server to Claude outside Escouade and to the Escouade agents of every project.

1. Open Settings › Claude Code. The “Escouade in Claude” group has the “Claude and the agents can drive Escouade” switch.
2. Turn it on. It is saved at once, without “Save”: the declaration writes into the Claude Code config of each account, which “Cancel” could not undo.

Escouade then starts the server and declares it in Claude Code for each active account, with the command `claude mcp add --scope user --transport http escouade <address> --header "Authorization: Bearer <token>"`, run the way the account runs Claude Code (its executable, its configuration folder). The entry lands in the account’s `.claude.json` (`~/.claude.json` for “Main”). The tab says “Declared in Claude · Main account, Pro account”.

- An entry that is already up to date is left as it is. A different one (another port, another token) is replaced. An account added or reactivated later receives the declaration.
- If it fails for an account, the tab says so (“Not declared for the Pro account: …”) and shows the command to run by hand (“Run it by hand in PowerShell:”), written for PowerShell on Windows and for `sh` elsewhere. The token is masked on screen; “Copy the command” copies the real one.
- Turning the switch off changes the token at once, then removes the entry from every account. The agents already running lose the tools at once too (their tokens are forgotten): turned on again, the switch gives them back the next time their process starts (“Restart”). Deleting an account removes its own.
- If the server does not start, the tab says so (“The server did not start: …”).

Claude Code knows the server as `escouade`: its tools are called `mcp__escouade__<tool>` (for example `mcp__escouade__list_tickets`).

> [!NOTE]
> On Windows with Claude Code in WSL, Escouade’s MCP tools need WSL’s mirrored network: `networkingMode=mirrored` under `[wsl2]` in `%UserProfile%\.wslconfig`, then `wsl --shutdown`. Settings › Claude Code reminds you when WSL’s network is NAT.

## The tools

In the arguments, a project is named by its id or its name (any case), an agent by its id or its name, a ticket by its key (`ATL-12`, any case) or its id. Answers are JSON.

### Reading

These ten tools change nothing.

| Tool | Arguments | What it returns |
|---|---|---|
| `list_projects` | none | The projects, in the app’s order: id, name, folder, current git branch, number of agents (archived ones left out), number of tickets in each column, and the remote control settings: `remoteControl` (“Remote control for this project’s agents”) and `remoteControlAll` (“Remote control for all agents”, the same on every line; when on, it covers every agent of every project and the project’s switch is grayed out in the window). |
| `list_agents` | `project` (optional) | The agents that are not archived, oldest first, of every project or of one: id, name, project, status (`idle`, `running`, `waiting`, `done`, or `error`), whether a question or a permission is waiting for your answer and how many, the key of their ticket, model, Claude account, cost in dollars, and remote control. `remoteControl` says whether it is in effect for the agent right now, so whether its session is reachable from claude.ai. `remoteSource` says what turned it on: `hand` (you, with the right-click on the agent), `project` (the project’s setting) or `global` (the setting for all agents, which comes before the project’s when both are on); `off` when you set the agent apart with “Turn off remote control” (no setting gives it back, a restart included, until you turn it on by hand); `null` when it is not in effect and the agent is not set apart. So `remoteControl` is `true` with `hand`, `project` or `global`, and `false` with `off` or `null`. `remoteState` is the state of the link with claude.ai that Claude Code reports: `ready` (waiting for a connection), `connected` or `unavailable` (in the Claude Code view, the interface is running but Claude Code did not open remote control: no claude.ai subscription, network, proxy or organization policy); `null` with no link in progress. `interfaceRemote`, for an agent in the Claude Code view: `true` when its interface is running, started with remote control (it stays linked to claude.ai until its next launch, even if `remoteControl` went back to `false` after a turn-off), `false` when it runs without, `null` when none is running (an agent outside the Claude Code view, or an interface not started). |
| `list_tickets` | `project`, `column` (optional: `todo`, `doing`, `review`, or `done`) | A project’s tickets in the Kanban’s order: id, key, title, column, the keys of the tickets they wait for, their agent’s name, and why they are blocked. |
| `get_ticket` | `ticket` | A whole ticket: title, description, criteria (met or not, with the agent’s note), loops (the current one and the maximum), column, tickets it waits for, progress, its images (`index`, `file`, `name`, `mediaType`, and `size`: pasted or dropped in the ticket’s window, or attached through the server; its agent gets them with its first message), the external ticket it comes from (Jira, Trello, GitHub, or Linear), its model and effort when it has one of its own, and what it takes to follow its flow: its agent (id, name, status, requests waiting), its branch and worktree (its agent’s: once the ticket is done, the worktree may be gone), what blocks it (`blocked`, `conflict`), the validation step running (`step`) and, once it is done, its result (`outcome`: the text, the pull request’s address when there is one, the commit the merge made on the target branch). An Escouade agent may leave out `ticket` to read its own. |
| `get_ticket_image` | `ticket` (optional), `file` or `index` | One image of a ticket, which Claude receives as an image (the content), followed by its `index`, `file`, `name`, `mediaType`, and `size` in bytes. It is named by its `file` (the name `get_ticket` gives) or by its `index` (its rank in the list of `get_ticket`, from 0), one of the two only. An Escouade agent may leave out `ticket` to read an image of its own ticket, and only reads the images of the tickets of its own project (a screenshot’s content is more sensitive than the ticket itself, which `get_ticket` lets anyone read); Claude outside Escouade reads those of every project. An image the ticket doesn’t have (an unknown name, a rank outside the list) is refused, and no name ever leads to a file other than the ticket’s. |
| `get_usage` | none | Each Claude account’s quota: whether new agents start on it now, the use of its 5-hour and weekly windows (`pct` from 0 to 100, `resetsAt`), and why the autopilot holds the tickets back (`reason`: `fiveHour`, `week`, or `limit`), until when. |
| `get_board` | `project` | A project’s Kanban settings, those of the “Kanban” tab of its settings: `project` and `projectId` (the project’s name and its id), `action` (what “Approve” does: `merge`, `pr`, `push`, or `keep`), `target` (the target branch; the project’s current branch while the Kanban has none), `strategy` (`merge`, `squash`, or `rebase`), `draft`, `cleanup`, `conventional`, `conflict` (`ask`, `agent`, or `abort`), `maxParallel`, `autopilot`, the ticket agents’ `model`, `effort`, and `mode` (empty: those of the app, which `defaults` gives), `testsFirst` (true only if the Kanban has a test command), `testCommand`, and `prefix`. Open to every project. Its answer given back as is to `set_board` is accepted and changes nothing. |
| `get_agent_summary` | `agent`, `project` (optional) | An agent without its conversation: id, name, status, the ticket’s key, last message (2,000 characters at most; a longer message gives its start and its end), and the files it edited (the latest 100 at most), with the number and the type of the requests waiting for an answer, and its remote control (`remoteControl`, `remoteSource`, `remoteState` and `interfaceRemote`, as in `list_agents`). |
| `list_requests` | `agent` (optional), `project` (optional) | The questions and the permission requests waiting for your answer, of one agent, of one project, or of all, in the order they came: the agent and the key of its ticket, `request` (the id the two answering tools name), `type` (`permission`, `question`, or `plan` for a plan to approve), since when, the tool and what it acts on (the command, the file, the whole plan), everything Claude Code sent (the content of a file to write, the strings of an edit, the flags of a command), the reason, whether Claude Code would refuse it by default, and for a question its questions with their options and whether several may be picked. `cut` says whether a text was cut: the whole request is in the conversation. An agent in the Claude Code view has none here: its requests are in its terminal. |
| `wait_ticket` | `tickets` (1 to 20), `timeout` (optional), `since` (optional) | Waits until one of these tickets changes, then says what: its column, its block (`blocked`, `conflict`), its agent starting or ceasing to wait for an answer (`waiting`: `list_requests` gives the requests), its agent coming to rest in “To review” (`resting`: the ticket can be approved), or the ticket deleted (`gone`). Answers at the first change, or after `timeout` seconds (120 by default, 240 at most) with `changed: false`. Each answer gives a `since`: pass it to the next call (even after other tools) and a ticket whose state differs from the one it holds is answered at once, a change made between the two calls included; without `since`, each ticket’s state at the call is the one compared. If the client cancels the request or drops the connection, the wait stops. |

### Acting

These tools do what you would do in the window, through the same functions: the window is told, external tickets follow, and the Kanban updates.

| Tool | Arguments | What it does |
|---|---|---|
| `create_ticket` | `project`, `title`, `description`, `criteria`, `after`, `images` | Creates a “To do” ticket at the bottom of the column. `criteria` is a list (two default criteria without it), `after` the tickets it waits for, by key or id. `images` attaches images to the ticket, as its window does. With the autopilot on, it starts as soon as a slot is free and its predecessors are done. Its description ends with “Created by `<author>` through Escouade”. |
| `update_ticket` | `ticket`, `title`, `description`, `criteria`, `after`, `addImages`, `removeImages` | Edits a “To do” ticket, field by field: what is left out stays. `criteria` and `after` replace the whole list. `addImages` adds images at the end, `removeImages` takes some off: the ones neither names are kept (the whole list is never replaced, so a forgotten image is not lost), and the two combine. Images alone change nothing else, the description included. A ticket that has already started cannot be edited, images included, and the refusal comes before any file you gave is read; a dependency that would make two tickets wait for each other is refused. If the title, description, or criteria change, the last line of the description becomes “Modified by `<author>` through Escouade”. |
| `move_ticket` | `ticket`, `position` (`top`, `bottom`, or `before`), `before` | Puts a “To do” ticket at the top, at the bottom, or just before another “To do” ticket of the project (`before`). Returns the column’s keys in their new order. |
| `set_board` | `project`, and any of `action`, `target`, `strategy`, `draft`, `cleanup`, `conventional`, `conflict`, `maxParallel`, `autopilot`, `model`, `effort`, `mode`, `testsFirst` | Sets a project’s Kanban, as its settings window does: only the fields given change, and `""` for `model`, `effort`, or `mode` puts the app’s back. The checks are the window’s: a known model, an effort among `low`, `medium`, `high`, `xhigh`, or `max`, a mode among `auto`, `default`, `plan`, or `acceptEdits`, a target branch that is a local branch of the project, 1 to 6 tickets in parallel. The window updates and the Kanban replans: turning the autopilot on can start tickets. The change applies to the next ticket agents, not to those already started. Returns the Kanban after the change, in the format of `get_board`. An agent that runs the Kanban can thus move the ticket agents to Sonnet to spare the quota. The answer of `get_board` given back as is is always accepted and changes nothing: a `target` equal to the Kanban’s (even empty) or to the one `get_board` shows is left as is, unchecked, and `testsFirst` is refused without a test command only to turn it on. An Escouade agent sets the Kanban of its own project this way, mode included. With Haiku, which has no effort and no Auto mode, the ticket agents start without an effort and, if the mode is `auto`, in “Ask” mode. |
| `start_ticket` | `ticket`, `model`, `effort` | Starts a “To do” ticket as the “Start” button does: its agent starts as soon as a slot is free. Answers once the ticket is queued; follow it with `get_ticket`. `model` and `effort` apply to this ticket only and come before the Kanban’s for its agent (keep `opus` on an architecture ticket while the Kanban is on `sonnet`): `""` puts the Kanban’s back, left out they do not change, with the same checks as `set_board`. Returns `key`, `starting`, and the `model` and `effort` its agent will start with (the ticket’s, else the Kanban’s, else the app’s); `effort` is missing when that model takes none (Haiku, whose agent also starts in “Ask” mode if its mode would be `auto`). The ticket keeps its own if it is sent back and started again. Its card shows them, without the effort for Haiku, next to its key (“Opus · Max”). |
| `create_agent` | `project`, `message`, `worktree`, `model` | Creates an agent in a project, with its first message, without changing the agent you are looking at. `worktree` (true or false) says whether it works in a worktree of its own, otherwise the project decides; `model` is named as in Claude Code (`sonnet`, `opus`, `haiku`…). Returns the agent’s id and name. |
| `send_message` | `agent`, `project`, `text` | Writes to an agent. An agent at work reads the message after its current turn (the answer says `queued`). |
| `stop_agent` | `agent`, `project` | Interrupts an agent’s current turn, as the stop button of its conversation does. The agent stays, and can be sent a message afterward. |
| `answer_permission` | `agent`, `project`, `request`, `decision` (`allow` or `deny`), `message` | Answers an agent’s permission request as the “Allow” and “Deny” buttons of its card do, or approves (`allow`) or sends back (`deny`) its plan. `message`, with `deny`, tells the agent why, or what to do instead. “Always allow” is not offered (`always` is refused): a lasting rule stays your decision, in the window. The request’s card, in the agent’s conversation, says who answered (“Allowed by `<author>` through Escouade”), and the agent reads who refused. |
| `answer_question` | `agent`, `project`, `request`, `answers` | Answers an agent’s question as its question card does: for each question (`question`, its text, which can be left out when there is only one), the labels of the options picked (`choices`, several only when the question allows it) or a free text (`text`). Every question needs an answer. The card says “Answered by `<author>` through Escouade”, and the agent reads each answer followed by who gave it. |
| `approve_ticket` | `ticket` | Approves a “To review” ticket as the “Approve…” button does: the tests first when the Kanban runs them, the commit, then what the project’s Kanban settings say (merge into the target branch, push and open a pull request, push the branch, or keep it). A ticket whose branch brings nothing more than its target, because you already merged it by hand, is closed without merging again. Answers as soon as the approval has started, with the ticket (its step reads “Validation…” or “Approving…”, in the interface’s language) and its `since`: follow it with `wait_ticket` or `get_ticket`. It may push and open a pull request. |
| `reject_ticket` | `ticket`, `comment` | Sends a “To review” ticket back as “Send back” does: it goes back “In progress”, with the same agent and the same worktree, and the agent receives the comment as test feedback, followed by “(sent back by `<author>` through Escouade)”. An empty comment is refused. Returns the ticket and its `since`. |
| `resume_ticket` | `ticket` | Resumes a blocked “In progress” ticket as “Resume” does: its agent goes on, or the ticket starts again when its agent is gone. Refused for a ticket that is not blocked, or whose agent is waiting for its quota to reset (the refusal says until when). Returns the ticket and its `since`. |
| `resolve_conflict` | `ticket` | Hands the merge conflict of a “To review” ticket to its agent as “Let the agent resolve” does: the target branch is merged into its own, then the agent is asked to resolve the conflicts (to rebase, with the rebase strategy) and to end with its report. Refused for a ticket with no conflict. Returns the ticket and its `since`. |
| `dismiss_block` | `ticket` | Dismisses the block of a “To review” ticket (a conflict, a failed step) as “Cancel” does: the block goes, the ticket stays in “To review”, and nothing else changes. Returns the ticket and its `since`. |
| `delete_ticket` | `ticket` | Deletes a ticket of any column as “Delete” does. A ticket “In progress” or “To review” has its agent archived, its worktree kept; the tickets that came after it no longer wait for it. Cannot be undone. Refused while the ticket’s approval is running. Returns `key`, `deleted`, and `agentArchived`. |

A title is 200 characters at most, a description 10,000, and a ticket has 30 criteria of 500 characters at most. A ticket created by the server has the default number of loops, 5, and its own branch.

A ticket’s images are attached with `create_ticket` (`images`) and `update_ticket` (`addImages`). An image to attach is `{ name, mediaType, data, path }`, with exactly one of `data` (its content in base64, in which case `name` is required) or `path` (the path of a file on your machine, whose name stands in for `name` when it is missing). `mediaType` is only a hint: as in the window, the type is read from the content. To take images off with `removeImages`, or to read one with `get_ticket_image`, an image is named with `{ file, index }`: its `file`, the name `get_ticket` gives, or its `index`, its rank in the list of `get_ticket`, counting from 0.

### Leading the whole Kanban from Claude

With these tools, Claude takes a ticket from start to finish without you opening the window: `start_ticket` starts it, `wait_ticket` waits until it changes (its agent asks a question, moves to “To review”, gets blocked), `get_ticket` says where it stands, then `approve_ticket` approves it or `reject_ticket` sends it back with what is wrong. `resume_ticket`, `resolve_conflict`, and `dismiss_block` deal with a block, and `delete_ticket` deletes. `wait_ticket` hands back at the first change, or after 120 seconds by default (240 at most); the `since` of its answer, passed to the next call, has a ticket whose state differs from the one it holds answered at once, a change made between two calls included. `approve_ticket`, `reject_ticket`, `resume_ticket`, `resolve_conflict`, and `dismiss_block` also return a `since`, the ticket’s as it was before the action: passed to `wait_ticket`, it has what follows told at once, a quick approval included.

Each follows the rules of the window’s button and the guardrails below: an Escouade agent neither approves nor sends back its own ticket, and only acts in its own project.

### Reserved to Escouade’s agents

These two tools are refused to Claude outside Escouade.

| Tool | Arguments | What it does |
|---|---|---|
| `report_progress` | `line` | Publishes a status line of 120 characters at most, about what the agent is doing. It shows under its name in the sidebar and the overview, and on the card of its “In progress” ticket, until its next call. An empty line clears it. |
| `split_ticket` | `tickets`, `chain` | Splits what remains of the agent’s ticket into ten “To do” tickets at most, after its own. With `chain` true (the default), each comes after the one before and the first after the agent’s ticket; false, all come after the agent’s ticket alone and may run in parallel. Each ticket can have its `images`, which name images of the agent’s ticket (by `file` or `index`, as for `removeImages`): without that argument it takes them all, with `[]` none. Each gets its own copies, and the agent’s ticket keeps its own. An unknown reference, or an image named in `images` whose file is missing, refuses everything and creates nothing; without `images`, an image of the agent’s ticket whose file is gone is skipped instead of blocking the split. Refused to an agent without a ticket. Returns the keys of the tickets made or, if some images were skipped, `tickets` (the keys) and `skipped` (one sentence per skipped image). |

## The guardrails

The tools that act follow the rules of the window and of the autopilot:

- **Quota.** No ticket (`start_ticket`) or agent (`create_agent`) starts when no account is usable for the project: autopilot paused, quota window above the “Pause above quota” threshold, usage limit, an agent waiting for its reset. A single free account is enough. The refusal says until when (“The autopilot is paused until 14:30: the 5-hour window is 96% used. Try again then.”). `send_message` is refused when the agent’s account is held back that way (agents on another account can still take a message).
- **In parallel.** The project’s “In parallel” maximum of tickets is not exceeded by `start_ticket`, nor its maximum of agents working at once by `create_agent`.
- **Dependencies.** A ticket that comes after tickets that are not done is not started without them: the refusal says which ones, and `update_ticket` takes the dependencies off. A circular dependency is refused.
- **A ticket’s images.** The window’s limits and refusals: PNG, JPEG, GIF, and WebP (the type is read from the content), 5 MB per image, 18 MB in all, and 20 images at most per ticket, the ones `update_ticket` keeps included; the total is held before reading, and the image that would go over it is refused before it is read. A refused image leaves nothing behind: no ticket made, no change, no file. An image’s name is cleaned (what follows the last `/` or `\`, on one line, 100 characters at most). For `path`, Claude outside Escouade gives any absolute path to a file on your machine; an Escouade agent only a file under its working folder (a link, symbolic or junction, that leaves it is refused), and a file outside that folder gets the same refusal whether it exists or not. This is a safeguard of the server, not a security boundary: an agent that has control of your machine has other ways. Also refused: a relative or network path (`\\server\share`, `//host/share`), anything that is not an ordinary file, a file of more than 5 MB (refused without being read), and a file that is not an image. The path is not kept: the ticket keeps a copy of the content. A ticket that has already started keeps its images.
- **Setting the Kanban.** The model and the effort have the window’s checks in both tools, `set_board` and `start_ticket`: an unknown model, or an effort outside the list, is an error. The rest only applies to `set_board` (`start_ticket` has no mode). It refuses `bypassPermissions`: starting agents with no permission request at all stays your decision, in the window, like “Always allow” (it is accepted only if it is already the Kanban’s mode, to change something else without undoing it); the other modes (`auto`, `default`, `plan`, `acceptEdits`) are set as in the window, including by an Escouade agent for the Kanban of its own project. It also refuses `testsFirst` without a test command, only to turn it on: the server runs no command and does not change the Kanban’s, which is set in the window. A mode outside the list, a target branch that is not a local branch of the project (except the one the Kanban already has, even empty, or the one `get_board` shows: it is left as is), an “In parallel” outside 1 to 6, or no field to change, is an error.
- **Remote control.** `list_projects`, `list_agents` and `get_agent_summary` read it; no tool turns it on, turns it off or sets it, for an agent, a project or all of them: turning it on exposes a session on the internet, reachable from claude.ai and the Claude app. That stays your decision, in the window (Settings › Claude Code, Settings › Projects, right-click on an agent), like `bypassPermissions` and the Kanban’s test command, which the tools do not set either.
- **The Kanban.** `start_ticket` is refused when the project’s Kanban starts nothing for now (the target branch has no commit or is not found, no active account serves the project); the refusal says why.
- **Escouade’s agents** only act in their own project, Kanban included (they read the others, except the images of their tickets), do not write to themselves, do not stop themselves, and do not answer their own requests. You do not write to an archived agent.
- **The Kanban’s flow.** Each tool is refused where the window refuses: `approve_ticket` and `reject_ticket` for a ticket that is not in “To review”, whose agent is working, or whose approval is already running; `resume_ticket` for a ticket that is not “In progress”, is not blocked, or whose agent is waiting for its quota to reset; `resolve_conflict` for a ticket with no conflict; `dismiss_block` for a ticket that is not blocked; `delete_ticket` for a ticket whose approval is running. A message the flow sends to an agent (`reject_ticket`, `resolve_conflict`, `resume_ticket`) only goes while that agent’s Claude account is not held back. An Escouade agent neither approves nor sends back its own ticket (approving would merge its work without a review), and does not act on it either with `resume_ticket`, `resolve_conflict`, `dismiss_block`, and `delete_ticket`: it is up to you or another client. Any client of the server can approve a ticket, and `delete_ticket` deletes as the window does, a ticket of any column. Every call is logged in the MCP activity.
- **Answering a request.** Once “Claude and the agents can drive Escouade” is on, any client of the server sees the requests of every project and can answer them, Claude outside Escouade as well as the agents, with no extra setting; an agent only answers those of the agents of its own project, never its own. `answer_permission` only offers `allow` and `deny`: “Always allow” stays your decision, in the window. A request that no longer waits for an answer (you answered it in the window, another client did, or the agent no longer runs) is refused, and if two answers arrive at the same time, only one goes through. An agent in the Claude Code view has nothing to answer here: its requests are in its terminal.
- **No tool** runs a command of its own choosing or deletes a project or an agent: an agent pushed by booby-trapped content cannot use them to escalate its rights. The exceptions are answering the agents’ requests and the Kanban’s flow. With the switch on, an agent can allow, one request at a time and never for good, what another agent of its project asks; it can also approve (the tests, then the merge) or delete the ticket of another agent of its project, as you would in the window.
- **What comes from the server is never taken for you.** A message sent to an agent (`send_message`, the first message of `create_agent`) is read by the agent and shown in its conversation under “Message from `<author>`:”, the author being the name of the agent sending it or “Claude (outside Escouade)”. A ticket created or split by the server ends with “Created by `<author>` through Escouade”, a ticket it modified with “Modified by `<author>` through Escouade”, on its card as in its agent’s protocol. The card of a request the server answered says who did (“Allowed by `<author>` through Escouade”, “Denied by `<author>` through Escouade”, “Answered by `<author>` through Escouade”), and a refusal, like each answer to a question, tells Claude who it comes from, not that it is you (“Refused by `<author>` through Escouade”, “SQLite (answer from `<author>` through Escouade)”).

A permission request for an Escouade tool names it in plain words (“Escouade · Create a ticket”, “Escouade · Start an agent”…) and shows what Claude gives it, one argument per line. A value of more than 2,000 characters is cut: the card says how many are not shown and points you to the conversation.

## Escouade’s agents and the server

The “Claude and the agents can drive Escouade” switch also serves Escouade’s agents, those of every project: there is nothing to allow in a project’s settings.

- **On**, each agent receives the server when its process starts, with a token of its own: it acts in its own name, never as Claude outside Escouade. It reads the tickets and the agents, and can create tickets or start other agents, which uses quota, and take the tickets of its project through to their approval, except its own. It also sees the questions and permission requests of the agents of every project, and can answer those of the agents of its own project.
- **Off**, the agents already running lose the tools at once, and Escouade keeps its server away from every agent that starts, even when an `escouade` entry is left in your Claude Code config: its tools are refused, and the server itself is not loaded (Escouade starts the agent with Claude Code’s `deniedMcpServers` setting). The agent therefore gets neither the tools nor the server’s instructions.
- **An agent already running** when you turn the switch on keeps a process without the tools. Its conversation shows “Escouade’s tools at the next start” with “Restart”: its process stops and the next one resumes the same session: the conversation stays, a command running in the background stops. The button waits until it is done with what it is doing (its turn, your answer, the setup of its worktree, a subagent or a workflow in the background). In the Claude Code view, “Restart” starts its interface again. Settings › Claude Code says how many agents are in that case.
- It is not a partition: an agent only acts in its own project, but reads the others (except the images of their tickets).

The server runs while the switch is on, and stops with the app.

> [!NOTE]
> Up to 1.7, each project had its own “Agents can use Escouade” switch (Settings › Projects › MCP server). It is gone: a project that had it on while “Claude can drive Escouade” was off no longer gives the server to its agents until you turn “Claude and the agents can drive Escouade” on.

In a conversation, a call to an Escouade tool carries the label “Escouade · ” followed by its name (“Escouade · Read a ticket”, “Escouade · Set the Kanban”, “Escouade · Report progress”).

## MCP activity

Settings › Claude Code › “MCP activity” keeps the last 200 calls and refusals, the most recent first, updated live. Each line gives:

- the time (on hover, the date);
- the caller: the agent’s name, “Claude (outside Escouade)”, or “Unknown client” for a request refused before its token says where it comes from;
- the tool, and in short what it was asked (never a token; for images, how many, never their content or a path);
- the result: “Done”, “Refused”, or “Error”, with the reason for the last two (shown in the alert color).

For a `set_board` that succeeded, the line keeps what was asked and also says what changed: each changed field with its value before and after (“model: opus → sonnet · effort: (default) → medium”), or “No change”.

“Clear” empties the list. The log is not saved: it starts from zero the next time Escouade starts.

Also refused, and logged: a request without a token (“Request refused: no token”), with an unknown token, with an unexpected `Host` header, with an `Origin` header (a web page), or to a path other than the server’s.

## Token and network

- The server only listens on `127.0.0.1`, on a free port between 47000 and 47999, chosen at the first start and then kept (it only changes when its own is taken, and the declaration is then redone in every account).
- Every request carries a token, in the `Authorization: Bearer` header. Claude outside Escouade’s token is kept in the system keychain; when it refuses it, and on Linux, in `~/.escouade/mcp-token.json`, readable by you alone. It is also written in plain text in Claude Code’s config (`~/.claude.json` for “Main”). An agent’s token is its own, lives in memory and in a configuration file under `~/.escouade/mcp/` that the app removes when its process stops. An agent without the tools starts with `~/.escouade/mcp-refused.json`, which keeps the server out.
- A request sent by a web page (`Origin` header) or addressed to a name other than `127.0.0.1` or `localhost` is refused, even with a token: a site you visit cannot call the server.
- Another MCP client connects to `http://127.0.0.1:<port>/mcp` with the same header. The address and the token can be read in the account’s `.claude.json`, in the `escouade` entry, or in the command the tab offers when the declaration fails.
